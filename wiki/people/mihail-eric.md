# Mihail Eric

**Stanford 兼任教授（adjunct professor），开设 CS146S "The Modern Software Developer"（⚠️ 课程代号在自动字幕里作 "CS46 146s"，本库标为不可确证）；同时是 Monaco 的 Head of AI。** 本库自 2026-11-08 起有他的材料。

## 他最有价值的一条：把"初级岗位消失后人怎么获得品味"变成一条供给安排

（[00:10:06]–[00:13:06]）✅ **本库判这是他目前最该被长期保存的内容，因为它是本库该条线上第一条机构级处方。**

- **他要防的那件事**：**"那条裂缝出现在已经在行业里待过、知道怎么回事、然后采用了 coding agent 变得很厉害的资深的人，和只能说'好，那我们现在干什么'的初级的人之间。"**
- **做法**：**把作业从自编的教学练习改成向真实的 AI-native 开源仓库提交贡献**。
- ⚠️⚠️ **而承重点不是课程内容，是谁来做 review**：
  > **"在做这些项目的过程里，你会真的在和维护者对话。他们会 review 你的代码。他们会帮你建立起关于什么是好软件的心智模型。这样一来，就有了一次把真正的好软件设计的接力棒传下去的过程——而我觉得大多数学生是没有机会做这件事的。"**
- ✅ **本库对这条的定位**：⚠️ **[徐天音](tianyin-xu.md) 与 [John Platt](john-platt.md) 给的都是对个人的建议（学生自己要怎么练），而这一条是对**供给**的安排——它承认 review 与 mentorship 是稀缺品，然后去别处把它调来。**
- ⚠️⚠️ **本库的保留**：**开源维护者的 review 带宽远小于学生人数，而这门课能调到它靠的是授课者个人"花了整个夏天去谈"。作为一门课的设计成立，作为可推广的制度尚未被证明，而该期未讨论可推广性。** 详见 [AI 与教育](../topics/ai-and-education.md)。

## 他给的那条课堂现状描述（本库认为可独立引用）

- **第一周课堂调查**（[00:10:06]）：**"我周二调查过的每一个学生——没有一个人还真的在手打代码了。所有人都在用 coding agent。而这些是 Stanford 的大二、大三学生。"**
- ⚠️ **而工具占比他明确说还没问过**（"我还没调查，但这是个好提醒"）。✅ **本库记这是该期唯一一次接近"学生实际在用哪个工具"的量化机会，被放过了。**
- **他给学生的地板判断**（[00:06:01]）：**"地板高多了。只做到一个 L3 是不够的。你一般得比那个好，几乎要到 senior 的水平才进得去。"**

## 他的教学三层法：消费者 → 200 行基线 → 用 MITM proxy 拆开真货

（[00:25:15]–[00:28:17]）

- **他的判断**：**"大多数学生最后就是在用这些工具。我不觉得他们在课业里得到过任何把这层洋葱剥开的曝光。"**
- **200 行那一层的论证是门槛极低**：**"你可以通过基本上入门算法级别的理解，就定义出一个 agentic loop，它能做你会称之为 coding agent 的大部分事情"**；**"Stanford 有门课叫 106B，入门算法。你不需要比 106B 更多的东西就能造出这样的东西。"**
- **第三层是拦真请求**：**用 proxy 拦 Claude Code 的请求与响应（对象是"两天前刚出的模型"），在课上逐个展示 system prompt、plan prompt、compaction prompt。**

## ⚠️ 他对 system prompt 变薄的归因（本库认为这是他最有迁移价值的一条机制观察）

（[00:30:18]–[00:31:18]）

> **"曾经是 system prompt 一部分的东西——比如怎么用 git，或者怎么设置任务这类——已经不在 system prompt 里了。它现在实际上被期待更多地被捕捉在模型里，在模型权重自身里。"**

- **他把它推成一个选型问题**：**"这就提出了关于模型与 harness 的有趣问题……公司该投什么？你自己该投什么？"** ✅ **他的现状判断是未定**：**"我觉得作为一个社群，我们在两者之间来回摇摆得很厉害。"**
- **他对早期 Claude Code 流行的解释**：**"他们是最早真正倾向于'让更少的工具做更多事'的那批人之一——倾向 SQL、倾向 Bash、倾向那些像瑞士军刀一样强的东西。"**

## 他的 context engineering 框架：RAPID

（[00:32:18]–[00:34:18]）

- **行业现状断言**（本库认为可独立验证）：**"即使在我面试人的时候我也看到这个——业界里非常少的人会进展到超出单纯的 vanilla prompting。"**
- **框架本身**，他自己对照为**"功能上类似 Dex 的 RPI"**：**research → proposal（给出几种备选解法）→ plan（也就是 spec）→ implementation → 用测试收口**。
- ⚠️ **人留在哪一步他说得很明确**：**"这里我也把 human in the loop 请进来，让人当那个在一种方案和另一种方案之间做决定的人。"**
- **适用规模**：**"确实有一种做法能扩展到几百万行长的代码库。而它不是单纯的 vanilla prompt。"**

## ⚠️ 他对 skills 的区分（本库认为这条比"skills 会不会死"更耐放）

（[00:45:23]）**对照的是 [swyx 那条"Anthropic 有人想让 skills 死掉……它不是 AGI 本来应该长的样子"](latent-space-hosts.md)。**

> **"我们把 skill 形式化成了一种表示我们最佳实践的方式，然后把它暴露给 agent、给 code review 系统，让它按我们喜欢的方式去定义 API、按我们定义的方式去立服务级边界。这是一种表示组织级知识的替代方式，而不那么像那种'你不想每次都写 prompt 的任意事情'。"**

- **他的预测**：**"我感觉这个定位、这个用途可能会比那些随机流程活得更久。"**
- ✅ **本库的归纳**：⚠️⚠️ **他与 swyx 没有分歧——swyx 说该死的是"个人的一堆临时流程"，他说能活的是"组织的成文规范"。而两者在文件格式上完全一样，于是"skills 会不会死"在当前形态下无法被回答。**

## ⚠️ 他对企业瓶颈的诊断：方向与"上更多 agent"相反

（[01:11:35]）✅ **本库认为这是他最实用的一条反向建议。**

> **"当我跟某个规模的公司聊，真正卡住他们的其实更多是那些低层的 DevOps、CI/CD 的东西——他们的 merge queue 堵了，立起一个 app 要太久。再丢进一个 SRE bot 不会是问题的答案，因为有更系统性的东西他们需要先搞定。"**

- 🔗 **本库此前的同类诊断落在组织侧（[Tenex](../videos/20261021-latent-space-tenex-enterprise-agent-5-percent.md)）、数据侧（[Legora](../videos/20261102-latent-space-legora-cto-cant-see-the-traces-agent-as-api.md)）、权限侧（[Serval](../videos/20261029-no-priors-serval-boundary-is-the-product-least-privilege.md)）；✅ 这一条补的是"工程基建"一项。**

## ⚠️⚠️ 两条预测

1. **开源会变成 agent 运行的工厂**（[01:23:40]）：**"我有个信念——大多数开源仓库、如果不是全部，将来都会变成实质上由 agent 运行的 software factory。"** **例证是 Warp 把自己的开源终端当成 software factory 在跑。** ✅ **他对后果明确表示不知道**：**"这让这个代码库对安全问题更脆弱还是更不脆弱？这有点难说。"** 🔗 **这正好是 [Jay Parikh 那条"维护责任只会搬家、不会消失"](jay-parikh.md) 的供给侧另一半，而两期同日发布、方向一致。**
2. **很多公司会演化成 coding agent 公司**（[01:19:38]）：**"任何在 B2B 软件上有交互、在收集关于用户的某些东西或者某种产品洞察的公司……我觉得你也可以把这个环闭上。"** **点名 Linear、Amplitude，以及"你要真想拉伸一下，甚至可以让 Decagon 或者 Sierra 做类似的事"。** ✅ **可检验形态：这些公司是否开始发布"从洞察直接提 PR"的产品。**

## Monaco 一侧（他作为实践者，而非授课者）

- **公司**：**Series B、在 SF、"实质上是一个 all-in-one 的销售平台，全部由原生 agent 做那些人不喜欢做、而 agent 不介意做的事"**；**从 seed–Series A 创业公司切入，正往上走。**
  - ⚠️ **他对为什么不从企业市场切**：**"把人从 Salesforce 拉走，比在他们还只是用 Google 表格跟 pipeline 的时候遇见他们要难得多，而这样我们可以和他们一起长。"**
- **自建的 agent harness**：**"从 Codex、Claude 这类系统里拿了很多灵感"**，覆盖 TAM/ICP 打分、pipeline 演进、会前笔记与摘要；形态是长时程与短时程 agent 并存。
- ⚠️⚠️ **垂直 AI 的模型路线阶段论**（[00:53:24]）：**"你一开始用前沿模型当第三方服务来看看什么是可能的……然后到某个点，从成本角度事情会变得有意思，你开始想能不能在开放权重模型上做得更快。那时候 AI 那部分的目的很大程度上就是去 post-train 那些模型、为 RL 之类建环境。"** ✅ **他说自己正在这个阶段。** 🔗 **swyx 当场把它接到自己的 ["agent lab playbook"](../videos/20260710-latent-space-swyx-agent-labs.md) 上，✅ 本库记这是第一次有被访的实践者在自己的路线图上确认那个框架。**
- ⚠️ **build / buy 口径**（[01:01:32]）：**"你买是为了学，你建是为了留。"** **边界条件是"我们一般是在觉得外面没有成熟供给的时候才自建"。**
  - ⚠️⚠️ **而本库认为值得保存的是同一个决策的两次评估判据完全不同**：**第一次（一年多前）做了统计驱动的普查（"看我们的 PR，做了一组饼图——啰嗦程度与有用程度之间的权衡"），结论是没有一家越过"立刻就有用"的门槛；第二次他明确不再硬推，采用来自自发需求（"有机地，人们就开始说'嘿，Devin 挺好的，你能不能把我加进去？'"）。** ✅ **他把后者当成了更强的信号。**
  - **自建的两个系统**：**背景 agent 平台 Monocoder（建在 coder.com 的平台上）**；**一个 Slack bot（名字不可确证），"一部分是 AI 支持、一部分像客户成功、一部分像 QA 工程师"。**
  - ⚠️ **而这个 bot 带出一个本库此前没见过的工程问题**：**"我们得回答一些有意思的问题，关于它在跟销售人员说话和跟开发者说话时分别有什么人格。"**
- **enrichment 供应商**：**Parallel 与 Exa（他明确保持中立，"今天我站瑞士"）**；**自建"enriched 公司 / 账户 / 联系人的世界数据库"**；**他举的信号是职位变动（"销售 VP 换了工作，那是个好信号，因为他们在职业过渡中更可能购买"）。**

## ⚠️ 他对野心的门槛线

（[01:59:04]–[02:00:05]）**评价的是去年一个学生的 capstone（拍设计笔记本照片 → 生成 Vercel app，该学生现在在 Vercel 工作）**：

> **"恕我直言，在今天这个时代，拍张照片把它变成一个 app 不算多有野心。写一个浏览器才算。而实际上有很多像那样的项目。"**

- **他对课程标准变化的表述**：**"去年那样可以，但今年我们显然会要求更多。"** ⚠️ **对照很具体**：**"去年我还花时间讲过 k-shot prompting 当作其中一课。而我觉得你们现在根本不会去想那个了。"**

## ⚠️⚠️ 本库对他的两处保留

1. ⚠️ **全部课程设计内容只能记为设计意图，不是经检验的教学结果**：**该期录于第二次开课的第一周结束（"这是第一周的结束"），因此关于有效性的证据只有去年那版的印象性反馈。** ✅ **可检验形态：那些开源贡献作业最终有多少被合并、维护者的 review 负担实际有多大。**
2. ⚠️⚠️ **他对"学生会不会 cooked"的回答只有半句**：**swyx 把局限点得很清楚——"Stanford 的孩子会没事的。但美国其余那些人会怎么样？"**，**他答"对，那是个开放问题"**，而全期此后没有回到它。⚠️ **本库标注这改变了他那条开源 mentorship 处方的读法：它成立的前提（学校能谈到合作、赞助方给额外 credits、维护者愿意 review）全部与学校声誉相关。**
