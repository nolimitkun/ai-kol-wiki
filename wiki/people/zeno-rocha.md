## 他的核心论证（本库目前已收录的）

来源：[Latent Space × Zeno Rocha](../videos/20261110-latent-space-zeno-rocha-aeo-agent-picks-the-api.md)

### ⚠️⚠️ 一、"agent 不会去拖一个 JavaScript 控件"：本库第一条带前后对照的 AEO 改动

（[01:00:53]–[01:01:54]）⚠️ **发现是偶然的**：**他做竞品分析时问模型"用 Resend 发 120 万封邮件、再用几家竞品发，谁最便宜"，而模型把 Resend 算错了，还说"Resend 的定价非常不透明"。**

- ⚠️⚠️ **诊断**：**"问题是，agent 其实不会去拖一个 JavaScript 控件。"**（定价计算器是个 JS 控件）
- ✅ **处方是那一页的 markdown 版本**，而验证是**"几天之后我再问一遍，它就把数算对了"**。
- ✅ **而他对效用的区分本库认为比结论更该被引用**：**"也许它对分发没帮助，但它对准确性有帮助。"**
- ⚠️ **代价他也说了且没有解法**：**"这确实意味着你没有单一真相源……那完全是难受的。"**
- ⚠️⚠️ **一处度量副作用**：**那个 `.md` 页"被访问的量大得惊人"，但"走不了常规的分析工具"——"我们得去 Datadog 才搞得清"。** ✅ **本库判这意味着 agent 侧流量在大多数公司的默认分析口径里是看不见的。**

### ⚠️⚠️ 二、而他把自己真正被推荐的原因归给了模型侧的时间偏好

（[01:05:55]–[01:06:56]）⚠️⚠️ **本库判这是他这一期最该被完整引用的一段，因为它是被推荐方对自己成功原因的降权**：

> ⚠️⚠️ **"本来没有任何理由让任何模型推荐我们，因为我们在 SEO 上落后太多……我一直想弄清那到底是什么。而我完全能看出来，至少在 Opus 4.5 上，在技术选型和它们取数据的地方存在一个 recency bias。"**

- ✅ **他给的唯一建议不是技术动作**：**"尽可能让更多的人在更多的地方谈论这个产品。"**
- ⚠️ **他自己报了一次失败（负面结果，本库认为更难得）**：**那套对比页/404 的想法——"我不觉得那是个好主意，因为我们的竞品真的做了对比页，而它们比我们的更常被推荐。"**
- ⚠️ **工具侧的缺口他说得很准**：**"我希望那些工具能给我动作。问题在于它们给不出该做什么，因为它们自己也在试着搞清楚需要发生什么。"**（⚠️ **自述同时订了四家**）
- 🔗 ⚠️⚠️ **本库标注这直接回答了 [Supabase 那期](../videos/20261028-latent-space-supabase-declarative-schema-billions-of-databases.md) 悬着的一处**：**那一期主持把 Resend 当成"不靠时间先后、靠好实践"的反例提出来，而这一期就是那次采访——而他给的答案更接近 Supabase 的"时机"那一侧。** ✅ **本库因此把"做 markdown 版本/FAQ/llms.txt"记为降低被误述风险的卫生动作，而不是可预期提升推荐率的手段。**

### ⚠️⚠️ 三、80 多个 MCP 工具，以及远程 MCP 迫出的依赖链

（[00:37:28]–[00:45:35]）

- ⚠️ **产品哲学**：**"我希望我的产品是无形的（formless）。他们想拿这个产品做什么，都应该是可能的。所以我们一直是 API first。"** ⚠️ **他对风向的态度是"我不再去管什么在风口上、什么过时了"。**
- ⚠️⚠️ **工具数从发布时约 20 个到"80 多个"且还在加**，⚠️ **而他对经典顾虑给的是一句经验性否定**：**"早些时候这是个更大的顾虑——工具太多它们会乱。我现在不怎么看到这个问题了。"** ⚠️⚠️ **主持当场把这框成与 Cloudflare 两工具路线相反的反共识选择，而双方都没有给任何测量。本库判这是目前关于 MCP 工具数量最值得被实测的一处分歧。**
- ✅ **而真正的难点被他指到覆盖率的最后一成**：**"把 dashboard 能做的事覆盖到 100% 其实非常非常难，因为那时候你要做的是用量计费、团队邀请、账户开通、删除——这些该不该暴露成 API？"**
- ⚠️⚠️ **远程 MCP 的依赖链是本库目前关于"把一个产品做成 agent 可用"最具体的工程代价清单**：**远程 MCP → 必须先有 OAuth → 于是重做整个权限模型与 RBAC → 再接可观测性 → 最后才是分发（"去跟实验室谈、进官方商店和插件市场"）。** ✅ **本库判它说明"支持 agent"不是加一层适配器，而是先要求身份与授权模型达到能把权限委托给第三方的程度。**

### ⚠️⚠️ 四、他作为买方：因为没有官方 MCP 而换掉供应商

（[00:40:32]–[00:42:34]）✅ **本库判这是本库第一份这类一手买方证词，而分量来自他同时是卖方。**

- ⚠️⚠️ **"作为 B2B 软件的买方，如果我去 Claude 的 connectors 里，没看到那家公司带着官方 MCP 列在那儿——"** → **Plausible 的 MCP 是 Sentry 做的，"我不在乎那个不是官方的……我需要那个软件的所有者自己拥有这块集成"** → ✅ **"于是我做了决定：我们把 Plausible 去掉，这里就用 PostHog。"**
- ⚠️ **C 端同理（因为有 MCP 才用 Strava）**，**判据是"如果它不在那儿，我就不用"。**
- ✅ **本库判这给"官方 MCP"赋予了一个此前没有的性质：它不是一个集成特性，而是一项信任凭证——而凭证的发行者是模型厂商的目录，不是厂商自己。**
- ⚠️ **主持在同一处给了反面经验（"我特别努力去拿这些合作，上线之后什么都没发生"），本库并列不裁决。**

### ⚠️ 五、一处被明确悬置的张力：agent 自助注册 vs 滥用

（[01:08:57]）⚠️ **主持引的是 WorkOS 的 auth.md（"不需要账号就能做基本动作"），并自己指出"这显然很危险"。**

- ⚠️⚠️ **而他的回答是一次明确的未决**：**"这正是我在犹豫要不要做的事。我们需要一个 provisioning API 吗？我一直来回摇摆。"** ⚠️ **阻塞因素只有一个：**"我不知道是不是我们这个行业的缘故，但就是有很多滥用。"**
- ✅ **本库判这处悬置本身就值得保存**：⚠️⚠️ **"让 agent 自己注册服务"当下被广泛当作下一步的标准动作，而这里是一位本该实现它的人说"我还没决定"，理由不是技术也不是标准成熟度，而是滥用的基准率。**

### ⚠️ 六、两条关于 AI 与这个行业的具体观察

- ⚠️⚠️ **AI 自己弄坏了一个核心指标**（[00:13:06]–[00:14:07]）：**打开率依赖一个 1×1 的透明 GIF，而"如果他们在做摘要和那类事情，他们会在邮件落地之前先读它"** → **"打开率作为一个指标整体上已经不像以前那么可靠了。"**
- ✅ **而 DNS 那一处是两头都由同一波 AI 造成的**（[00:19:15]–[00:20:18]）：⚠️ **他这边是"我们在服务一个甚至不知道怎么排查问题的人群……他们就是不知道什么是 CNAME"（自述 DNS 是工单量第一），**✅ **而主持那边是"Claude Code 完全替我管我的 DNS 记录，我根本不用操心"。** ⚠️⚠️ **本库标注两者显然没有接上——他的工单量说明不会的人并没有都拿到那个工具。**

### ⚠️ 七、两条运营/定价细节

- ⚠️⚠️ **一条可直接搬用的支持制度**（[00:18:14]）：**"你只能用一个链接来回一个工单。所以你不能直接把答案给出去"**——**回一个工单要花约一个半小时，但"现在你把那个链接一遍一遍地发出去"。**
- ⚠️⚠️ **按联系人计费被 AI 原生客户打破**（[01:15:00]）：**"我们服务的那些 AI 公司增长太快了……所以按联系人定价的商业模式有点坏掉了。"** ✅ **本库判这是"席位制 vs 按量计费"那条线上一个此前没有的方向：不是买方嫌贵，而是计价单位本身的增速超出了它被设计的范围。**
