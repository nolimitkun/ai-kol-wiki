# James Sun

OpenAI，**computer use 的企业侧与安全控制**一侧。自述 **2026-01 入职**，最初做浏览器产品；入职前是创业者。

**本库收录他的理由**：⚠️ **他是本库第一个把 computer use 的企业控制面讲到产品形态层的一手当事人**——本库此前这一层只有 [Ari Weinstein 的 harness 与技术路线](ari-weinstein.md)（产品/工程侧）与防守方的反方口径（[Kurtz](george-kurtz.md)、[Knecht](dane-knecht.md)）。✅ **而他同一期里给了两条对自家不利的承认**，本库认为那两条比任何能力主张都更有价值。

## 核心观点（2026-10-26）

来源：[a16z × OpenAI / computer use 的 scaling moment](../videos/20261026-a16z-openai-computer-use-superhuman-webmcp.md)
⚠️ **厂商节目，主持方是写过这个赛道研究的投资机构，全部陈述为自述且本期一处未被独立追问。**

### ⚠️⚠️ 两条 against-interest 的承认

1. **Atlas 里的 agentic 体验"没什么人用"**（[00:41:27]）：⚠️⚠️ **"在那个产品里，agentic 的体验因为几个原因其实并不是一个大的卖点。没有很多人用它，部分原因是我觉得人们大体上把它当成一个普通浏览器。"** **转折是把 browser use 并进"所有已经有 agentic 用量的现有产品"，之后"我们看到的是 YC 级别的周环比增长"**（⚠️ 无数字）。⚠️ **产品名本库不写定：字幕作 "Alice"，疑为 Atlas，视频简介未确认。**
2. **自家的凭证与会话碎片化**（[00:38:24]–[00:39:24]）：⚠️⚠️ **Chrome 扩展用 Chrome 的密码管理器、桌面 app 的内置浏览器另一套 cookie 与密码、云上那台电脑又另一套**——**"对普通消费者来说这挺迷惑的。"** ✅ **他自己给的性质判断**：**"这有点像个悖论，因为 computer use 其实是最容易理解的 AI 产品——它就是一个 AI 在用你的电脑。但因为要管理的不同状态，实现细节有时会渗出来，于是它就变得不好 grok 了。"**

### ⚠️⚠️ 企业控制面：从"模型足够对齐"退到"确定性控制"

（[00:17:14]–[00:19:16]）✅ **本库认为他这段论证的结构值得单记：他不是用"模型更对齐"去说服企业，而是承认那说服不了。**

> **"我觉得真正让企业有安全感的是确定性的控制——即使我们的模型是史上最对齐的……但当企业管理员可以直接说'某些任务或某些数据源就是太敏感、不能用'的时候，就是会有一种安全感。"**

- **已发布的两件（⚠️ 发布口径自述）**：**① 确定性沙箱**（能用哪些应用/网站、不能用哪些）；**② 人在环的档位**（下载与上传要人批准、首次访问新网站要人批准），✅ **"这些都是旋钮，企业可以自己调"**。
- **第三件是模型而非规则**（[00:10:08]–[00:11:08]）：⚠️⚠️ **Guardian**——**"app 里的自动批准，一个很聪明的模型，在看 computer use agent 采取的每一个动作，来判断它是否安全、是否和书面意图（written intent）对齐。"** ✅ **本库标注这是把对齐从训练期挪到运行期**；⚠️ **而 [Kurtz](george-kurtz.md) 与 [Knecht](dane-knecht.md) 都主张防守方不能依赖模型层——这处张力两边无交流。**
- ⚠️ **消费与企业的分叉**：**"消费者可能就是'我想让它什么都干，别来问我批准'；而企业可以决定哪一类动作才放行。"**
- ⚠️ **第二层是展示 eval**（内部与第三方对照），**无任何具体 eval 名或数字。**

### ⚠️⚠️ 开放网络：广告收入冲突与 WebMCP

（[00:11:08]–[00:13:13]）✅ **本库第一条由 agent 厂商自己承认发布方商业模式冲突的材料。**

- **阵营一（商业模式不相容）**：⚠️⚠️ **"广告主、发布方的商业模式整个建立在广告上。如果 agent 替他们用网站，那收入从哪来？而在大多数地方，agent 的一次广告展示并不真的算进真实收入。"** ⚠️ **他没有给任何解法**（"我们一直在和合作团队一起处理"）。
- **阵营二（想拥抱的）**：⚠️ **他点名 WebMCP 并说"我们在 app 的浏览器里加了支持"**。✅ **他要的形态是分工而非替代**（agent 做乏味的部分 → 人完成交易与输入信用卡 → 再交回 agent），**定位是"你和网站的接口仍然是网站本身，而不是一个 API，但人是和 agent 一起在用它"**。
- ⚠️ **本库标注这与 [Dane Knecht](dane-knecht.md) 构成一处清晰的立场对立**：**Knecht（发布方一侧）主张人与 agent 各自接住、按内容站自己的 CPM 定价；他（agent 一侧）主张同一个界面上协作。两边都在自己的利益方向上。**

### ⚠️ 用例清单与一条倒转

- **他把企业用例分两类**（[00:20:16]–[00:23:17]，⚠️ 无客户名与效果数字）：**一、乏味工作流**——全部 system of record（ERP/CRM）、**采购**（大表 → ops 录入采购软件 → 逐个联系供应商）、**财务月末对账**（⚠️⚠️ **前提是"很多这类财务软件没有 API"**）、销售 prospecting、市场调研；**二、更有野心的创造性工作**——电路设计、建筑、硬件工程、游戏设计，⚠️ **他自己说企业现在还较少想到这些，即这一类没有采用证据。**
- ⚠️⚠️ **一条顺带说出、本库认为很要紧的倒转**（[00:04:03]）：**企业里的遗留软件"已经被用了 15、20 年"、"没有任何 MCP 工具"，而"很多时候那些东西对一个普通人来说其实挺难用的……你甚至不知道怎么操作那些关键功能"**，**所以"有公司在造 skills，教模型更好地使用它们"**。✅ **本库的标注：卖点因此不只是"替人做"，而是"agent 比在职员工更会用公司自己的老系统"——这把 ROI 的来源从省人力挪到了消除培训与操作知识的损耗，⚠️ 而本期没有给任何一例数据。**

### ⚠️ 对"UI 会消失"的反对，以及"为一个人设计的软件"

（[00:27:19]–[00:29:19]）⚠️ **"如果互联网变成只是一堆 agent 互相说话、人不再用任何东西了，我会非常难过。"** 理由是**手艺**——"匠人式软件就是用起来感觉好，因为设计它的人真的理解客户想要的体验"。

- **他的例子**：妻子玩一个连五颗棋子就赢的棋类游戏（⚠️ 字幕作 "O Mac"，按 Omok / 五子棋理解）在线被打得很惨，他给她做了个**按不同开局练的战术训练器**，**"我知道她喜欢用某种方式做"**。
- ⚠️⚠️ **他的推论**：**"如果任何人都能造任何东西，而且能在很短时间里为很小众的用例造出这种精心打磨的软件……我觉得那是一个很美的世界。"** ✅ **分工他说清了**：训练后的错题总结可以交给 agent，**但"她真的在和 AI 对练、在变强"这件事"是人必须自己做的"**。
- ✅ **收尾的一句**：⚠️ **"便宜软件带来的压力会让软件不得不变得更好。"**

### ⚠️ 厂商侧对"扩散缺口"的四步拆分

（[00:35:21]–[00:37:23]）⚠️ **这是被问"创业公司还有没有护城河"时的回答，立场上有动机往"有"的方向说：**

- ⚠️ **一条关于自家人力的承认**：**"即使我们现在挺大了，有几千人，我们内部仍然觉得被摊得很薄……相对于所有这些问题，团队并不大。"**
- ⚠️⚠️ **四步缺口**：**"对普通的美国人、普通的中小企业主、甚至普通的企业来说——连搞清楚这些工具能干什么是第一；把工具以合理的方式连起来是第二；部署是第三；服务是第四。"** ✅ **本库标注这是第一次由模型厂商把扩散缺口拆成四步**，⚠️ **但四步全落在集成方，这正好是一个对厂商有利的分工结论（模型归我、集成归你），本库记为立场。**
- ⚠️ **他给的那个端到端用例**：餐饮集团**拍后厨储藏间照片 → 按次日客流预测判断缺什么 → 用 computer use 去采购软件下单 → 再进 ERP 调整排班**。⚠️ **无公司名、无规模、无效果；采购软件名本库无法写定（字幕作 "Shopee"）。**
- ⚠️ **他说今天真正存在的护城河是两个词**——字幕作 "speed and pay"，**疑为 "speed and taste"，本库不写定。**

### 另记

- **"我现在什么都先问能不能让 agent 做"**（[00:14:13]）：他把它变成一条强制练习；⚠️ **例外只有"给人发消息时我想让它感觉是我发的"与"特别敏感的事"。**
- ⚠️ **"computer use 不是一个你会单独拿起来用的东西"**（[00:16:13]）：**"它其实是模型为了做成任何事而拥有的那个通用 API。越复杂的任务，越可能在某个环节用到 computer use。"**
- **主动性的两个一手用例**（[00:05:04]–[00:08:07]）：**外部日历邀请不进公司日历导致漏会，dots 主动标出并问要不要替他在 Gmail 里接受**；**Slack** 从"每小时去捞一次"（⚠️ **"我最后把很多通知都屏蔽了，因为有时有用有时没用"**）换成给高层目标（"汇报链上任何人说了什么就标给我"）。✅ **以及一条用云电脑的组合流程**：用户报 bug 带 Sentry 日志 → 驱动本地浏览器 + 云电脑登录 Sentry、拉日志、分析、给反馈。
- ⚠️ **"共享智能层" vs 碎片化**（[00:31:19]–[00:32:20]）：**"如果每个网站都有自己的 agent、而它不跟你的 agent 说话，那会是一个非常碎片化的世界。"** ⚠️ **本库标注：这条主张要求一个跨站点、以用户 agent 为中心的上下文层，而谁持有那一层正是上面那处立场对立的核心——节目没有点出。**
- ⚠️ **下一个拐点他指向云与手机**：**"桌面仍然非常是高级用户的东西……大多数消费者在手机上"**，目标是**"给每一个只用手机过日子的人一台他们甚至不需要理解怎么用的强大电脑"**、**"带到十亿用户"**。
