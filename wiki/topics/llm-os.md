# LLM OS 与新计算范式

> LLM 不是聊天机器人，而是新兴操作系统的内核进程。

## 各家观点

### Andrej Karpathy（美，2023-11）
提出 LLM OS 框架：LLM 作为 kernel process 协调内存与计算工具——context window ≈ RAM（有限的宝贵工作记忆），互联网/本地文件 ≈ 磁盘（经浏览/RAG 访问），计算器/Python ≈ 外设；未来还有多线程、投机执行、用户态/内核态的类比。生态上闭源（GPT/Claude/Gemini）vs 开源（Llama 系）对应 Windows/macOS vs Linux。（[Intro to LLMs](../videos/20231123-karpathy-intro-to-llms.md) 00:42:28–00:45:30）

### Dan Biderman（美，Engram CEO，2026-07）：RAM 不够——记忆、context rot 与"训进权重"
来源：[Latent Space 访谈](../videos/20260713-latent-space-dan-biderman.md)

接续 Karpathy"context window ≈ RAM"的框架，给出 2026 年的工程续集——**光把 RAM 做大（长上下文）不够**：
- **"记忆 / 持续学习本质是长上下文问题的伪装"**；即便 10M 上下文，仍有 (1) **context rot**（喂进越多 token 越困惑）与 (2) 内存/成本爆炸两大限制。**compaction（模型自管理上下文）在改进但按定义有损**、当前偏非黑即白，长会话深处会健忘（00:18:11–00:21:13）。
- **KV cache 的内存怪兽**：Llama 70B 读一篇几十 KB 文章，"脑状态"就占约 80GB HBM，与整个模型参数（约 140GB）同量级——RAM 极度低效（00:22:16–00:23:17）。
- Engram 的下注是把语料用梯度下降**训进权重**（"cartridges"，约 1000× 压缩），与文本表示（RAG/wiki，即 Karpathy 的"磁盘"）互补；长期"每人一份权重、跑在个人设备上"（00:09:04–00:11:05、00:26:19–00:28:24）。这把 LLM OS 的"内存管理"从"如何调度 RAM/磁盘"推进到"哪些知识该内化进内核本身"。

### Peter Steinberger（美/奥，OpenClaw 作者，2026-02）：个人 agent 就是下一个 OS

来源：[OpenClaw 访谈](../videos/20260212-lex-openclaw-steinberger.md)

- **"这是 puck 要去的方向——个人 agent 会越来越成为你的操作系统"**：coding agent 与生活 agent 终将融合；当前 chat 界面只是过渡形态，"就像电视刚发明时人们在电视上播广播节目"（01:48:24–01:51:34）。
- 从实践侧填充 LLM OS 的多个抽象层：**记忆**用 Markdown 文件 + 向量库（自评"level 2–3"，终极 boss 是 continuous RL）；**外设/驱动**用 CLI + skills 而非 MCP（CLI 可组合、可 `jq` 过滤、零 context 污染——"每个 MCP 做成 CLI 都会更好"）；**进程调度**有 heartbeat（定时"surprise me" prompt 让 agent 主动行动，被嘲"不就是 cron 吗"，"Dropbox 不就是 FTP 吗"）（00:19:29–00:20:32、02:38:59–02:42:08、02:36:56–02:38:59）。
- **自修改软件已是现实**：agent 完全"自知"（源码、harness、文档、所跑模型），用户 prompt 即可让 agent 修改自身软件（00:22:36–00:24:40）。
- 与 [Karpathy 的 LLM OS 框架](../videos/20231123-karpathy-intro-to-llms.md) 对照：Karpathy 从内核抽象出发，Steinberger 从产品/社区侧把同一形态"prompt 进存在"；与[罗福莉](../people/luo-fuli.md)"智能体框架 = 人与模型的中间层"是同一物的作者视角与研究者视角。

## 中方视角：模型即操作系统

### 广密（硅谷投资视角，2026-04）

来源：[广密·全球大模型季报第 9 集](../videos/20260415-zhang-xiaojun-guangmi-llm-quarterly-9.md)

- **模型 = 新一代操作系统 = global GDP 的 OS**：最领先的三五家模型将成为世界最重要的技术基础设施（生活问它、工作自动化靠它、科研支持也是它），重要性超过今天的 Google；每家估值 10 万亿美金（01:04:51–01:06:53、01:13:05）。
- **OS 的定义"支持应用的无限扩展"**——这里的"应用"就是 agent，会形成像 Android/Windows 一样的新生态（01:05:52）。这是对 Karpathy"LLM 是新 OS 内核"从商业/投资侧的放大：不只内核，而是承载全球 GDP 的操作系统。

### 罗福莉（中方 research lead，2026-04）：Agent 框架是"人与模型之间的中间层"

来源：[罗福莉访谈](../videos/20260424-zhang-xiaojun-luo-fuli-agent-paradigm.md)

- **智能体框架（如 OpenClaw）= 人与模型之间的"中间层"**：同时定义"人如何交互"和"如何与模型沟通"两层，可做得很厚重，而前端 UI 是"最薄且不关键的一层"（00:20:16–00:21:16）。这为 LLM OS 补上"内核之上的调度/编排层"的中方一手描述。
- **框架能弥补模型短板**：一套足够好的 agent 框架 + 中层模型，就能在 85% 场景达到顶尖模型水平（3B 端侧模型接入也能干"小模型不该能干"的事）（00:15:13–00:16:13）——OS 的"驱动/兼容层"让弱硬件也可用，是同一隐喻。
- **模型与框架必须协同进化**（自学习）；开源框架 + 群体智能让这一层迭代极快。呼应 Dan Biderman"哪些知识该内化进内核"的问题：罗关注的是"哪些能力该由框架补、哪些该训进模型"。

### Gavriel Cohen（NanoClaw 作者，2026-06）：第二大脑与 LLM Wiki 优于检索
来源：[NanoClaw 访谈](../videos/20260629-latent-space-nanoclaw.md)
- 继 OpenClaw 之后又一个"个人 agent 即 OS"的一线实践；主张**"claw 类 agent 的杀手级用例是第二大脑"**——不断喂信息、让 agent 建 LLM Wiki/知识图谱，而非要现成产出（00:05:04–00:06:05）。
- **LLM Wiki 优于检索/RAG**（对 Karpathy"磁盘 ≈ RAG"框架的一个反转）：问"这周最该关注什么"没有 embedding/关键词能答，但有好的 LLM Wiki（项目/时间线/本周通话 log）就能跨文件收集给出——所以他个人直接把 agent 指向 Karpathy 的 LLM Wiki 帖照做；已知痛点是会造重复文件、需背景进程查重（**与本库 Lint 巡检同构**）（00:11:07–00:13:09）。**本条本身是本库范式的元证据**：新加坡外长用 NanoClaw + Karpathy LLM Wiki + Nemon 记忆系统搭第二大脑。

### Akshat Bubna（Modal CTO，2026-07）："LLM 内核"之辩与 agent 自造基础设施
来源：[Modal 访谈](../videos/20260708-latent-space-modal-agent-infra.md)
- swyx 抛出非共识："也许 AIOS/LLM OS 的内核真就是个 LLM（软权限就够）"；Akshat 明确保留——sandbox 层要**硬边界**（详见 [LLM 安全](llm-security.md)）（00:43:32–00:44:34）。这是对 Karpathy"LLM 是内核进程"的一个边界追问：内核可以是 LLM，但**权限/隔离不能只靠 LLM**。
- **agent 自供给基础设施**：self-provisioning runtime 让 agent 能 spin up 别的 agent、起自己的基础设施；SDK 从"开发者体验"转向"agent 体验"——OS 的"系统调用"正在为 agent 而非人重新设计（00:04:06–00:07:10、00:37:29）。

### ⚠️ Akshay Nathan（OpenAI，2026-07）：LLM OS 被逐项做成了产品，但他不用这个词
来源：[OpenAI 把 ChatGPT 做成"万物应用"](../videos/20260728-latent-space-akshay-nathan-chatgpt-work.md)

这是本页迄今**与 Karpathy 清单对应最整齐的一份产品实证**，且它来自 OpenAI 产品侧而非研究侧：

- **持久计算机环境 + 文件系统**：ChatGPT Work 在 web 和 mobile 上给你一个持久环境，**文件跨会话保留**；加上**定时任务**与**跨时间引用**（[00:46:28]–[00:47:28]）。
- **可扩展的工具层**：**plugins 在 ChatGPT、ChatGPT Work 与云端是统一原语**（[00:14:07]）；目标是"**你来到这个产品、开一个会话就能做任何事，不用点按钮跳去别处**"（[00:47:28]–[00:48:28]）。
- **记忆作为系统状态**：ChatGPT Work / 云端**默认继承 ChatGPT 记忆并可写回**，同属 memory V3；**Chronicle**（从你如何使用计算机中学习）是一个新的记忆输入源，目前实验性、默认关闭（[00:56:33]、[00:59:36]–[01:00:37]）。
- **模型做调度**：进 chat 模式还是 work 模式**由模型决定**（[00:15:09]）——对应 Karpathy"LLM 是内核进程"里最核心的那条，但落在**模式选择**而非资源调度。
- ⚠️ **但他自己的参照系不是操作系统，是 [OpenClaw](../people/peter-steinberger.md)**：他讲了自己的 OpenClaw 时刻，承认灵感来源，并指出"**原语是一样的**"（定时任务、文件系统、跨时间引用）。**同时他明确不认为 ChatGPT Work 会取代 OpenClaw**——"那个团队做出来的这种了不起的开源技术永远有其需求"（[00:47:28]）。是 swyx 在本期说出了"**个人 OS**"这个词。
- **harness 层的一条演化观察**（对本页有直接含义）：Codex 的 harness 实际上取代了 ChatGPT 的 harness，理由是"**给 agent 一个无限灵活的环境——一台计算机——它能做到非常强大的事**"（[00:16:10]）。**"计算机环境"作为 agent 的通用抽象胜过"对话"作为通用抽象**，这正是 LLM OS 命题的一次经验性支持。
- ⚠️ **一处 swyx 追问后未被正面回答的技术缺口**：只靠 MCP / CLI / API 即时拉数据是否够，还是需要**数据仓库/缓存/语义层**？Akshay 的回答是"取决于访问模式"、且多数用例本来就不需要即时返回，**没有确认也没有否认内部是否存在这一层**（[00:50:29]–[00:51:29]）。本库不做推断。
- **权限层问题**（新角度，另见 [LLM 安全](llm-security.md)）：多人共享 artifact 时，**人本身充当了权限层**；一旦被 agent 取代就没有天然屏障，且**当事人无从知道自己不知道什么**（[00:25:12]）。

## ⚠️ 界面世界模型与"完全神经的操作系统"（Runway，2026-09-25）

来源：[Latent Space：Runway 的世界模型、机器人与神经操作系统](../videos/20260925-latent-space-runway-world-models.md)

⚠️ **本页此前的 LLM OS 材料全部来自 [Karpathy 的框架](../people/andrej-karpathy.md)（LLM 作内核、上下文作内存、工具作外设）。这是本库第一份把"界面本身"也纳入可学习部分的材料**，而且它来自视频模型一侧。

### 界面世界模型是什么

（[00:44:28]–[00:45:29]）**把世界模型当作软件的通用界面**——它**直接渲染界面的像素**，训练目标是"预测点击或其他交互之后会发生什么"。

- **没有 HTML、CSS、React**；输入是**点击、拖拽、滚动**；**同时生成音频**。
- **界面的行为写在 prompt 里而不是标记语言里**："如果我按这个按钮，我期望发生这个。"

> ⚠️ **"为什么要生成那段生成像素的代码？直接生成像素就好了。这是端到端哲学应用到前端。"**（[00:46:30]）

- **对照实验**（[00:47:32]）：同样的界面去 prompt Claude（给 Figma 参考图 + 要求某个交互），结论是**除了更慢，某些交互靠纯 LLM 很难捕捉**。
- **副产品：个性化**（[00:48:34]）——按访问者换 prompt，比如为无障碍需求把字号调大。
- **他自己给的限制**（[00:48:34]–[00:50:35]）：**算力需求远高于渲染 HTML**；有环境动效时必须一直跑。优先级判断是"**先找到几个明显比传统界面更有说服力的交互场景，之后服务成本变便宜只是时间问题**"。

### ⚠️ 终局：神经操作系统，以及"application 这个抽象可能不再需要"

（[00:51:36]–[00:53:39]）他明确引 **Karpathy 很久以前写过这个**，然后给出自己的论证：

> **"今天你和一个 LLM 交互，这个 LLM 什么都能跟你聊、对话可以往任何方向去，它非常通用、能解决各种任务——但你是通过一个非常僵硬的界面在和它交互。所以在我看来，界面本身变得可学习只是时间问题。"**

⚠️ **更激进的一层，本页此前没有过**：

> **"application 这个概念，来自'你需要各自独立的代码库来驱动每一个工具、每一个应用'这个前提。"**

如果界面由视频模型即时生成，**"应用"这个抽象可能不再需要**——需要发明新的软件抽象。

⚠️ **他反复强调世界模型有两个客户**（[00:53:39]–[00:54:40]）：**给人用**和**给 agent 用**。界面世界模型对 agent 这一侧是：**训练 computer-use agent 的合成数据生成器**，以及**可做在线 RL 的活环境**。

## ⚠️ 另一条路：不生成文本，而是选选项——决策引擎与概率式编程的复活（a16z，2026-09-26）

来源：[a16z：为什么下一批突破可能来自实验室之外](../videos/20260926-a16z-outside-the-labs-security-regulation.md)

⚠️ **这一节与上面那节是同一问题（LLM 怎么接进软件）的两个相反答案**：Runway 让软件变成模型的输出；这一节让模型缩成软件里的一个算子。

### Casado 的解释：历史包袱在于"它来自聊天"

（[00:48:24]–[00:49:25]）LLM 生来是 text-in / text-out，**为了和人沟通**；而我们花了好几年**试图把这个吐文本的东西塞进传统程序**——"**传统程序并不讲文本**"，于是变成在 prompt 里塞 schema、模型还经常忽略它，"**一直特别糙**"。

新做法：**读文本、保留全部理解能力，但不生成文本；给它一组选项，它选最好的那个。**"**我们可以做得极快、极便宜，而且因为可以专门为此训练，准确率也高得多。**"他称这是"**自 ChatGPT 以来最快的 AI 模型采用，因为我们都为它准备好了**"。

### ⚠️ Sinofsky 的两层加码

（[00:49:25]–[00:51:27]）

1. **交互效率的断言**："**从来没有任何用户研究表明，用完整自然语言和计算机交互是高效的。**"检验很朴素——**会议里能问出好问题的人不到一半**；而且"**你还得付钱看着七段文字一段段吐出来，最后它再道歉**"。
2. ⚠️ **概率式编程的复活（本库第一条这方向的论证）**：这类模型的输出**天生是为概率式编程设计的**——不是"这是不是客服问题"，而是"**这有 80% 是客服问题**"。他指出**计算机科学有约 50 年关于"概率式 if 语句"的研究**：1970 年代之前的编程大多是模拟（"发射导弹打中目标，但有风，而风不是常量"），这门学问在 1980 年代被会计式编程取代而死掉。

   > **"所以计算机科学里最酷的位置，将会是概率式编程。"**

### ⚠️ "创新中心已经移动了"

（[00:52:27]–[00:54:28]）Casado 对"为什么不是实验室做出这个"的解释：

> **"这不算指控，而是对他们思维方式的一种映照：他们在试图创造存在物（beings），而存在物会说话。如果你想创造神，神是用自然语言说话的。而这件事其实是关于给传统软件用的东西，那不是他们一直在走的方向。"**

Sinofsky 给的平台层一般规律：**一旦你成为平台，无论加多少人都会被"让它跑着 + 兼容性"淹没**，于是外部开始出创新（Apple 社区管这叫 sherlocking）。

> **"所以我认为这是一个信号：人们已经搞明白了，有创新可做——是对着模型做，但在模型之外。"**

## 开放问题

- 通用 System 2（慢思考换准确率）如何实现——Karpathy 2023 年认为尚无模型具备。

## ⚠️ 可塑操作系统：Linux 的历史性翻转（DHH，2026-08-26）
来源：[Lex #501 / DHH](../videos/20260826-lex-dhh-agentic-programming-omarchy.md)

本页此前的 LLM OS 讨论集中在**模型/agent 作为新的 OS 抽象**（Karpathy 的内核类比、Steinberger 的个人 agent 即 OS、Runway 的神经操作系统）。DHH 这期是本页第一份**从真实操作系统一侧**给出的论证：不是"OS 被模型取代"，而是"**OS 要变成可被 agent 改写的东西**"。

### 翻转本身

- **"agent 爱 Unix 哲学"**（[01:40:42]–[01:41:45]）：三大桌面系统里，没有哪个像 Linux 一样"**一切都是配置文件或 CLI 工具**"。⚠️ 他的原话结构是："**而这五分钟前还是 Linux 的最大缺点**"——人们不喜欢 Linux 正是因为它全是配置文件和命令行。
- **Mac 的反例**（[01:42:48]）：Raycast 这类工具的配置只能点 GUI 再导出文件，**整台机器的配置无法自动化**；Mac 默认快捷键"必须像山顶洞人一样用鼠标点"。
- **诊断能力反转**（[02:24:00]）：Linux 那些"对人毫无意义的晦涩报错"恰好是 agent 的最佳输入——它在 4000 万行 Linux 代码上预训练过，能直接定位。⚠️ 他的一手说法：**今年以来自己机器上没有一个问题是 agent 诊断不了的**，而一年半前还在翻论坛。
- **做成产品特性**（[02:25:01]）：Omarchy Quattro 内建 **crash watcher**——任何应用崩溃就弹窗问要不要让 AI 诊断；他描述的典型路径是 agent 翻 systemd 日志 → 拉崩溃应用的源码 → 定位到某个 Rust 文件某一行的 unwrap → 问你要不要带全部细节提 bug 报告。

### 结论与判据

- **"能 vibe code 任何应用的时候，你也应该能 vibe code 你的操作系统"**（[01:58:13]）——可改外观、行为、面板，而这**要求 Linux**，另两个系统给不了。
- 他认为 Linux 接管桌面"不仅可见，而且是**最可能的结局**"，理由不是免费或自由，而是**可塑性**（[03:38:37]）。
- ⚠️ **产品方法论上的一条反直觉**（[03:41:44]–[03:58:14]）：他刻意**不做"便宜的 Windows/Mac 仿制品"**（他认为那是 Ubuntu 的路线，"而人们并不在乎熟悉，他们只要更好的东西"）。证据是他自己的 A/B：Omakub（仿传统桌面）只聚起几千人；Omarchy（平铺窗口、完全不同）立刻获得远超前者的牵引力。
- **可塑性的即时验证**（[00:48:26]）：Quattro 发布三天内插件市场有 **330 个插件**，仅"换个日历"一项就有约 17 个实现——因为系统自带一套 skills，告诉任何 agent 该怎么给这个 OS 写扩展。
- **下一步**（[04:20:49]）：**Omarchy mobile**——fork Android（类似 GrapheneOS 路线），他承认 tap-to-pay、相机等限制但认为可解。
- ⚠️ 与本页 Runway 那条的分野值得单记：Runway 设想的是**界面由模型逐帧生成**（"application 这个抽象可能不再需要"）；DHH 设想的是**传统 OS 保留，但每一层都能被 agent 改写**。两条路线都自称是 agent 时代的 OS 终局，前提完全不同。

### 个人 agent 这条线：他试过，然后放下了

- 2026-02 他搭 OpenClaw（bot 名 KEF），做过一个标志性实验（[04:13:40]–[04:15:44]）：让它**纯靠 web 界面**注册 Fizzy → 发现需要邮箱 → 被告知"你自己去注册一个" → 真注册了邮箱 → 回去完成注册 → 收 Basecamp 邀请邮件 → 点链接进去 → 在 AI 房间自我介绍。全程约 **12 分钟**。
- 动机是**嫌 MCP 笨重**（协议不是为"让 agent 操作 web 系统"设计的）；结论是**当时还不够快、token 效率太低**，所以仍需要 CLI 与 MCP（[04:14:43]–[04:16:45]）。⚠️ 与 [Steinberger 的"MCP 已死、CLI + skills 万岁"](../videos/20260212-lex-openclaw-steinberger.md)是**从不同理由走到相近结论**。
- 他之后没继续用个人 agent：**Claude 的手机 app 能直接接上终端里的 Claude Code 会话**，省去搭 Telegram 那套（[04:17:46]）；加上家庭共识——"我太太说，家里不装机器人"。
- ⚠️ 两则他转述的"已经住在那个未来里"的轶事（未核实）（[04:18:46]–[04:19:48]）：有人把 agent 接上健康数据和 Tesla，**agent 因为他喝水不够让车自己改道去了杂货店**；Tobi 的 agent 有零花钱，会替他挑衣服直接送到门口。

## ⚠️ 消费侧的界面之争：iMessage 的"特权位置"、语音、与随身硬件（a16z，2026-09-29）

来源：[a16z / Assistant Benchmark](../videos/20260929-a16z-personal-agents-assistant-bench.md)

⚠️ **本页此前讨论的"操作系统"都在模型与软件栈这一层。这一节是终端表面那一层**——即**个人 agent 到底住在哪儿**。⚠️ **页内产品事实为录制当周状态，本库未核实，极可能已过时。**

- **实际存在的表面**（[00:12:08]–[00:14:09]）：**iMessage、独立应用**为两种主流，另见 **iPhone 小组件**方向。
- ⚠️ **[Anish Acharya](../people/a16z.md) 的分化假设**（[00:13:09]）：可能**按世代分化**（Z 世代更愿直接发短信，千禧与 X 世代更愿用 app 界面），**可能还按性别分化**（他拿自己与太太对比：她偏视觉界面，他偏功能）。⚠️ **他自己限定了这是一个 generalization，本页照录这个限定。**
- ⚠️ **"特权位置"这个说法值得记**（[00:13:09]）：**"iMessage 这个空间更珍贵……它在我手机上处在一个特权位置，而 app 网格上的图标没有。"** ⚠️ **但他立刻给了失效条件**：**"当然，如果每隔一个会话就是一个 agent，这件事就会变。"** 本页记为**一条自带有效期的护城河**。
- **语音被两人同时列为当周最强体验**（[00:17:09]–[00:19:10]）：全双工、**能看到你所有会话**（可以问"我开过的那三个项目现在到哪了"）。配套的界面原则是 ⚠️ **"助理最有用的时候，是你最被占住的时候"**。
- **硬件**（[00:14:09]–[00:17:09]）：
  - ⚠️ **Acharya 的警告**：**"每一个在做硬件的人都觉得自己那块硬件是终极答案——吊坠是终极、表带是终极。我不认为那是对的。"** 他的判断是**像首饰一样因人而异**，但"**有一个随身的、环境式的东西去捕捉一天里全部的上下文、请求、承诺，这件事是有价值的**"；他同时提醒**隐私预期还得整个社会一起摸出来**。
  - ⚠️ **嘉宾的 hot take**（[00:15:09]）：**Muse charm 与其说是要赢硬件，不如说是 Meta 在真实世界里采数据**。他对"眼镜不是已经拿到了吗"的区分是：⚠️ **"吊坠是环境式的 24/7 陪伴，眼镜更偏行动导向。"**
  - ⚠️ **Acharya 的沉睡黑马判断**（[00:16:09]）：**纯音频眼镜可能是 sleeper hit**，理由是社交尴尬——**"有一部分人喜欢脸上戴摄像头，但另一些人意识到它会让别人不舒服，他们想要连接但不要摄像头带来的社交别扭。"**
- ⚠️ **本页认为最该保留的一条机制解释（麦克风隐喻）**（[00:22:14]）：**"消息这件事就像是有人拿着麦克风，而把麦克风交给 agent 让人不舒服；换成 Discord 或者传统网络论坛，agent 可以发一个帖子，你可以选择接或不接——那就没那么侵入。"** ⚠️ **这条解释了一个本页此前只记录为现象的东西：为什么群聊里的 agent 普遍失败，而异步、可忽略的表面更容易接纳 agent。**

## ⚠️ 把 harness 拆成脑 / 手 / 界面，以及"可变软件"（Thariq Shihipar / Anthropic，2026-09-29）

来源：[Latent Space / Anthropic](../videos/20260929-latent-space-thariq-claude-code-mods-pacing.md)

⚠️ **本页此前的"操作系统"讨论集中在模型层与推理层。这一节是 agent harness 这一层的架构主张**，而且来自 harness 的作者一侧。

### ⚠️ 拆包：现在三件事挤在一个地方

（[00:11:04]–[00:12:05]）现状是：你给**本地**的 Claude 发消息，它在本地起 session 并执行——⚠️ **"现在这些全都发生在同一个地方。"** 他说的方向是拆成三层：

| 层 | 是什么 | 在哪儿 |
|---|---|---|
| **界面** | artifact（带数据库、托管在某处） | 哪儿都行 |
| **脑 / 推理** | 智能 | ⚠️ **云上——"你不用担心关不关自己的电脑"** |
| **手（hands）** | 实际干活的地方 | ⚠️ **本地、远端沙箱，或任何需要工作发生的地方** |

- **路径**：换成**你给一个跑在云上的 Claude 发消息，由它去起本地或云端 session**；他说 **Claude Tag 大致就这么工作**，并且**以后会加 local hands**——⚠️ **"那个 agent 在你电脑在线时访问你电脑干活的能力。"**
- ⚠️ **主持人给的好记说法**（[00:51:34]）：**"这其实是反向的 remote control——remote 是你把活交给云，而这里是云把活交给本地。"**

### ⚠️ artifact 作为 harness 的界面

- **能力**（[00:08:02]）：artifacts **带一个数据库**，所以**能存写持久数据、能回馈给 Claude**；⚠️ **多个 Claude 可通过 artifact MCP 访问同一份数据，而那个 artifact 也能反过来与这些 Claude 对话。**
- ⚠️ **他的判断**（[00:10:04]）：**"在极限下我认为 artifact 会成为你进入 harness 的界面：你可以在这份活的计划文档上评论，你可以看到多个 agent 在做不同的事。"** 他称之为 ⚠️ **"给你的 harness 现做一个界面"**。
- **他承认难点**（[00:09:03]）：**"这比一道多选题复杂太多了"**——图、代码片段、schema，每个问题形态不同。

### ⚠️ 可变软件（mutable software）：主张与反对

- **机制**（[00:34:23]、[00:41:28]）：**Claude Mods 可定制 harness 的执行与 UI 两边**；内部原名 **function hooks**；跑在 TypeScript 运行时**进程内**，所以**作用域里有会话状态**（轮数、token 数、消息）、**能派生 sub agent 并解析结构化输出**，⚠️ **而且能改 UI——"这是你在 hooks 里永远做不到的"**。
- ⚠️ **让它便宜的那个原语**（[00:35:23]）：**"forked agent 会维持 prompt cache，所以你可以 fork 出去做一个小请求，而它会非常便宜。"** 由此得到 **supervisor 模式**（[00:45:31]）：next-steps 用 forked sub agent 做，⚠️ **"所以它之后不留在上下文里"**。
- ⚠️ **他的主张**（[00:39:27]）：**"这是 mutable software 的一个预览……如果开启，你可以安全地定制任何一个软件。我觉得越来越多的应用理想上都该做这样的事。"** 给创业者的具体建议：**"你可以直接去问 Claude：我们能不能做个扩展系统？那会长什么样？"**
- ⚠️ **主持人的反对意见本页并列记录**（[00:39:27]）：**"当你什么都能做的时候，用户往往会困惑。所以通常能成的是一个有主见的流程。"** ⚠️ **他的回应很短但对**：**"或者可以有一个 skill 来给出主见。"**
- ⚠️ **与本页既有材料的关系**：这与 [DHH 的"可塑操作系统"](#-可塑操作系统linux-的历史性翻转dhh2026-08-26) 形状相同、层级不同——**DHH 讲的是 Linux 这一层的可改写，Thariq 讲的是应用自身的可改写，而且是由 agent 来改。** 它也与 [Sinofsky 的"决策引擎与概率式编程"](#-另一条路不生成文本而是选选项决策引擎与概率式编程的复活a16z2026-09-26) 构成同一周里的两种"软件会变成什么"的回答。

### ⚠️ harness 的苦涩教训，以及杠铃

- **他的版本**（[00:46:31]）：他先自我澄清"我们这里稍微误用了 bitter lesson——它更多是关于 scaling 和算力"，然后给出自己的用法：⚠️ **"harness 会非常快地过时，而它们怎么变是不直觉的。"**
- ⚠️ **他对"为什么现在该把智能花在界面上"的解释**（[00:47:31]）：**"模型的智能比一般软件工程任务高得多……但目标仍然是交付用户价值。所以你花算力的方式，是把用户留在环里、确保最终到了正确的决定——而 artifacts 和 mods 就是花掉这份智能的方式。"**
- ⚠️ **核心 harness 必须复杂且非常安全**（[00:47:31]–[00:48:33]）：清单是 **agent loop + 沙箱 + auto mode（权限与批准）+ computer use + MCP + web search/fetch**；**"随着模型能做的越来越多，核心 harness 其实必须相当复杂、而且非常安全——但你怎么和它交互，可以变很多。"**
- ⚠️ **杠铃效应**（[00:48:33]）：**"对很复杂的编码任务，你该用我们的 harness；而对更简单、更垂直的东西，你可以自己搭——因为 Claude 变得更会搭 harness 了，而且我们有 managed agents 这样的原语。"** 他说以前不得不用 **Agent SDK（其实就是 Claude Code 的封装）**。
- ⚠️ **他留的一条自我否定的可能**（[00:48:33]）：**"有一条分叉路——最终模型就是能一次性 vibe code 出 Claude Code 的精确版本。但我认为它们现在能一次性做出更简单的 harness。"**
