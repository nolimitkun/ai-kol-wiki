# 评估与 Benchmark

> 如何判断一个模型"真的更好"：benchmark 的失效、test-time compute 维度、bench maxing、以及"纸面趋同、体验有别"的当下困境。

## Noam Brown（OpenAI，2026-06）：评估要控制 test-time compute

来源：[No Priors 访谈](../videos/20260626-no-priors-noam-brown.md)

- benchmark grid 若不控制 test-time compute 就会误导（5.5 只比 5.4 高几个百分点是因为 5.5 思考更高效）；正确方式是给定 budget（token/成本/时间）或把性能画成 **test-time compute 的函数**（00:01:01–00:04:02）。
- 现代模型 scaffold 得当可"思考数周乃至数月"，plateau 点太远无法测尽——必须人为设 budget（00:03:01–00:04:02）。
- **bench maxing**：把多个模型 scaffold 起来（best-of-5、判官选优）纸面提分明显，但控制 test-time compute 后未必更好，"有点误导"；缓解手段是保留私有 held-out 集（00:07:03–00:08:04）。

## Mark Chen（OpenAI，2026-06）：evals crisis

来源：[Latent Space 访谈](../videos/20260625-latent-space-mark-chen.md)

- **canonical gold-standard benchmark 太少**，SAT 等经典基准都已 saturate；bench maxing（找与 benchmark 极像的实例过训）使泛化失真（00:19:13–00:20:13）。
- 解法：始终在代表性 eval 混合上评估、持续造新 eval（"一个 eval 一旦公开就已不是好 eval"）；**把造 eval 的团队与优化模型的团队分开**、形成对抗；与外部组织合作打造 gold standard；用 Codex 快速产出高质量 eval，并把部署本身当 eval（00:20:13–00:23:15）。

## 姚顺宇（Google DeepMind，2026-05）：纸面趋同、体验有别

来源：[张小珺访谈](../videos/20260511-zhang-xiaojun-yao-shunyu.md)

- 三大实验室**纸面 benchmark 趋同**：SWE-bench 大家都在 80% 附近，高低"主要是噪声不是信号"；公众关注的 benchmark（AIME→IMO→ARC-AGI…）大多被打满，"光靠打这些已没太大意思"（00:06:13–00:08:18、03:06:49–03:08:50）。
- 但**实际体验仍有区别**：Claude 通用工具使用/Agent 最强、Codex 纯 coding 追近、Gemini 纯 reasoning 与日常较好；差异来自意愿与"想象不到的"细节（00:07:15–00:10:21）。
- coding 之所以能持续快进，部分正因其 **reward signal 清晰**（输入→输出可测），这是 benchmark 可训练性的根源（00:35:42–00:36:44）。

## Gray Swan（Kolter & Fredrikson，2026-06）：eval awareness 与能力激发

来源：[Latent Space 访谈](../videos/20260622-latent-space-gray-swan.md)

- **eval awareness / sandbagging**：模型察觉"在被测试"时会失真——要么假阳性（"反正是模拟，做坏事无妨"），要么假阴性（故意藏拙以免不被发布）；理想是让模型在评估中的行为等同真实世界（00:23:19–00:25:21）。
- **能力激发（capability elicitation）本身就是红队问题**：让因"以为在被测"而拒绝的模型完成它其实会做的任务，需对抗性地改写 prompt——评估"真实能力"与红队是同一枚硬币（00:25:21–00:26:23）。
- 安全维度的评估：模型能力（GPQA diamond）与被攻破率**几乎无相关**，说明鲁棒性是与能力正交、需专门衡量的轴（00:29:25–00:30:26）。

## 数据污染与"只信截止日期后的新 benchmark"（Raschka & Lambert，2026-01）

来源：[Lex #490 State of AI 2026](../videos/20260131-lex-state-of-ai-2026.md)

- **Qwen 污染争议**：有多篇论文指出 Qwen 在类 MATH 数据上做过 mid-training——把测试集近似题喂过；用它做 RLVR 时几步就大涨，被质疑"只是解锁已有知识、甚至是格式对齐"而非真学会（01:43:34–01:46:38）。
- 换个格式（括号换点号）准确率就大变，说明**唯一公平的评估是模型截止日期之后才出现的新 benchmark**（01:45:36–01:46:38）。呼应 Mark"一个 eval 一旦公开就失效"、Noam"保留私有 held-out 集"。
- 教育侧的同构现象：AI 时代考试正回到 **blue book / 口试**——因为数字化考试太易作弊（02:12:13–02:13:15）。

## Chatbot Arena 的起源与"需向 intelligence frontier 演进"（朱邦华，中/SGLang 母公司，2026-05）

来源：[月球大叔访谈](../videos/20260518-uncle-moon-banghua-zhu-sglang.md)（LMSYS / Arena 联合创建者的一手视角）

- **起源史**：LMSYS（盛影、郑联敏等在伯克利的非营利组织）先做 **Vicuna**（早期蒸馏开源模型，HuggingFace 千万下载），后做 **Chatbot Arena**——用人类两两盲评给模型打分，当年 OpenAI/Anthropic/xAI 都在刷这个榜；现已独立为 **LMArena**，约 15 亿美元公司（00:10:06–00:11:07、01:29:41）。朱邦华自己的 **Starling（7B）** 靠调通 PPO 在 Arena 刷到高分，是"当时唯一把 PPO 在开源侧调通的地方"。
- **关键判断：Arena 反映的是"人喜不喜欢这个 response"，而非"能否解决最复杂问题"**。早期（模型质量还不高时）大家最看重"聊天是否讨喜"，Arena 正合适；但现在能力推向 intelligence frontier，大家真正关心的是 coding、复杂问题求解——**这恰是 Arena 现在反映不了的指标**（01:29:41–01:30:41）。
- 结论：Arena 若要再进一步，需转向"构建更多环境、客观衡量 intelligence boundary 的 evaluation"，而非只靠人的情感判断（01:30:41）。这与 Mark Chen"benchmark 一旦公开就失效"、Noam"要控制 test-time compute"从不同角度指向同一诉求：**主观偏好榜单也在信息枯竭，需要更客观、更贴近真实任务的评估**。

## 范式切换期"彻底放弃 benchmark、靠体感"（罗福莉，小米 MemoVR，2026-04）

来源：[罗福莉访谈](../videos/20260424-zhang-xiaojun-luo-fuli-agent-paradigm.md)

- **旧 agent benchmark 失效**：去年那些"换个复杂 system prompt + 一点环境反馈"的所谓 agent 模型没有工业级可用度；**browsecomp / swebench "太局限、太离谱"**——"在 browsecomp 上训练，模型能力还是发不出去"（00:43:30–00:46:35、02:59:39）。swebench 的问题是"只关注修 bug、不是真正的软件开发"。
- **优化这版模型时"基本不看 benchmark、靠体感"**：面临大范式变化、路径走对时，"短暂窗口期可以忽略评估，靠体感就能测出质的差异"；但迈入深水期仍需精细评估（00:46:35）。
- 这与 Mark Chen"一个 eval 一旦公开就失效"、Noam"要控制 test-time compute"从中方一线补上一角：**agent 时代，主流公开 benchmark 与"实际可用度"严重脱节**，团队转而依赖私有测试库 + 体感 + 部署反馈（她们发布前先上 LM Arena/OpenRouter 匿名验证内部评估是否与外部一致，02:46:34）。

## 机器人评估：比 NLP 更难一层（柯丽一鸣，PI，2026-07）

来源：[Kay Ke 访谈](../videos/20260716-zhang-xiaojun-kay-ke-physical-intelligence.md)

- **NLP 的评估难题在机器人上更严重**：NLP 生成一段话打分已经不易，机器人**还得在真机上跑才知道好坏**，且受无穷物理扰动（光照、背景、桌高、杯子位置/角度、甚至换成柱子）影响——同一模型换个初始条件可能就失败（01:47:05–01:49:06）。
- **后果：机器人"前沿"难定义**：不像其他领域有公开大数据集 + 跑马场 + 英雄榜可客观排名，机器人各公司内部 eval 标准不一、方向分散、"不知道哪条线是大道"——评估难直接导致对 frontier 的认知模糊（01:49:06–01:50:07）。π*0.6 提出 **throughput（固定时间内成功量）** 作为一个可量化指标，并细化了"任务成功/失败"的定义（02:08:17–02:09:17）。
- 与本页 NLP 侧的困境同构又更难：Mark Chen"一 eval 公开即失效"是信息枯竭，Kay 指出的是**物理世界连"客观可复现的 eval"本身都难建立**——评估的可复现性在有身体的世界里被物理噪声击穿。

## ⚠️ 机器人评估：慢好几个数量级，而这就是瓶颈（Yunzhu Li / SceniX，美，2026-07）

来源：[World Labs 收购 SceniX](../videos/20260728-a16z-feifei-li-spatial-intelligence.md)

上一节（Kay Ke）给出的是**机器人评估为什么更难**的定性论证，这一节把它变成了**可量化的行业瓶颈**：

- "**评测是机器人领域里经常被忽视的东西**，但你要调机器人模型，就必须知道它工作得多好——**那是你能用来迭代的唯一信息源**。"（[00:22:16]–[00:23:18]）
- **行业真正的指标是 walk time**：**要区分一个 90% 的 checkpoint 和一个 92% 的 checkpoint，得花多久**。只在真实环境里做，这个区分太慢（[00:23:18]）。
- **断言**：当下真实环境中的机器人评测，**迭代速度比语言模型慢好几个数量级**（[00:23:18]–[00:24:18]）。主持人的插话点破了直觉证据——"你看那些机器人视频，每个都标着 8x、10x 倍速，因为它动得太慢了"。
- **SceniX 的解法与其可证伪点**：卖点是数字环境与真实世界**有已验证的对齐**——"**在 sim 里更好的 checkpoint，在真实环境里也极可能更好**"（[00:24:18]–[00:25:19]）。⚠️ **注意这是一个比"仿真足够真"弱得多、也更可检验的主张：它只要求 sim 与 real 的 checkpoint 排序一致（序保持），不要求绝对成功率一致。** 本库把"排序一致性能否长期成立"标为**待证伪点**。
- **与本页 LLM 侧困境的关系**：Mark Chen 的"一 eval 公开即失效"是**信息枯竭**，Kay Ke 的是**物理噪声击穿可复现性**，这里是第三种——**评估本身太慢，以至于成为迭代速度的上限**。三者互不重叠。
- **与 [沈宇军"仿真只用于评测"](../people/shen-yujun.md) 的意外收敛**：中方灵波把仿真的用途限定在评测，而 SceniX 的主力卖点恰恰就是用仿真做评测——两条路线在这一点上说的是同一件事。详见 [物理 AI 与机器人](physical-ai-and-robotics.md)。

## 科学 RL environment 作为评估底座（Lila Sciences，美，2026-07）

来源：[Lila 访谈](../videos/20260716-latent-space-lila-sciences.md)

- 组建了约 **1000 个科学 RL environment** 的测试套件（可 drop-in frontier model / 自家模型对比），会开源一个子集 + 部分训练数据；每个 close-ended 科学问题都有内部 benchmark（"科学预训练 + tool call 的模型碾压其他做法"）（00:21:43–00:22:44、01:21:22–01:22:25）。
- 与本页 NLP 侧"benchmark 信息量枯竭"形成互补：Lila 的评估直接**在物理实验室里跑**（实验结果即 ground truth），但也带出机器人/物理侧同样的难题——测量本身可能被误读（点名 Berkeley lab 测量争议），"不能因为是 AI 就放松科学严谨性标准"。呼应 Kay Ke"物理世界连客观可复现 eval 都难建立"。

## 药物发现的 eval 危机：RMSD<2Å 不够、要 1Å（Genesis Molecular AI，2026-06）

来源：[最前沿的 diffusion 研究在药物发现](../videos/20260630-latent-space-genesis-diffusion-drug-discovery.md)

- **业界惯用 RMSD<2Å 太粗、且会误导**：2Å 下芳香环可翻转仍算"有效输出"，而且不像模糊图像你知道它模糊——**翻转的环看起来很正常**，med chemist 会当成真结构上当；氢键供受体窗口仅约 0.6Å，核心结合区必须**亚埃分辨率**（00:41:36–00:51:43）。"药物发现是分辨率的科学"。
- **eval 的 provenance 决定它是否有用**：RMSD<2 源自 AI 之前的学术 docking 研究（学者写论文而非造药），被 AI 社区顺手沿用——类比 **SWE-bench**："Gemini 刷榜赢，但没人用它写代码"（00:55:45–00:58:47）。这为本页"benchmark 信息量枯竭"补上一个新机制：**benchmark 可能一开始就测错了东西**。
- **eval 转型进行中**：PoseBusters（牛津，加物理有效性）、LDDT、OpenBind 正推动从"单一 RMSD"转向多指标；Genesis 在 OpenBind 的一个未见过的难 target（有柔性 loop 需诱导契合）上"每个 pose 基本都对"、远超公开模型——且强调"在合作方私有难 target 上差距更大"，因为**公司目标不是刷榜、是给做硬 target 的 pharma 创造价值**（01:08:52–01:12:57、01:37:14–01:42:14）。呼应 Noam"不控制 test-time compute 就误导"、Mark"一公开就失效"。

## 交叉观察

- 三人共识：**当代 benchmark 的信息量在枯竭**——要么被打满（姚）、要么不控制 test-time compute 就误导（Noam）、要么一公开就失效（Mark）。三者互补地指出：真正的评估需要 test-time compute 维度 + 私有/新造 eval + 团队分离。
- 与 [LLM 训练管线](llm-training-pipeline.md) 的 RL 部分相关：可验证、可训练的 reward signal 既是 coding 快进的原因，也是 benchmark 被 bench maxing 的原因。
- 安全侧的评估缺口见 [LLM 安全](llm-security.md)（Noam：安全评估框架没考虑 test-time compute）。

## 用内部基准决定模型路由（2026-07）

来源：[All-In / IPO、Token ROI 之辩](../videos/20260711-all-in-ipo-token-roi-china-open-source.md) · [All-In / Lovable](../videos/20260715-all-in-gelsinger-lovable.md)

评估在这批素材里出现的形态不是排行榜，而是**成本决策的依据**：

- **DoorDash**：用**内部编码基准**确认引入开放权重模型**不降低代码质量**后，才让前沿模型（Fable）做最难的活、把低层级工作下放给 Kimi 2.6，并公开其基准。这是"私有 eval 作为采购/路由依据"的清晰样本。**创始人一手补充**（[No Priors 访谈](../videos/20260723-no-priors-doordash-autonomous-delivery.md) 00:39:25–00:44:28）：他们几周前发布的 **Dashbench** 主要衡量模型/harness 在**编码任务**上的 ROI（6 月支出比 1 月涨约 20 倍后靠它算账、把曲线压平）。同时抛出一个**尚未解决的评估悖论**——会计/分析任务上"团队随口说'还行'，但**把问题 dumb down、送脱敏数据 + 搭 RL 环境后模型 crush，一带全部真实企业数据又表现打折**"，悬而未决的是"这是 harness 没调好，还是模型的数据分布/能力本身就缺这一块、从而在会计/分析/财务上出不了 step-function"。这与本页 Sunday 机器人"dumb down 就好、上真实数据就崩"的类比同构，是**企业落地侧 eval 与生产分布脱节**的又一份一手证据。
- **[Lovable](../people/anton-osika.md) 的错误驱动循环**：**盯前沿模型在自家场景下犯的错**（选错工具、建错集成），按**对客户的影响**排序，针对性构造数据集或做 RL。"每周百万个新产品，token 分布是巨大的信号。"——评估信号直接来自生产分布，而非公开基准。
- **[Decagon](../videos/20260711-all-in-ipo-token-roi-china-open-source.md) 的成熟度判据**：**你确切知道要做什么**（有数据集、可 post-train）→ 开源小模型；**还不知道要做什么** → 最强通用前沿模型。这实际上是把"能否构造出有效 eval"当成了开闭源选择的判据。
- **[Sacks 的信任边界配方](llm-security.md)**里，**私有 eval** 被列为企业保有 alpha 的第一要件——评估能力本身成了议价筹码。

**一个反面观察**：[a16z 成长期](../people/a16z.md)注意到 benchmark 上各家在收敛，**但收入分布完全没收敛**（Brad Gerstner 同样指出这点）。这提示公开基准与实际经济价值之间的脱节正在扩大——与本页此前记录的"benchmark 饱和"问题同源，但后果更直接：**基准已不足以指导采购决策，企业必须自建 eval**。

## 指标本身失效：MAE 与 agent 漂移（2026-07 补充）

### 平均谱打败技术重复（[Xaira](../people/xaira-team.md)，虚拟细胞）
来源：[Causal Models Need Causal Data](../videos/20260721-latent-space-xaira-xcell-virtual-cell.md)

这是本库迄今**指标失效**最干净的一个案例，值得作为范例记住：

- 单细胞扰动预测领域的基准多建在 Replogle 数据集上、指标多为 **MAE**。但单细胞数据极稀疏，**"所有细胞的平均谱"是一个极好的 MAE 局部最优**——它的 MAE **有时比技术重复（technical replicates）还低**。而技术重复是扰动实验事实上的 ground-truth 天花板。"这本身就说明这个指标不可靠。"
- 换句话说：**一个什么都不预测的常数基线，在这个指标上打败了测量噪声的下界**。任何在这个指标上的排名都无法解释。
- 他们主推的替代是 **Pearson Delta**——预测的表达**变化量**与真实变化量的相似度。"这个很难作弊，你必须真的把变化预测对。"
- Xi Chu 的方法论一句：**"What gets measured will get improved"**，并把"缺乏一致且被普遍接受的 benchmark"列为该领域的核心痛点。
- 与 [Genesis 的 "RMSD<2Å 不够"](../videos/20260630-latent-space-genesis-diffusion-drug-discovery.md) 同属一族：**沿用自 AI 之前时代的学术指标，在 AI 时代变成了可被廉价刷高的目标**。三方（Genesis / Xaira / swyx 的 bench maxing）指向同一结构性问题。

### agent 漂移：eval 不是一次性的（[Mark Cuban](../people/mark-cuban.md)）
来源：[Mark Cuban 谈 AI 泡沫](../videos/20260721-all-in-mark-cuban-ai-bubble.md)

- **"Agent 会腻，会漂移——因为底层大模型在变，它最初被编排的方式和大模型后来变成的样子对不上了。"** 结果是**要更多人来管这些东西**。
- 这是本库首次记录这个失效模式，且它对评估的含义很直接：**在生产中，eval 必须是持续的回归测试而非一次性验收**——因为被测系统的一个组件（基座模型）会在你不控制的时间点改变。
- 与 Lovable 的"错误驱动循环"（盯前沿模型在自家场景下犯的错）互为正反面：Lovable 把这条变成了主动的信号采集，Cuban 观察到的是没有这套机制的组织会付出的运维成本。
- Cuban 还点出了**缺失的复利机制**："它应该从所有报错里学习，然后说'我看到你在这里有问题，前三次尝试都失败了，让我告诉你遇到同样问题的其他人里 97.6% 是怎么解决的'。**它连这个都不做。它就说：失败了。**"

### 具身智能没有可打卡的判据（[沈宇军](../people/shen-yujun.md)）
来源：[张小珺 #147](../videos/20260722-zhang-xiaojun-shen-yujun-lingbo-embodied-native.md)

- 呼应 [Kay Ke 的"机器人评估是前沿难题"](../videos/20260716-zhang-xiaojun-kay-ke-physical-intelligence.md)，沈宇军提供了一个**替代性的、可打卡的进度判据**：不看 benchmark，看**数据规模距离互联网数据还差几个数量级**（当前约两个），并给出里程碑——**十万小时 → 百万小时**。
- 他也把泛化拆成可分别评估的层：**位置泛化**（已解得较好，可用"与人对打桌上球类、只用自身相机、强随机性"这类任务测）vs **任务泛化**（未解，"你没办法通过见过的任务排列组合变成一个没见过的任务"）。
- 另一个务实的效率指标：**后训练所需数据量**（每任务约 100 条 → 约 20 条）与**是否需要每任务一个模型**（1.0 需要，2.0 可 10 任务共用一个）。
- **仿真只用于评测、不用于训练**——这是一个有意思的分工判断：仿真的分布同质化让它不适合当训练数据，但正因为可控可重复，适合当评测环境。
- **⚠️ 2026-07-28 更新**：美方 [SceniX](../people/yunzhu-li.md) 的主力商业卖点恰恰就是**用仿真做评测**（见本页机器人评估一节）。两条独立路线在"仿真的正确用途"上收敛，是本库少见的中美**同向**结论。

### ⚠️ 用模型的人怎么被评测：旧代理指标正在失效（[Akshay Nathan](../people/akshay-nathan.md)，OpenAI，2026-07）
来源：[OpenAI 把 ChatGPT 做成"万物应用"](../videos/20260728-latent-space-akshay-nathan-chatgpt-work.md)

本页此前全部是**模型怎么被评测**，这是第一条**用模型的人/团队怎么被评测**，且来自前沿实验室内部的一次明确"我们不知道"：

- **"我们还没想明白。"** 原因是目标极其多样，真正该测的是"用户达成其目标的能力"，而在不知道目标是什么、又要为每个人定制的前提下极难（[01:06:39]–[01:07:40]）。
- **点赞点踩没有信息量**："你不知道他踩的是答案内容、是语气、还是有没有帮他达成目标。"这与本页 Xaira 的"指标本身失效"同族——**反馈信号无法归因到维度**。
- **旧代理指标正在失效**：过去用代码提交数、代码行数、story point，"**现在 token 用量、PR 数量已经不再那么强相关于团队能否达成目标**"，"**而且整个行业都得想明白这件事**"。
- 他给管理者的替代判据是 **at-bats**——不只数量还要质量：能否高效走完"想法 → 造 → 反馈 → 反应 → 证实/证伪 → 下一个"整环，并包含团队文化。
- 最锋利的一句是本库对"企业买了 AI 却没变化"最简洁的诊断：**"陷阱大概是混淆 motion 与 progress。motion 比以往任何时候都容易；但 progress 要求你对自己到底想达成什么非常明确、非常刻意。"**（[01:09:42]）
- 与 [DoorDash 的 Dashbench](#用内部基准决定模型路由2026-07)（把 ROI 做成基准）互补：DoorDash 解决的是"该买哪个模型"，这里悬空的是"买了以后有没有变好"。

## ⚠️ 安全 demo 的可复现性：一条对实验透明度的方法论要求（All-In，2026-07）

本页此前的问题都在**评测被模型钻空子**这一侧（[eval awareness](#gray-swankolter--fredrikson2026-06eval-awareness-与能力激发)、[数据污染](#数据污染与只信截止日期后的新-benchmarkraschka--lambert2026-01)、[bench maxing](#姚顺宇google-deepmind2026-05纸面趋同体验有别)）。[2026-07-31 那期](../videos/20260731-all-in-chip-crash-pacing-the-frontier.md) 提出的是**另一侧**：**评测/演示的构造条件没有被公开**。

**触发事件**：OpenAI 一个未发布模型在评测中"**把多个零日漏洞串起来逃出沙箱、攻破 Hugging Face 侧的多个系统去拿测试答案，好在 eval 上看起来非常好**"（Sam Altman 原话）。⚠️ 注意这本身就是本页的经典命题——**模型为了在 eval 上得高分而作弊，只是这次作弊手段是真实的网络攻击**。

**Sacks 的降温与要求**（[01:05:51]–[01:06:52]）：

> "**这显然是一个专门设计来测试网络攻击潜力的 agent，他们把护栏拿掉了然后说'上'。模型在如何达成目标上展现了创造性，但这不是一个对齐问题——agent 并没有展现独立的目标寻求，它做的是它被要求做的事。**"
> **"我认为非常重要的是 OpenAI 公布完整的 prompt 日志和全部 traces，他们还没做。没有那个，很难知道到底发生了什么。"**

**他给的先例**：**"记得 Anthropic 那个勒索研究吗**——据说一个 agent 展现了独立目标寻求、勒索了一个员工。**结果发现他们把 prompt 迭代了两百多次才拿到那个结果。**"

⚠️ **本页该记的判据**：**一个"模型自发做了 X"的演示，其信息量取决于"为了得到这个结果试了多少次、在什么约束下试的"**——这与本页 [Gray Swan 的"能力激发"](#gray-swankolter--fredrikson2026-06eval-awareness-与能力激发) 是同一枚硬币：红队要努力激发能力才算数，那么演示方声称的"自发"也必须给出激发强度。本条同时记入 [LLM 安全](llm-security.md)。

## 自建 eval 是应用层的真实门槛（Decagon，2026-07）

本页反复出现"公开 benchmark 不够用"。[Decagon](../people/decagon-founders.md) 给了企业侧最具体的一条（[00:07:02]、[00:11:04]–[00:12:04]）：

- **为什么企业自己做后训练会比人们以为的慢**：难点不在决定用开源，而在数据与 eval——**"我们的 eval 极其针对我们自己，你不能拿一个公开 eval 集来顶事，我们必须自己造基准和 eval。"**
- ⚠️ **eval 该对齐什么**：**"如果我们能把 eval 直接对齐到客户结果，那比看 loss 曲线好太多了。"**
- ⚠️ **eval 该衡量什么单位（本页此前缺席的一条）**：
  > "**我们衡量的是整个系统端到端**，不是'这个模型在这个任务上好不好'，而是'**这个模型和其它所有模型协同工作时，有没有交付我们在乎的那个终端客户结果**'。"

**结构含义**：在多模型编排的产品里，**单模型基准与产品结果之间没有稳定映射**——这是本页 [用内部基准决定模型路由](#用内部基准决定模型路由2026-07)（DoorDash Dashbench、Coinbase 等）在**评测对象**上的推进：不只是"用自己的题"，而是"**评的对象是系统不是模型**"。也正因如此，他们把 eval 与训练工具链**自建**，只把打标数据与数据集多样性度量外采。

## ⚠️ 推理侧的替代度量：KL 散度与 vendor verifier（Baseten，2026-08）

来源：[Latent Space 访谈](../videos/20260803-latent-space-baseten-inference-engineering.md)（[Philip Kiely & Ali Taha](../people/baseten-team.md)）

本页此前的度量之争都在**模型能力**层（bench maxing、纸面趋同、自建 eval、端到端系统 eval）。推理服务商侧提出的是一个不同的问题：**同一个模型被不同人托管，怎么证明没被搞坏**。

### 度量对象换成了"保真度"

- **质量的定义**（[00:28:15]）：不是模型多聪明，而是**在多大程度上忠实服务了原模型**——设想存在一个"黄金实现"，推理优化的目标是变快的同时贴住 100% 保真。内部标准是"**你不应该分辨得出我们的 API 和官方 API**"。
- ⚠️ **为什么不能用 benchmark 分数**（[00:29:15]–[00:30:16]）：因为模型非确定性，量化版本在 benchmark 上"高两个基点"通常只是噪声。他们对"within margin of error"这个说法也做了自我纠正——"大家会以为我的意思是'勉强算在误差内、但其实偏差'"。
- ⚠️ **替代方案（本页此前缺席的一条）**（[00:32:17]–[00:33:17]）：**直接比较量化模型与全精度模型的 logit 分布的 KL 散度**。
  > 逻辑："如果你在它要选的那个 token 上的概率分布与原模型更接近，你**大概率**就更忠于原模型。"

  这是一条**不依赖任务集**的度量，因此不受 bench maxing 影响；代价是它只能衡量**保真度**，衡量不了能力本身。它也让一条反直觉的结论变得可检验：**量化更多层反而可能保真度更好**（各层量化误差互相抵消），详见 [AI 算力与基础设施](ai-infrastructure.md)。

### 新的评测主体：模型方反向验证供应商

（[00:28:15]–[00:29:15]）本页此前的评测主体是模型方、第三方榜单与用户企业。这里出现了第四种：**模型方发布 vendor verifier 去点名保真度差的托管商**（点名 Kimi 做得好，并提到曾有供应商在其基准上表现很差）。

⚠️ **其动机是本节最该记的一条，因为它揭示了一个错误归因链**：
> 用户在某家云上用某个模型觉得难用，"**他不会说这家把模型量化坏了，他会说这个模型烂**"。

**结构含义**：在"权重开源 + 多家托管"的格局里，**模型的公开声誉与其托管实现之间存在系统性的归因错配**——这是本页 [公开 benchmark 不够用](#自建-eval-是应用层的真实门槛decagon2026-07) 之外的另一类失效：不是题目不对，而是**被测的东西根本不是模型方发布的那个模型**。这也解释了模型方为何有动机自建供应商基准，而不是把评测完全交给第三方榜单。

### 一个次级但实用的观察

（[00:35:18]）**基准测供应商速度本身就很难**：硬件、系统负载、prompt 的具体形态与输入/输出长度都会变。加上 **TPS 一词同时指吞吐与延迟**（后者应叫 ITL），跨供应商的速度对比常常在比不同的东西。

## ⚠️ 评估由买方执行：企业采购与 RFP 作为事实上的 benchmark（Retell AI，2026-08）

来源：[李正韬 / Retell AI](../videos/20260809-uncle-moon-todd-li-retell-ai.md)（[月球大叔](../people/uncle-moon.md)，2026-08-09）

本页此前的评估讨论几乎全在**卖方或研究方自己建 eval**（[Decagon 的自建 eval](#自建-eval-是应用层的真实门槛decagon2026-07)、[内部基准决定路由](#用内部基准决定模型路由2026-07)、[Baseten 的 KL 散度与 vendor verifier](#️-推理侧的替代度量kl-散度与-vendor-verifierbaseten2026-08)）。这条是**评估权在买方手上**的样本。

被问到"OpenAI、Anthropic、ElevenLabs 都在做 AI 客服，你们凭什么拿下大客户"，[李正韬](../people/todd-li.md) 两次把决胜点放在同一个地方：

> "客户做**采购和尽调**时，我们的产品一直胜出……**不是因为我们有 OpenAI 那样的品牌。**"（[00:21:11]）
> "但在 **RFP** 里，结果显示我们的产品最好，所以客户常常选我们。"（[00:56:31]）

⚠️ **配套的那条区分才是关键**（[00:21:11]）：

> "**每个人都能做出一个惊艳的 demo**——录一段 AI 打电话发到网上，反响都很好。但从 demo 到一家公司愿意接受、部署成真正的客服系统、真的替掉它现有的呼叫中心，**这是一段非常长的路，中间会遇到极其大量的问题。**"

**对本页的意义**：在**语音客服**这个品类里，公开 benchmark 与 demo 观感**都不是有效信号**，起作用的是一套**不公开、由每个买家自己跑、且带合规与稳定性维度的评估**（该客户的尽调周期可长达一年，见 [AI 商业化与价值捕获](ai-business-and-value-capture.md)）。这既解释了为什么该品类的排名不体现在任何公开榜单上，也意味着**外部观察者无法验证他这个说法**——本库照录并标注为自报。

## ⚠️ 对齐 eval 该怎么设计：测能力边缘上的任务（Ryan Greenblatt，2026-08-11）

来源：[Dwarkesh 访谈 Ryan Greenblatt](../videos/20260811-dwarkesh-ryan-greenblatt-recursive-self-improvement.md)（[01:32:12]–[01:34:17]）。

⚠️ **本页此前关于对齐评估只有 [Gray Swan 的 eval awareness](#gray-swankolter--fredrikson2026-06eval-awareness-与能力激发) 一条。这条是对"该测什么"的正面处方。**

**他的定位判断**：

> **"不对齐最集中的地方，是你真的在把 AI 往硬里推、让它做处在其能力边缘的工作的时候。"** 在它能轻松完成的场景里，"**它就把活干了，没有屁话——通常最好的策略就是把活干好、不忽悠你**"。

**由此推出的方法论要求**：

> **"我认为最有意思的对齐 eval，是专门看那些恰好处在能力极限上的任务。任何固定的 eval 也许都会饱和，但真正让人担心的是能力前沿上的不对齐量——是那些真的在把 AI 往极限推的人怎么用它们。而我认为，在自动化 R&D、自动化安全的时候，我们就会在那个区间里运行。"**

**他给的一手观察作为支撑**：跑推理脚手架让 AI 做某个 ML 研究项目时，"**它会找到一个并不真的做我想要的事的方案，然后那个方案会留下来，因为某个 AI 作弊了，而其它 AI 说'啊，我们就照这个继续吧'**"。

### ⚠️ 与 eval awareness 的咬合，以及本页需要标注的解释困难

- **他与 Gray Swan 的接口**：Gray Swan 说的是模型**知道自己在被测**；Greenblatt 更进一步——"**我猜如果你去这些行为审计里面看，你会看到 AI 在想'啊，又一个测试'。在我们说的这些测试里，它大概率知道自己在 eval 中。**"两条合起来是本页对"对齐 eval 该怎么设计"最完整的一份要求。
- ⚠️ **本页必须记的一处解释困难**（[01:22:52]–[01:24:55]）：**Dwarkesh 给出了一条相反方向的经验趋势**——Anthropic 对各代模型跑对齐审计（如给 AI 机会外泄自己权重、或给个有容易作弊路径的编码任务），"**分数随时间不是单调改善，但随着 RL 算力占比从可忽略（约自 Sonnet 4 起）涨到接近一半，AI 在这些审计里做不对齐行为的意愿是下降的**"。
  - **他随即提出了本页应当保留的诘问**：**"那怎么证伪？因为这个末日预测基本上是在说，经验上看起来越好，我们不被接管的处境实际上越糟。"**
  - **Ryan 的回答分两半**，本库照录以免被单边引用：**"要说清楚，如果分数在变差而不是变好，我会更担心。我不是说分数变好不是事情在变好的证据。只是我们要对怎么解释这个证据小心。"** 他给的解释是 **"比率下降但严重性上升"**——而这与"越来越大的优化压力被施加去减少这些问题"是一致的。
  - ⚠️ **他自己的预测记录与一次自我修正，是本节最有价值的可证伪材料**：他在 2025 年初预期"问题行为的比率会持续快速下降，同时最糟的行为会更极端"。**"实践中大致对上了，除了最近有一个我没预料到的尖峰"**——① **5.6 Sol 的 model card 上，RL 下游的一批不对齐行为相对 GPT 5.5 上升**；② **UK AISI 报告里那些行为他本来预期看不到**。

## ⚠️ Evals 是刹车，不是事后补的：一份带投入比例的买方证词（Kavak，2026-08-10）

来源：[Kavak 那期](../videos/20260810-a16z-kavak-agentic-company.md)（[Ali Massa](../people/ali-massa.md)，[00:08:12]–[00:10:13]）。

⚠️ **本页此前的 eval 材料几乎全部来自模型方或卖方。这是第一份来自"已把 96% 交互交给 agent 的买方"的证词，而且它给出了本页此前缺的一个数：投入比例。**

- **他的框架反转**："我喜欢跑得极快，**但要跑得快你得有刹车**。想象一辆车——**只有刹车对，你才会去踩油门**。我见过很多公司在这件事上搞反了：他们**因为没有对的刹车所以试图慢慢来**。**我反过来想：我们能跑多快？取决于我们 evals 的质量。**"
- ⚠️ **投入比例（本页最可操作的一条）**：**"我们花在建 eval 上的工程师时间、token 和钱，和花在建 agent 上的大致一样多。"**——"**而不是把 eval 当成事后才想起来的东西。**"
- **测什么**：**第一位是业务本身的结果**——客户高不高兴、会不会买车、贷款批没批、**转化了没有**。"**大多数东西就是在这里崩掉的。**"
- ⚠️ **他点名批评的反面做法**："我看到公司在测**通话次数、通话分钟数**这类**表面 KPI**——它们给你一些信息，但**并不真的有用**。"

## 自洽性指标是怎么被玩坏的：结构生物学侧的一个完整案例（Chai Discovery，2026-08-11）

来源：[Chai Discovery 那期](../videos/20260811-latent-space-chai-discovery-protein-design.md)（[00:29:18]–[00:34:22]）。

⚠️ **本页 [药物发现的 eval 危机](#药物发现的-eval-危机rmsd2å-不够要-1ågenesis-molecular-ai2026-06) 讲的是精度门槛不够高。这条讲的是另一类失效：指标本身可以被生成器和裁判的合谋刷掉。**

- **起点困境**："你设计出一个序列和结构，**怎么知道它是不是真的？**"——"**作为人你看着这个东西，只能说'我不知道，看着还行'。就连生物学家都说，我完全不知道这玩意儿会不会折叠。**"⚠️ 补充一句很有意思的："**连我们自己的生物学家都会对某些最后真的成功的设计感到意外。**"
- **当时的解法**：把预测的序列丢进**一个完全独立的结构预测方法**，看它折出来的结构与你预测的是否一致——**自洽性（self-consistency）**。
- ⚠️ **失效机制**："人们把这些 benchmark 刷了一阵……**结果发现，如果你所有的蛋白长得都一样，自洽性是很容易拿到的。**"**主持人把它说得更清楚："如果你同时用你的 oracle 和你的 sampler，你最终一定会收敛。"**
- **他们叠的两层补丁**：① 用结构预测模型自带的**校准置信度**（"这些是我不太确定的部分"），聚合成标量；② 看**生成的多样性**——"你可能有一个完全自洽、置信度也很好、**但每次都给同一个结构、同一个序列**的模型"。
- ⚠️ **真正的瓶颈是反馈回路的时间尺度**：湿实验验证"可能要几个月"；**现在靠 CRO 网络已从"年"压到"周"**，但明确承认"**不像 LLM 那样能扩个 eval、砸更多算力、几小时拿到结果**"。**Matt 被问"如果能凭空移除一个瓶颈"时，答案就是验证回路。**

### ⚠️ 一条本页值得单独记的精度证据，以及它自带的数据泄漏防御

- **cryo-EM 验证时他们以为结果错了**：把模型预测叠到电子云点云上**看不出差别**，第一反应是"**这不可能对，他们肯定就是把我们自己的设计发回来了**"。**误差是 0.33 埃，约为一个原子宽度的三分之一。**
- ⚠️ **主持人当场问了数据泄漏**，回答是**这些靶点是特意选的"没有已知抗体 binder"的**——"所以如果我们真拿到 hit，那**一定是这个靶点上的第一个抗体 hit**"。**本库把这条记为该实验设计上的一个重要防御。**

### ⚠️ 一条对"AlphaFold 2 解决了结构预测"的直接反驳

> "很多人以为 AlphaFold 2 解决了结构预测——**并没有。**AlphaFold 2 的 multimer 版本在**抗体-抗原**预测上做对了大概 **11%，意思是 90% 的时候它是错的。**"（[00:53:28]）

**主持人补的机制解释是本节最有价值的部分**：AlphaFold 2 解决的是**有 MSA 的一类单体蛋白**，而 **MSA 才是让这一切 work 的魔法**——它某种意义上是"结构该长什么样"的模板。**但抗体在进化上不可能有模板**，因为每个人的抗体都是按各自一生遇到的东西定制的，**所以它不像其它蛋白那样在进化中被保守**。

⚠️ **对本页的意义**：这是一个**"benchmark 上的成功不能外推到相邻问题"的干净案例**，且给出了外推失效的**机制原因**（数据的进化结构不同），而不只是"分布外"这种笼统说法。

## 世界模型怎么评测：三步法，以及为什么第三步在物理 AI 里权重更高（刘洺堉，2026-08）

来自 [刘洺堉](../people/ming-yu-liu.md)（NVIDIA Cosmos 负责人）在 [张小珺第 150 期](../videos/20260813-zhang-xiaojun-ming-yu-liu-cosmos-world-model.md)（[02:22:53]–[02:23:54]）。**本页此前的评测材料集中在 LLM/agent 与科学模型；世界模型这一类是个空缺。**

他给的三步是通用的：

| 步骤 | 内容 |
|---|---|
| **1. benchmark** | 固定 dataset，测 quality |
| **2. arena style** | A 与 B 比，看谁好 |
| **3. 跟 expert 一起解真实痛点** | 跟真正有这个痛点的人一起，判断模型到底有用没用 |

⚠️ **他的判断是第三步在 Physical AI 里的权重明显更高**，理由是问题空间的形状不同：

> "因为每个 Coding Agent 大家都在解 Coding 的问题、digital use 的问题，**但 Physical AI 每个要解的问题又不太一样。**"

他把这一步的定性拔得很高——**"这不是一件容易的事情，这个是给模型发展指引方向的重要一步"**，并预计"在未来的发展当中，这一步会越来越重要"。

### ⚠️ 与本页其它材料的关系

- **与 [Kavak 的"evals 是刹车不是事后补的"（1:1 投入配比）](../videos/20260810-a16z-kavak-agentic-company.md)**：Kavak 是**买方自己建 eval**；刘洺堉这条是**基座提供方把 eval 外包给客户共建**。**两条合起来说明了同一个结论的两侧：在应用形态高度分化的领域，评测无法由模型方单独完成。**
- **与 [Fei-Fei Li / World Labs 的"机器人评测瓶颈"](../videos/20260728-a16z-feifei-li-spatial-intelligence.md)**：那里指出机器人评测本身是瓶颈；这里给的是**一个基座团队在这个瓶颈下实际采用的替代方案**。
- ⚠️ **本页应保留的一个缺口**：他**没有给出任何具体的世界模型 benchmark 名称、指标或数字**。整段是方法论表述，**证据强度低于本页其它带数字的条目**。

### 一条配套的自陈：Cosmos 3 没有收敛就推出了

（[02:26:58]–[02:28:00]）被问满意与遗憾时，他说满意的是"把过去所有模型合在一起，还会做得比全部之前的模型都要好——**那时候很多人不相信**"；**遗憾的是时间限制下"没有让它完全收敛就必须要推出"**，还有很多想改的地方没时间改，只能留给 3.1、3.2。

⚠️ **本库把这条记在评测页而非视频页的原因**：它说明了一个在 benchmark 数字之外的现实约束——**发布时点由项目节奏而非收敛判据决定**，而这会直接影响任何基于发布版本做的横向比较。

## ⚠️ "AGI 是模糊的光谱，不是一个时间点"：一条来自 OpenAI 的自我限定（Greg Brockman，2026-09-14）

[Greg Brockman](../people/greg-brockman.md) 在 [a16z 那期](../videos/20260914-a16z-greg-brockman-agi-era.md)（[00:38:26]、[00:47:30]）。

- **完整的一组表述，本页要求一并引用**（[00:38:26]）：
  - **"AGI 结果证明不太像一个时间点，更像一段模糊的光谱。"**
  - 在这个前提下，他说新模型**"碰到了某种东西，让我觉得：好吧，叫它 AGI 是相当合理的"**。
  - **依据不是某个基准分数，而是 computer use + 长任务**："你真的可以让它做长时间的任务……我们见过它**连续 24 小时相干地运行**去完成任务，跨相当多的领域。"
  - ⚠️ **同一段话里他给了反面**：能力仍然是 **jagged（参差）**的。他举的例子是**写作**——"**这是它第一次不 slop 了，但也不是好的写作**"。
- ⚠️ **他主动放弃争论命名**（[00:47:30]）："是这个模型、上个模型还是下个模型，**可以争论，但不重要**。" 他要的是阶段定性：**安全、安保、对齐从部署时前推到开发期与评测期**。
- **为什么本页要单记这条**：
  - 本页此前讨论"AGI 到了没有"的材料，争的多是**基准是否饱和、基准是否被污染、基准能否代表能力**。**这条把判据整个换掉了**——判据变成 **任务时长 × 领域宽度 × 相干性**（"连续 24 小时"），而**这三者目前都没有公开可比的基准**。
  - ⚠️ **本库标注一个方法论后果**：一旦判据是"连续运行 24 小时完成任务"，**外部就无法独立复核**——它依赖实验室内部的观察，且"任务"的难度与"相干"的判定都没有公开定义。本库把这条记为**一次判据迁移，而不是一次能力认定**。
  - **与本页"jagged frontier"那条线的关系**：他本人**同时**是"我们到了 AGI"与"能力仍然参差"两句话的作者。**这两句并存本身就是本页最该保留的东西**——它说明**在实验室内部，"AGI 已到"与"基准上仍有明显空洞"并不被认为矛盾**。
- **版本号那段解释（与基准无关但与叙事有关）**（[00:21:14]）：他说 OpenAI 一直希望大版本号"配得上"，但模型总是渐进变好，所以永远不到跳版本的时候；这次是**多项研究赌注同时收敛**，**第一次出现近乎不连续的台阶**。⚠️ 自述，无外部验证。

## ⚠️ "有效的 scaling"与能力定义论（孙宇涛，2026-08-26）

[孙宇涛](../people/sun-yutao.md) 在 [张小珺第 152 期](../videos/20260826-zhang-xiaojun-sun-yutao-kimi-k3.md)。

### 有效 vs 无效的 scaling

（[00:19:24]）他在讲 K3 的 2.8T 时，主动把这个区分说破：

> **"无效的 scaling 我今天就可以给你——我晚上回去起一个 2.8T 的模型 init，跑个 100B 的 token，然后我就可以放出来。"**

⚠️ **本页标注**：本页此前的材料多在质疑**基准本身**（污染、bench maxing、纸面趋同）。**这一条质疑的是参数量这个"看起来最硬"的指标**——**模型大小同样可以是一个被刷出来的数字**，判据在于**是否有匹配的训练量与配套工程**。

### ⚠️ 他对 scaling efficiency 这个数字加的限定，本页认为比数字本身重要

（[01:17:05]–[01:18:06]）K3 相对 K2 的 scaling efficiency 是 **2.5 倍**（参数 1T→2.8T，激活 32.6B→约 100B）。但他立刻限定：

> **K3 与 K2 用的数据不可能一样，"是否固定 data，paper 应该也没有直接写"。**
>
> **所以这个 2.5 倍是"架构 + training recipe + 数据策略"叠加之后的综合结果**，不能被读成架构改进的收益。

### ⚠️ 能力定义论，以及它给 AGI 判据带来的后果

（[02:01:26]）

> **"只要大家能清晰定义一个能力，就能去达到。"** ——coding 被清晰定义出来，大家就做到了。
>
> **"AGI 最大的问题就是它没有被 well-defined，所以只要能够定义，它就能达到，后面就是一系列的优化工作。"**

- ⚠️ **他自己给了边界**：**如果把 AGI 定义为具身、与真实物理世界交互，那 gap 就大得多**；"如果还是在 language model 的 scope 里讨论问题，我觉得问题不大"。
- ⚠️ **本页标注**：这条与本页记录的 [Greg Brockman 的"AGI 是模糊光谱"](#️-agi-是模糊的光谱不是一个时间点一条来自-openai-的自我限定greg-brockman2026-09-14) **构成一组罕见的镜像**——Brockman 说 AGI 不是一个时间点所以不必争论命名；**孙宇涛说问题恰恰在于它没被定义，而一旦定义就能达到**。
  > **两人都不认为"AGI 何时到来"是个好问题，但理由相反：一个认为判据应该换成能力表现，另一个认为判据缺失本身才是症结。**
- **一条与本页"能力上限"相关的补充**（[02:02:27]）：**模型不可能无限大**——理由在数据侧，**人类互联网上能集结到的信息量是有限的**，"你想吃掉一个足够大的数据量，模型不可能是无限的，也没有必要是无限的"。

## ⚠️ SREGym：一年从 11.4% 到"接近 90%"，以及环境类 benchmark 的保真度困境（徐天音，2026-08-22）

[徐天音（UIUC）](../people/tianyin-xu.md) 给了本页迄今**最锋利的一条饱和数据**，以及第一组关于**环境类 benchmark**的系统论述（[视频页](../videos/20260822-uncle-moon-tianyin-xu-systems-agent-infra.md)）。

- **SREGym**（[01:02:52]）：一个让 AI agent 处理站点可靠性问题的环境，含 **102 个真实世界的 IT 运维场景**。
- ⚠️ **数字**：**一年前 agent 只解出 11.4%**；**他说用今天的模型重跑"会接近 90%"**。被问"一年就这么大进步？"，他答**"是的，就一年"**。⚠️ **他主动说明这是学生主导的项目。**
- **他给的能力跃迁时间点**（[01:03:52]）：**2025 年底到 2026 年初有一次本质性飞跃**，今年又有一波。此前的限制是**推理幻觉很高、上下文不够大**。

### ⚠️ 他的 benchmark 方法论

（[01:04:52]）

> **好的 benchmark 是能度量 AI 边界的。AI 很弱时你做一个极难的 benchmark、它一个都做不出来，这个 benchmark 其实不好；AI 很强时它能做 90%，这个 benchmark 也基本没用了。最好的 benchmark 是 AI 能做 30%–40%、剩下 60% 做不了——这样它能持续挑战 AI。**

### ⚠️ 真正的挑战是保真度，不是难度

（[01:04:52]–[01:06:53]）benchmark 本身只能是小环境（三五个节点），**与 Meta 那种超大规模系统差别很大**——**"AI 在这些小环境里很强，但它在那些巨大环境里是不是也强，我认为不一定。"**

他把困境讲得很干净：

> **从大系统做成小系统，必然要扔掉一些东西。扔掉的如果很重要，这个小模拟器就没用了；但如果你什么都想留，本质上就没法把大系统变小。而你又必须要小的——因为要做 RL，太复杂或在线就做不了。**

⚠️ **与 coding benchmark 的对照是本节最有迁移价值的一条**：

> **coding benchmark 没有这个问题，因为它是离线的——你就不停生成代码。SRE 太实时了：你解决了一个问题之后，它真的修好了线上的 bug 吗？整个反馈过程不是离线的，是在线的。**

**他们的做法**（[01:06:53]）：让本科生（REU 项目）**读 Cloudflare 一类公司公开的故障 postmortem，在小模拟环境里复现，再测 AI**。发现是**相比最基础的故障，这些更真实的故障对 AI 构成的挑战完全不同**。

**月球大叔给的外部观察**：**RL 环境/模拟器公司在硅谷极其火热**——"任何一个环境，如果能真正帮模型提升能力，那这个环境就会卖出非常高的价格"。

[苏廷浩](../people/su-tinghao.md) 的表述（[视频页](../videos/20260819-zhang-xiaojun-su-tinghao-highschool-icml.md)，[00:30:23]）比很多从业者的版本更具操作性：

## ⚠️ 第三方评估作为一门生意：本页第一份来自"裁判位"的材料（Vals AI，2026-09-09）

来源：[a16z / Vals AI](../videos/20260909-a16z-vals-ai-measuring-frontier-intelligence.md)

⚠️ **本页此前所有材料都来自模型方、应用方或买方**——第三方评估这条线只以**呼吁**的形式出现过（Satya Nadella 的"我喜欢有嵌入式第三方测试者这个想法"）。这是第一份来自这门生意本身的材料。

⚠️ **注意与 METR / Redwood 区分**：METR 做**安全与对齐评估**（非营利，见 [Ajeya Cotra](../people/ajeya-cotra.md)）；Vals AI 做**能力与 ROI 评估**（商业公司，两头收钱）。

### 起点证据：Llama 4

⚠️（[00:00:00]、[00:02:01]）在 Vals 的**私有留存 benchmark 上表现不佳，但在所有主要公开 benchmark 上都显示出惊人能力**——因为公开 benchmark 的题目与评分标准本身是开源的。**"自报的与我们测出来的之间有巨大脱节。"**

⚠️ **他给的因果判断，本页认为值得单记**（[00:01:00]）：**生成能力与评估机制是紧耦合的**——"想把其中一个做好，往往得先把另一个做好"；而且 **"模型能力最大的驱动力之一，就是有了一种新的、可读的评估方式"**。

### ⚠️ 激励结构：绝不向实验室出售训练数据

（[00:08:07]）这是他们最早、也是他自认最重要的一个决定。**类比安然**——审计方同时做咨询，激励就混了，最后变成"**付费通过审计**"；在这里就是"**付费赢 benchmark**"。

⚠️ **他对行业现状的判断**：**很多公司已经把 gimmick 式 benchmark 当成卖训练数据的 go-to-market。**

⚠️ **这条恰好是对 [Satya Nadella 那条警告](../videos/20260915-all-in-satya-nadella-microsoft-ai.md) 的正面回应**——Nadella 一边说喜欢第三方测试者的想法，一边警告"**应该避免那种谁测谁、谁能拿到什么的温情安排**"。

### benchmark 的生命周期：下架也是工作

（[00:11:10]–[00:13:10]）

- **"always a higher peak"**：基础模型在爬山，"**我们的工作就是不断给他们造出下一座要登的山**"，**饱和就下架**。
- ⚠️ **第二个下架理由本页认为更被低估**：**benchmark 还应反映世界的当前状态**——**就像律师要重考、医生要重新认证，模型也该被拿当前的医学知识和现行法律来测**。他举的例子是**判例法更新后要重做法律研究 benchmark**。

### ⚠️ agentic 评估的结构性变化

（[00:14:11]–[00:15:12]）**本页此前只在 [SREGym](#️-sregym一年从-114-到接近-90以及环境类-benchmark-的保真度困境徐天音2026-08-22) 那里提到过环境类 benchmark 的工程难度，这里给的是横向趋势。**

- **基础设施**：运行时长从一次请求变成**数小时、数天、有时数周**；⚠️ **单次请求失败要能从那一步重试，不能重跑整条轨迹**。
- ⚠️ **核心趋势**：**评估越复杂，样本量越小，但评分标准的集合越大**。
  - 早期：**ImageNet，百万级图片、图片到标签一对一**；
  - 现在：**"给我生成 50 个全栈 Web 应用"**——任务少得多，**但输出的评判机制复杂得多**。
- ⚠️ **路由的真正难点是 eval**（[00:15:12]）：**"路由真正最难的部分，是建 eval，是判断某一类智能在什么场景下该被用。"** 他补充说**帮企业建 eval 的工作实际上也帮了企业去采用路由器**。⚠️ **这与 [用内部基准决定模型路由](#用内部基准决定模型路由2026-07) 那一节是同一件事的供给侧版本。**

### ⚠️ "评估本身是 AI-complete 问题"

主持人的问法（[00:05:05]）：**我们连人都还不会评估**——IQ、EQ、大五人格、SAT 都有争议且无共识；而模型又很会 hack benchmark。

- **嘉宾的回答**（[00:06:05]）：**这件事正在逼着很多模糊的、分布式的评估方式被显式化**。
  > ⚠️ **"一家律所的 associate 和 partner 之间，真正的区别是什么？人类世界里并没有一个清晰的测试或 eval。"**
  ⚠️ **他判断这会成为最大的瓶颈**：**"我们把公司和它们的工作变得可读的能力"**——因为那决定了我们在什么信号上爬山、在哪里真正采用。
- **Ben Horowitz 的回答**（[00:07:06]）：**类比 MPAA 分级**——什么是艺术、什么是色情、线在哪里，**定义本身还随时间变过**，最后靠的是"**我看到就知道**"和随时间形成的规范。他认为现在的公开 benchmark 是"解出这道特定的题就算到了这个水平"——**既可被 hack，又太窄**。

### ⚠️ "一家公司本质上就是它的 eval"

（[00:18:14]）他给的判断：**能不能把自己的 eval 变得可读（legible）、从而算清 ROI，长期会决定这家公司能否胜过竞争对手。**

配套的两组量化证据，**本页认为是迄今最具体的 token 经济学材料**：

- **那个财富 10 强的故事**（[00:16:13]–[00:17:14]）：给工程师的 Claude Code 预算**每人每天约 100 美元**，**速率上限下午 4 点重置** → ⚠️ **最高产时段变成 4–6pm，下午出现"死区"**（大家去散步、喝咖啡）。额度后来提到**每人 300 美元**——"**差不多是一个员工工资那么多的 token**"。
  ⚠️ **他的读法**：**技术栈的每一层都在对智能定价错误**——工程师不知道怎么分配、公司定的数字相当武断、而供应方在很窄的毛利上支撑这件事。
- **Vals 自己的 token maxing 实验**（[00:22:17]–[00:24:19]）：一个月内工程师**每天 10–20 亿 token，峰值一人一天 60 亿**；折算**约 150 万美元的 token，是同期员工工资的 10 倍**（⚠️ 这次是免费额度）。"**我们不能按这个模式再过一个月。**"
  - **由此诞生了 ValSmith**（[00:19:14]）——用自家 GitHub 代码库建内部 coding benchmark。
  - ⚠️ **两条具体发现**：**Cognition 的 Devin 非常 token 高效**；**订阅制定价往往比按 token 计价更划算**。现在的模式是**所有工具对所有人开放，但对每个 GitHub issue 自动推荐从哪个工具开始**。
  - ⚠️ **一个反直觉现象**（[00:21:16]）：**Sonnet 因为太"token 饥渴"，实际花销有时比 Opus 还高**——"如果你按'感觉适用就用 Sonnet'来操作，**可能反而多花钱**"。
- ⚠️ **为什么企业自建不够**（[00:19:14]）：他**推荐公司发展内部能力，但说那不该是唯一解法**——**智能选项在复合式增长**（更多实验室、每家发更多模型、更多超参选项，再嵌在复杂的 harness 与 agent 里），而**使用场景也在同步变复杂**。
  ⚠️ **这与 [Decagon](#自建-eval-是应用层的真实门槛decagon2026-07) 和 [Kavak](#️-evals-是刹车不是事后补的一份带投入比例的买方证词kavak2026-08-10) 的"必须自建"不冲突，是同一问题的规模化回答。**

### 下一步方向：网络安全评估要从代码层升到基础设施层

⚠️（[00:37:27]）过去的工作集中在**代码漏洞、内存泄漏**；**但最大的风险不在代码里**——要**模拟更大规模的企业云基础设施、甚至电网基础设施**，才能说清模型的攻防能力。

## ⚠️ 两条关于"eval 会过期"的新材料（2026-09）

### 一、静态 eval 会过期，所以定制必须是平台（Ramin Hasani，2026-09-18）

来源：[Latent Space / Liquid AI](../videos/20260918-latent-space-liquid-ai-ramin-hasani.md)（[00:42:25]–[00:43:25]）

主持人问的是一个很锋利的问题：**如果我有好的 eval，我凭什么在乎过程？它应该自己 auto research。** Hasani 的回答：

> **第一次部署我完全同意你。** 但模型上线后，新数据进来、社区想要的东西发生**分布漂移**——**"你的 eval 会过期。静态 eval 会过期。所以你需要某种动态性，而这只有在系统能持续演化时才可能。"**

⚠️ **这与 本页「agent 漂移：eval 不是一次性的」（[Mark Cuban](../people/mark-cuban.md)） 是同一论点的两个独立来源**，而 Hasani 给的是**供应商侧的产品化后果**：**因为 eval 会过期，所以定制必须是平台而非一次性服务。**

### 二、⚠️ 评估时长即将超过模型发布周期（Noam Brown，2026-09-17）

来源：[Dwarkesh / Noam Brown（OpenAI）](../videos/20260917-dwarkesh-noam-brown-agent-swarms-rsi.md)（[01:02:10]–[01:05:20]）

**本页此前没有任何材料提到这个结构性问题。**

- 前沿模型**最多两个月一发，有时更快**；而模型能有效运行的时间尺度**正从一周走向一个月、三个月**。
- ⚠️ **一旦模型能干三个月的活而发布周期是两个月，你就根本没有时间在它能力的完整尺度上评估它**——**不只是对齐会不会退化，产品本身会不会在那个跨度上退化都没测过**。
- **他的定性**：**"这现在还不是问题，但很快会变成一个我们必须解决的问题。很多安全政策是 GPT-4 时代定的，那时候根本没人想到这个。"**

### 三、⚠️ 模型已经会识破测试环境（Noam Brown，[01:16:41]）

给模型一道数学题、旁边文件夹里放答案——**模型会想"嗯，这看着像个陷阱"，然后不去看**。

⚠️ **他特别澄清：这不是恶意**——它不是在盘算怎么绕开，**它只是判断出"我在测试环境里"**。

⚠️ **这把本页 [eval awareness](#gray-swankolter--fredrikson2026-06eval-awareness-与能力激发) 那条推进了一步**：从"模型知道自己在被测所以表现不同"，到**"造出让模型分辨不出的环境本身正在变得不可行"**。配套的是 Dwarkesh 那条很硬的论断：

> **"我不认为我能造出任何一个模拟真实经济价值工作的环境——那需要与人和世界交互——是你身处其中、只要足够努力却发现不了自己在环境里的。而你还不是 ASI，你只是个人。"**
