# 开源基础设施与治理

> AI 时代的公共软件底座**由谁维护、靠什么钱撑住、被谁决策**。本库此前的开源讨论集中在"开源模型 vs 闭源模型"（见 [中美 AI 生态对照](china-us-ai.md)）；本页处理的是另一层——**开源基础设施项目本身的组织学**。

主要素材来自 [游凯超（vLLM / Inferact）](../people/you-kaichao.md)（2026-07），辅以 [志鹏](../people/zhipeng.md)、[vLLM Omni 团队](../people/vllm-omni-team.md)、[朱邦华](../people/banghua-zhu.md)、[江鋆晨](../people/junchen-jiang.md) 的月球大叔系列，以及 [Peter Steinberger（OpenClaw）](../people/peter-steinberger.md)、[Gavriel Cohen（NanoClaw）](../people/gavriel-cohen.md) 的个人 agent 开源项目。

## 一、伯克利谱系：为什么重要的开源基建总从同一个地方长出来

来源：[游凯超访谈](../videos/20260728-zhang-xiaojun-you-kaichao-vllm.md) [00:38:57]–[00:39:57]

- **谱系**：BSD（操作系统）、RISC-V（芯片）、RAID（存储）、Spark、Ray、vLLM——共同点是**都由在读学生从 research project 发起**，再变成学生主导维护、社区壮大、最终成为工业界基础设施。
- **David Patterson 的"5 年关停论"**（2014）：每个实验室/研究中心只做 5 年就够了，因为**5 年恰是博士生毕业周期**。伯克利由此一脉相承：**AMP Lab（→ Spark）→ RISELab（→ Ray）→ Sky Computing Lab（→ vLLM）**。
- 游凯超的推论：**"实验室的 5 年周期和工业界的需求周期一旦共振，就会诞生一些重要的项目。"** 他 2023 年正是据此判断 vLLM 是下一个，并主动申请去伯克利。
- **副产物：这套机制也决定了项目不能挂靠学校**——实验室按设计就该 5 年关停，"**所以实验室不是一个具备这样资格的实体**"（[01:04:41]）。

**谁适合维护开源项目**（一条很具体的人力经验，[00:41:01]–[00:43:02]）：低年级博士生急着开新方向发论文；博士后期急着找工作；**最合适的是博士中后期、无毕业压力、又对开源有兴趣的人**。这实际上意味着开源基建的核心人力供给来自一个**极窄且不稳定的时间窗口**——这也直接通向下一节的问题。

## 二、开源社区撑不住工程：三个具体约束

来源：[游凯超访谈](../videos/20260728-zhang-xiaojun-you-kaichao-vllm.md) [01:34:20]–[01:37:25]

本库对"开源可持续性"最有说服力的一段——**不是理念之争，而是三个卡死工程的现实约束**：

| 约束 | 内容 |
|---|---|
| **人力不确定** | 参与者来去自由，"**没有办法支撑你长期做一个重要的 feature**" |
| **法务：无主体可签 NDA** | vLLM 常做新模型/新硬件的**发布前**支持，对方法务要求保密协议——但"**开源社区它不是一个实体**"，谁来签？对方还会追问"这次是这些人、下次是另一些人，里面有没有我的竞争对手" |
| **算力：从"一台机器"到"一个集群"的断层** | 2024 年模型小，单机单卡能做很多事，也有公司捐机器；2025 年**很多优化必须是集群级**，"**他给我一台机器已经是顶天了**"。只能"各处乞讨"：花一个月劝人给机器，拿到后马不停蹄用（一个月到期），而且随时可能被收回——"甚至通知你说接下来一个小时我马上要用" |

> 游凯超对那一年的自评罕见地直白：**"我们 25 年其实我觉得说实话，我们做的不是很好。"**

**这三条恰好构成了"必须成立公司"的完整论证**，也解释了一个此前本库未处理的问题：为什么一个 GitHub 上最活跃的项目仍然会撑不住。

## 三、基金会 + 公司的双层结构

来源：[游凯超访谈](../videos/20260728-zhang-xiaojun-you-kaichao-vllm.md) [01:02:37]–[01:08:47]、[01:44:29]–[01:47:30]

vLLM 的解法是**两件事同时做，且顺序是先捐后开**：

- **捐给 PyTorch 基金会 = "保险杠"**。基金会是独立法人（可注册商标、有法务、可接受募捐），但**不参与技术治理**，"代码什么的其实还是自己要写"。真正锁死的是**商标**——"**你不能把 vLLM 闭源了之后，然后再说我支持 vLLM 项目**"。
- **公司（Inferact）= "支柱"**。Ion Stoica 的历史类比：**Linux 需要 Red Hat、Kubernetes 需要 Google、PyTorch 需要 Meta、Spark 需要 Databricks**——"vLLM 的体量已经达到了前几个项目的体量，但是没有一个这样的公司在支持"。
- **为什么必须是创业公司而非大厂**：大厂会带来立场偏见，"**可能有别的大厂不服它，所以所有人不会跟它一起走**"。具体到 vLLM：Meta、NVIDIA、AMD 都在用也都投入资源，但"**他们之间可能本来就会打架，因为 Meta 是 AMD 和 NVIDIA 的客户**"，只能做参与者决策、做不了战略决策。
  - **一个失败的对照实验**：Simon Mo 曾试图借 Character AI 之力支持 vLLM（从公司抽人、要机器），结论是"**最终还是发现没有办法靠别人**"——公司里只能有一个小团队"**用爱发电**"，"你很难说服公司高层说我有一个正经业务的公司、然后我需要全力来支持 vLLM 开源项目的发展"。
- **两者为何不矛盾**：**"如果我们想做闭源的话，我们就可以自己去找家公司做了。"**
- **商业化反而增强社区**：有了公司才能签 NDA（"他们的法务也很开心"）、才能合规采购算力（此前"资金放在谁的口袋里都是一个问题"）、才能招人买机器。而且——
  > **"社区对一个开源项目的意见，并不是说他能在项目里面写多少代码，更多的是说这个项目能不能给他带来收益**——新模型发布时是不是又能支持了、新硬件发布时是不是又能支持了。"

**当下的议价地位**决定了冲突尚未真正发生："**我们不接这样的商业客户。我们现在是供少于求的状态**……所以可以非常爽快地拒绝我们不想做的事情。"（[01:46:29]）——⚠️ 这是一个**有时效性的前提**：一旦供求反转，社区与商业客户的冲突才会真正被检验。这是本页最值得跟踪的证伪点。

**商业模式**（[01:48:32]）：Endpoint Service（直接卖 token）/ BYOC（客户有机器、公司供软件）/ 生态合作，统一**按量收费**——"**我们不是技术外包，我们不是在售卖我们工程师的时间**；我们产生的价值取决于我们为你多产生了多少 token、为你的机器又节省了多少成本。"
- 与 [AI 商业化与价值捕获](ai-business-and-value-capture.md) 呼应：这是**基础设施层用"节省的成本"而非"投入的人时"定价**的一个具体样本。

## 四、分级治理与"仁慈的独裁者"

来源：[游凯超访谈](../videos/20260728-zhang-xiaojun-you-kaichao-vllm.md) [01:20:03]–[01:24:07]

- **结构**：4 位 BDFL（Simon Mo、Woosuk Kwon、游凯超、李卓翰 + Red Hat 若干）→ 十来个核心维护者 → 几十个 committer → **约 2000 名贡献者**；决策层每周碰一次。之上还有 PyTorch 基金会引入的大公司治理层（NVIDIA、AMD、Red Hat、亚马逊、Google），**"我们作为项目维护者的职责之一，也就是协调这些大公司之间的合作"**。
- **"独裁"的实例**：把 **beam search 基本从引擎中删除**——推荐系统用户持续抱怨，但主流 workload 的推理形式已不适配它，"**如果持续维护它，只会给模型和推理引擎的适配带来越来越多的复杂性、不可维护**"。其余多体现在优先级：优先大集群上的大模型，**几百兆的小模型不列高优先级**。
- 一句概括：**"最大的挑战就是你要梳理事情的优先级，要做什么，更重要的是不做什么。"**
- **创始团队的不可替代性**：被问及有没有"换过领导还发展很好的开源社区先例"，回答是 **"我觉得换过领导之后，这个项目基本上就很难发展得很好了。"**

## 五、⚠️ AI slop：开源的基本假设被打破

来源：[游凯超访谈](../videos/20260728-zhang-xiaojun-you-kaichao-vllm.md) [01:24:07]–[01:30:17]。**本页最具时效性、也最值得本库长期跟踪的一节。**

- 背景：2025 年 GitHub 统计中，**按贡献者活跃度排序 vLLM 是整个 GitHub 上最活跃的项目**。
- **2026 年 5 月**发现：**有培训机构提交垃圾 PR 来包装学员简历**——只要能合进 vLLM，学员简历上就能写"vLLM 项目贡献者"。
  > **"这对我们来说是一个非常大的变化，它彻底打破了我们对于开源社区的用户都是善意的这一基本假设。"**
- **应对**：引入认证机制、更重视知名机构的贡献、**拉黑机器人账号**（"10 分钟之内提交 20 个 PR，这种人一定是机器人……我们叫做 **AI slop**，完全没有营养的东西"）。

**由此推出的结构性预测**：
> "**代码变得如此廉价，以至于维护者花时间去看别人的 PR，不如自己让 coding agent 再写一遍**——然后他自己还有更多的 context 说我想让 coding agent 怎么写。"
>
> "**未来开源社区的演进方向，会更多地掌握在机构和这些重要的贡献者手中，一些个人贡献者他能做的事情其实会变少。**社区会变成**维护者和用户**两部分：用户只需要提交 bug report 或 feature request，**你就不需要贡献代码了**。"

他认为这是**开源社区的整体方向而非 vLLM 一家**，并援引 **PyTorch 核心维护者 Edward Yang** 的同类表述（"与其花时间去看别人的 PR，不如我自己重写一遍"）。

### ⚠️ 本库内部的一处直接张力（不做裁决）

| | [志鹏](../people/zhipeng.md)（2026-05，vLLM-Omni committer） | [游凯超](../people/you-kaichao.md)（2026-07，vLLM 主库 BDFL） |
|---|---|---|
| 个人贡献者的位置 | **上升通道敞开**——"做 contributor 初期，你对仓库的贡献远小于你在贡献中学到的东西"；一年从零基础到 committer | **空间收窄**——代码廉价化，社区分化为维护者与用户 |
| 对新人的建议 | 改文档 → 抢 issue → 适配小模型，单卡可入门 | 认证机制、更重视机构贡献、拉黑疑似机器人账号 |

两条判断**相隔两个月、同出 vLLM 生态一线**，且并不逻辑互斥（志鹏描述的是已发生的路径，游凯超预测的是未来的分布）——但它们对"现在该不该劝人从贡献开源入门"给出的实践指导是相反的。本库两条并存。

## 六、AI 能不能接管开源维护

来源：[游凯超访谈](../videos/20260728-zhang-xiaojun-you-kaichao-vllm.md) [01:27:12]–[01:30:17]

- **对 [OpenClaw](../people/peter-steinberger.md) 的观察**（本库首次由另一个大型开源项目维护者评价其治理）：**"OpenClaw 感觉已经变成了纯 AI 治理的方式——AI 提交 PR、AI 来审、AI 来合并，已经变成了一个 AI 自治的社区。"** 但方向好坏"不是很好说"。
- **vLLM 为什么不能这样做**——理由不是能力而是**时间方向**：
  > "**我们做的很多事情，它不是来解决现有的一个问题，它很多时候是解决接下来将要发生的问题**——比如我们要支持接下来三个月内要发布的新模型。所以我们在维护代码的时候，脑海里还必须想着接下来三个月的模型、接下来半年一年要推出的新硬件要怎么支持。**所以这个项目维护的过程中必须是带着大量的个人 context 去做的**，这一部分目前还没有办法交给 AI。"
- **总体尺度**：**"AI 可以帮我们走完 90% 的路程，但是还有 10% 的关键的、画龙点睛的那一部分，是需要人来提供支持的——需要提前预判、顶层设计。"**
  - 与 [志鹏](../people/zhipeng.md) 的"编程在编两样东西"（实体 code 会被取代，**脑海里的架构心智模型**暂时不会）是同一判断的两种表述；也与 [AI 与就业](ai-and-jobs.md) 中"人的价值转向 verifier/设计决策"一致。

## 七、开源基建的长期投入问题

- 游凯超举的反面教材：SSH/SSL 一类的基础加密设施长期"就只有那么几个人在自己维护"，直到十多年前一次漏洞事故"导致可能全世界都在裸奔"，之后才有人成立基金会注资。
  > **"开源基础设施建设一直是老生常谈的话题——它们都很重要，但是直到它们出问题之前，大家都觉得不需要投入。"**（[01:31:17]–[01:33:19]）
  - ⚠️ 转录作 "OpenSSH"，但所述事件（漏洞致全球暴露 + 事后成立基金会注资）与 **2014 年 OpenSSL Heartbleed 及随后的 Core Infrastructure Initiative** 吻合，疑为口误或转录误识。
- **对照 vLLM 的运气**：它是**在出事之前**就拿到了资金与组织结构的少数案例——2023 年就有基金给项目本身几十万美元级资助，2024 年 Sequoia、真格以捐赠形式支持开源社区，2025 年底成立公司时"**其实我钱已经准备好了**"（[01:38:25]–[01:39:26]）。

## 八、与开源模型之争的关系

本页处理的是**基础设施层的开源**，与 [中美 AI 生态对照](china-us-ai.md) 中的**模型层开源之争**（美国是否该封杀中国开源模型、蒸馏、权重 vs 输出）是两个不同的问题，但有一处交叉值得记：

- 游凯超给出的事实是——**"每一个模型的发布背后都跟着 vLLM 的支持，每一个芯片厂商都会主动来靠近 vLLM"**（[01:40:26]）。即**中美两侧的开源模型共享同一个推理底座**。
- 这为 [姚顺宇](../people/yao-shunyu.md)"知识已无秘密、纸面趋同"补了一层机制性解释，也意味着模型层的开源封禁讨论**绕不开一个中立的、由基金会持有商标的公共基础设施**。本库尚无 KOL 正面处理这一交叉，留作待跟踪问题。

## 九、⚠️ 一条与"开源正在赢"叙事相反的机制（Decagon，2026-07）

本库关于开源模型份额的记录长期在两条线上拉扯：一条是 [Jason 的"OpenRouter 上开源份额已超 50%、自托管是不入账的暗 token"](../videos/20260724-all-in-open-source-ban-anthropic-copyright.md)，另一条是 [Sacks 的"心有余而力不足"](../people/all-in-hosts.md)（企业**想**多元化但大多**没有技术能力**建 token 路由中间件）。

[Decagon 那期](../videos/20260731-a16z-decagon-enterprise-ai-apps.md) 给了**第三种解释，而且是一条机制而非一个数字**（[00:08:02]）：

> "现在企业里虽然对开源有很多炒作，但**开源推理的份额其实在下降**。因为**大家在起一堆新用例，而如果你在起新用例，你当然会用前沿模型，直到它跑通为止**。"
> "但这些用例里有些会死掉，有些企业会说'好，我们要继续发布并推广它'——**一旦到了那个点，他们就有强烈动机转开源，因为便宜得多也快得多**。"

⚠️ **结构含义：开源份额是用例成熟度的滞后函数，不是一个单调趋势。** 在用例爆发期，开源份额**会被新用例稀释而下降**，即使每个成熟用例最终都转向开源。

**这条为什么重要**：

- 它说明 Jason 与 Sacks 可能在用**不同时点的截面**互相反驳——同一份统计在用例爆发期与成熟期会给出相反的方向。
- 它给"企业会不会自己做后训练"提供了一个**时间表而非是非判断**：会发生，但慢，因为难点不在决定用开源，而在 **eval**——"⚠️ **我们的 eval 极其针对我们自己，你不能拿一个公开 eval 集来顶事，我们必须自己造基准和 eval**"，再加上模型风险治理与安全流程的惯性，"一次只能起那么多用例"。
- 它也解释了**为什么应用层公司在这件事上有规模经济**：Decagon 转开源的动机是**延迟**不是成本（语音 agent 上线后延迟成硬约束，而"**前沿实验室确实有小模型，但你没法按你想要的方式控制它们**"），而且他们**只干客服这一件事**，所以为这个用例做微调的固定成本能摊薄——"**但如果你是那家企业，值得把宝贵的研究资源拿去调一个客服行为的模型吗？大概率不值得。**"

### 与"闭源必然更聪明"的对立

⚠️ 同期他们给了本库最强的一条相关技术判断（[00:05:00]）：

> "推特上这些辩论的权衡往往被说成：我们要非常贵的最聪明的模型，还是把它变笨一点换便宜？**我其实认为那是一个假的权衡**……**当我们微调更小、更笨的模型时，它们只是没那么通用，但在我们要它做的那个具体任务上，它们确实超过又大又聪明的 SOTA 模型。**"
> **"所以我们最后三样全拿到了：更好、更便宜、而且更快。"**

**现状数据（公司自报）**：**90% 的工作流跑在开源上**；剩下 10% 用闭源前沿模型做新项目与**开放式探索型任务**（如让一个 agent 去审阅一百万条对话、造出主模型的变体并比较）。

### "模型工厂"：开源的运维成本是持续的

（[00:09:02]–[00:10:03]）他们强调这**不是一次性工程**："我们不是建好一套开源模型然后就完事、两年后再回来看。"随着前沿能力变化会冒出新用例，所以他们**不断训练全新模型、淘汰不再相关的旧模型**；Decagon Labs 被定义为"**某种意义上的模型工厂——建它就是为了压缩'新模型出来'到'对我们任务有用的微调模型掉出来'之间的时间**"。

**这条对本页主线（谁来维护公共软件底座）的意义**：开源模型的"使用"和开源基础设施的"维护"一样，**真实成本不在获取，在持续跟进**——他们为此养了"一个**很贵**的研究团队"。

## ⚠️ 开源模型互相借零件：从口号到可操作（Baseten，2026-08）

来源：[Latent Space 访谈](../videos/20260803-latent-space-baseten-inference-engineering.md)（[Philip Kiely & Ali Taha](../people/baseten-team.md)）

本页此前的"开源优势"论证多在**治理与商业模式**层（基金会+公司双层结构、Decagon 的模型工厂、开源基建靠谁撑住）。这一节补的是**技术层最具体的一条**——开源的可组合性在推理服务商手里是**逐周落地的工程**，不是口号（[00:16:11]–[00:21:11]）：

- **给 GLM 5.2 装上 Kimi 的眼睛**：GLM 5.2 没有视觉，于是把 **Kimi 的视觉编码器嫁接过来**。做法是**编码器冻结、主干冻结，只训中间的投影层**（仅几百万参数）——"**眼睛是冻的、大脑是冻的，我们只是在训练眼睛和大脑之间的连线**"。训练从"描述这张图里有什么"起步，后来改成**每张图配一组问答**（"图里有没有鸟？有没有科学家？"）才真正 grok。
  - 结果：**MMLU Pro 约 56%**，"不算前沿，但**你的 GLM 5.2 质量一点没损失**——没有图片时它的行为与原来完全一致"（推理时直接跳过编码器即可）。⚠️ 连误答都保留了结构："给它 Stephen Hawking 的照片，它可能说是爱因斯坦——**它仍然理解这是一位有重大成就的男性科学家**。"
- **换掉低效的层**：MiniMax M3 的头用**全注意力**，导致投机解码时 KV cache 极大、n² 瓶颈严重；于是**把这一层换成另一模型的 GQA 层**，再"用对的训练"把接收率训回来。
- **本节的收束句（Philip）**：
  > "**你突然就有了 Kimi 的视觉、GLM 的权重、DeepSeek 的注意力，全在一个模型里。这就是开源的力量与美——你可以把这些不同组件组合成一个比任何单独一个都更好的系统。**"
- ⚠️ **但代价被同时说清了**：这类改造的难点**全在训练**——"如果某一层低效，替换是很可能也很必要的，**挑战在于你怎么保证训得对**"。这与本页 [Decagon 的"模型工厂"](#模型工厂开源的运维成本是持续的) 是同一条结论的两种表述：**开源模型的真实成本不在获取，在持续跟进与再训练能力**。

### ⚠️ 一条分模态的限定：开源在视频上远没有赢

本页与 [AI 商业化与价值捕获](ai-business-and-value-capture.md) 里的"开源商品化"叙事基本以 LLM 为样本。本期给了它一条重要限定（[01:14:45]–[01:15:46]）：

- **LLM 侧**："Kimi K3 已经几乎可比最好的闭源模型；**差距曾经是 6 个月，现在基本没有了**。"
- **视频侧**：差距是**天壤之别**，而且形成了**恶性循环**——"我可以让你花 10 美元生成一整部 3 小时电影，闭源要 1000 美元；**我便宜 100 倍，但那还是 1000 美元，媒体公司还是会用闭源做全部镜头**"→ 需求少 → 创新少 → 开源 checkpoint 更少。
- ⚠️ **方向甚至在逆转**：原本发布开源模型的视频实验室**已把最新模型闭源**。

**本库标注**：本页此前记录的"开源正在闭合差距"是**文本模态的观察**，不应外推到生成式视频。这条同时记入 [中美 AI 生态对照](china-us-ai.md)——本期讨论的默认开源模型（GLM、Kimi、DeepSeek、MiniMax）全部来自中国，"支持新模型"在美国推理服务商的实践里主要就是支持它们。

## 十、同一个项目的另一侧：Simon Mo 的美方政策语境版本（2026-08）

来源：[a16z 访谈](../videos/20260806-a16z-simon-mo-open-source-inference.md)（[Simon Mo](../people/simon-mo.md) + Matt Bornstein）

本页此前的 vLLM 材料全部来自 [游凯超](../people/you-kaichao.md)（中方维护者、中文播客、组织学问题意识）。2026-08-06 这期是**同一项目的另一位 BDFL、在美方风投频道、面向政策语境**。事实基座高度重合，问题意识完全不同——**游凯超被问"开源社区靠什么撑住"，Simon Mo 被问"开放权重在中美政策战里站在哪一边"**。

### 交叉验证的三条事实

| 事实 | 游凯超（2026-07） | Simon Mo（2026-08） |
|---|---|---|
| 生态位 | "每一个模型的发布背后都跟着 vLLM 的支持，每一个芯片厂商都会主动来靠近 vLLM"（[01:40:26]） | 支持 **1000+ 模型架构**、**day zero model release**；NVIDIA/AMD/Google/Amazon/Intel 的新芯片确保 vLLM 能跑，"**很多情况下拿它当 benchmark**"（[00:08:03]） |
| 伯克利谱系 | AMP Lab → RISELab → Sky Computing Lab，David Patterson 的"5 年关停论" | "**我们来自 UC Berkeley，有很长的开源软件与系统研究传统**……开源是你能遇到最多使命一致的人的地方"（[00:31:21]） |
| Ion Stoica | "Linux 需要 Red Hat、Kubernetes 需要 Google、PyTorch 需要 Meta、Spark 需要 Databricks" | "**一直是开源优先**：我们需要造的东西尽量在开源里造，而我们能交付的价值是把最后一公里做完"（[00:36:22]） |

⚠️ **一处只有中方一侧留下记录的事**：游凯超提到 Simon Mo 曾试图借 **Character AI** 之力支持 vLLM 而失败（"最终还是发现没有办法靠别人"）。本期 Simon 本人没提这段。两条不冲突，但**失败记录只存在于另一侧的讲述里**——这本身值得记。

### ⚠️ 一条与"个人 context 不可替代"互补的论证：部署足迹不可替代

本页 [第六节](#六ai-能不能接管开源维护) 记的是游凯超的论证：vLLM 的维护必须带着**大量个人 context**（要预判三个月后的模型、半年后的硬件），所以交不给 AI。

Simon 给的是**另一个维度**（[00:26:16]、[00:28:18]–[00:29:19]）：

- 模型是在**给定硬件、给定架构**上训出来的，"**但一旦放到野外，每个人的集群拓扑和用例都不一样**"——
  > **"关键是你怎么把'一个用例'变成'几乎无穷个用例'。"** 有人往边缘设备适配，有人跑史上最大规模；要对**语音 agent** 可靠，也要对**编码 agent** 可靠。他称之为"**一整个村庄的事**"。
- **规模本身就是验证机制**：要抓住"**大约 0.00001% 的概率才出现的最后一批 bug**"，就需要尽可能大的部署足迹。"**事实上今天很多推理云和 API-as-a-service 底下用的都是开源推理引擎**，因为那里有太多经过实战检验的配方可以直接站上去。"

**两条合起来才是完整的**："这层为什么不能被一家公司闭源做掉"——**上游要靠个人 context 预判，下游要靠部署足迹暴雷**。

### ⚠️ 开源模型怎么养活自己：本页的第三种机制（许可证分层）

本页此前记录了两种：**基础设施层按 token 计费**（vLLM / Inferact）、以及 [Decagon 的"模型工厂"](#模型工厂开源的运维成本是持续的)（应用层自己养研究团队）。Simon 给了第三种，是**模型实验室自己的**（[00:19:14]–[00:23:15]）：

- **起点**：开放权重曾像软件一样是 **Apache 2**——"拿去改，随便你怎么用，这是给世界的礼物"。
- **转折与三个样本**：
  - **Llama**：日活或 ARR 超阈值须单独与 Meta 签商业协议。⚠️ Matt Bornstein 的一手补注：**"当时那些数字是特意挑的，你能查出来全世界大概只有两家公司符合他们排除掉的那个定义。"**
  - **MiniMax M2.7**：发布时带针对**使用方式**的条款。
  - **Kimi**：带**衍生作品**条款——"当时的大新闻就是 **Fireworks 和 Cursor** 关于他们怎么在 Kimi 模型上做二次开发"。
- ⚠️ **Matt Bornstein 的辩护是本节最该被引用的一段**：**"我不认为这是贪婪。"** 开源软件靠人捐时间、或大公司授权员工捐时间支撑，"**这在 AI 里根本行不通——我没法晚上回家跟朋友一起'为了好玩'训一个前沿开源模型**"，那要几百万甚至几十亿美元的算力。
- **Simon 的类比是制药**：怎么保证新药 R&D 得到可持续融资——因为知道药上市后有一部分收入回流去养下一轮。⚠️ **Matt 立刻指出类比的不对称**：一个分子一旦发布，"**你拥有最强的控制——别人根本没法制造它，那是最闭源的形态**"；而模型放出来任何人都能拿走、使用、扩展。

**这一节对本页主线的意义**：本页开篇问的是"公共软件底座靠什么钱撑住"。三种机制现在齐了——**基建层卖 token、应用层自养研究、模型层收分层授权费**。⚠️ 三者共同的前提是**没有一种靠捐赠时间维持**，这与本页第一节记录的伯克利学生驱动模式已经不是同一个时代。

### ⚠️ 一条对"开源份额"记录的收束

本页 [第九节](#九️一条与开源正在赢叙事相反的机制decagon2026-07) 记了 Decagon 的反直觉观察——**企业里开源推理的份额其实在下降**（新用例爆发期都先用前沿模型）。Matt Bornstein 从推理侧给的是方向相反却不冲突的观察（[00:07:03]）：

> "在任何给定时刻——**包括现在**——OpenAI 和 Anthropic 的模型总体上都比开源模型用得更广、更关键。但我认为我们在**大约一年前**跨过了一个门槛。"门槛是新的应用公司在解"我怎么不只是当 OpenAI 的壳"，"**这个问题的答案最后就是开源**"——因为需要自己的 mid-training、post-training、推理部署技巧，"**闭源厂商不会给你这种访问权限**"。**他点名 Cursor、Decagon、Harvey。**
> "**所以开源变得非常核心，而这件事并不总是可见的，因为它被深埋在这些产品里。**"

⚠️ **本库把两条合成一句准确表述**：**开源在"已跑通的用例"里是默认，在"新起的用例"里不是**——所以任何单一时点的份额统计都会因为统计口径落在哪一侧而给出相反方向。⚠️ 注意 Matt 点名的 Decagon 正是那条"份额在下降"的来源公司，两条出自同一频道、相隔 6 天，**这不是矛盾而是同一现象的两层**。

### ⚠️ 护栏误杀：开放权重的第四种采用动因

本页与 [AI 商业化与价值捕获](ai-business-and-value-capture.md) 此前记录的"转向开源"动因有三种：**成本**、**延迟**（Decagon 的语音 agent）、**数据主权**。Simon 给了第四种，而且是一条**一手证词而非行业观察**（[00:33:22]）：

> Inferact 与 vLLM 内部**很多开发者正在从 Fable 5 撤退**——他们研究 GPU kernel，"**哪怕只是一个 invalid memory access 报错，我们都在触发红线**"（前沿 AI 研究相关的护栏）。代价不可恢复："**你有一个两小时的任务，触发了红线（假阳性），然后你全部的工作就没了。**"于是"**很多开发者今天在用比如 Kimi K3，就因为它质量相近、护栏对我们来说是合理的**"。

**他由此推出的终局论证**（[00:32:21]–[00:33:22]）：如果**内容审核这个问题永远解不掉**（他认为会非常难），那么"**可信用例会默认走向开放权重，因为那是你确知护栏被削弱、或者护栏由你自己控制的地方**"。

⚠️ **这条为什么属于本页而不只属于安全页**：它把"谁维护公共底座"的问题推进了一步——**如果闭源模型在专业工作上系统性误伤，那么基础设施从业者本身会成为开放权重的结构性用户群**，而这批人恰好就是维护这层底座的人。完整记录见 [LLM 安全](llm-security.md) 与 [中美 AI 生态对照](china-us-ai.md)。

## 注册表这一层：谁在维护，以及资助缺口的量级（2026-08）

来源：[a16z / AI 正在学会黑客攻击](../videos/20260807-a16z-ai-learning-to-hack.md)（[Socket 的 "Fas" 与 Truffle Security 的 Dylan](../people/truffle-socket-founders.md)，Black Hat 2026 现场）

本页开篇问的是"公共软件底座由谁维护、靠什么撑住"，此前的材料集中在**推理引擎与模型层**（vLLM / Inferact / 伯克利谱系 / 许可证分层）。这一节补的是更下面的一层：**包注册表与其上的包本身**——而且是从**它被攻破时**的角度看。

### 现状描述

- **注册表大量由志愿者运行**（[00:06:03]，Fas）："我们喜欢盯着注册表，因为**很多注册表是志愿者在跑的，资源不足、资金不足，那里有很多风险，而这会向整个生态的其余部分级联**。"
- **包本身也是**："**我们都依赖的很多包背后是单个人。**几乎可以肯定——我们知道——软件里有很多漏洞，**而没有资源去找它们**。"
- ⚠️ **一个具体样本**：Truffle Security 在 **Ruby Gems** 发现过一个**缓存问题，可以窃取任意 token、拿到任意账号、给任意包装后门**。对方"很好合作，很快修了"，**但这正是一个资源不足的组织**（[00:19:09]）。

### ⚠️ 本页第一条给出量级的资助建议

（[00:19:09]–[00:20:09]）Dylan 问的是一个很实际的问题：一家公司选技术栈时，**该不该把"这个包管理器背后有没有安全团队"算进决策**？

Fas 的回答分两半：

- **换语言不现实**——"**很难让人因为这个就整个换语言，如果他们已经建在上面了。**"
- **可操作的那一半**：**"最可行的事情是大家应该出钱资助这些东西。要多雇一两三四五个安全人员，在这些基金会里其实花不了多少钱，但能带来非常大的差别。"**
  > **"不需要很多家公司各开 2.5 万、5 万美元的支票，就能给这些人带来很大差别。"**
- 主持人补的一条**本页此前没有的资助形态**："**或者给他们多点推理算力去跑测试、去打补丁。**"

⚠️ **这条与本页"许可证分层"那一节的关系**：Matt Bornstein 论证的是**模型层没法靠捐时间维持**（"我没法晚上回家跟朋友一起为了好玩训一个前沿开源模型"）。这里给的是**注册表这一层仍然靠捐时间维持、而且已经撑不住了**——但缺口的量级小到荒谬（几张 2.5–5 万美元的支票）。**两层的融资问题差了三到四个数量级，却都没有解决。**

### 责任分配：一条清晰但被自我限定的立场

（[00:17:09]–[00:19:09]，Fas）顶级 maintainer"**没有安全团队，没有企业 SLA，他们是志愿者，只是把代码放在 GitHub 上**"。因此——

> "**责任其实落在使用者身上，要去审自己在用什么。很难说'我们是家公司，我们在网上找到这段代码，直接部署到生产环境了，这是别人的错'。不是的，这些软件的用户对自己引进环境的东西确实负有一部分责任。**"

但他立刻加了限定：**"我不想把太多责任推到人身上，因为这是个难题。"**

⚠️ **本库标注**：这与本页此前记录的 [FFmpeg 维护者视角](../videos/20260506-lex-ffmpeg.md)（AI 批量生成的安全报告构成"对维护者的拒绝服务攻击"、激励错位）是**同一结构的两侧**——那边是**上游被外部安全流程压垮**，这边是**下游主张自己应当承担审查责任**。两条合起来给出的图景是：**报告与修复之间的鸿沟，不是靠把责任推给任一侧能解决的，而是缺一层被资助的中间人。**

### ⚠️ 强制 2FA：一条同时给出日期、机制与副作用的措施

（[00:16:09]，Fas）**npm 已宣布计划在 2027 年 1 月起要求任何新发布之前必须有人工交互式 2FA 确认。**

- **判断**："**那大概会彻底杀死整个蠕虫这个概念。**"
- ⚠️ **代价被明说**："**会极度具有破坏性，因为所有人都把这套接到自动化上了**（GitHub Actions 触发发布）。所以他们做这件事的时候基本上会**把整个生态搞坏**。**但我认为这是对的决定。**"
- **覆盖不到的部分**："还有其它**由志愿者运行、没有 GitHub 和微软背书**的生态，**它们大概不会做这些改动**，所以我认为我们还会继续看到这类事。"

⚠️ **这条对本页最重要的地方在于它揭示了一个此前没被记录的不对称**：**有大厂背书的注册表能承担"搞坏生态"的代价去换安全，没有背书的不能**。安全能力因此会沿着**资助结构**分层，而不是沿着技术能力分层。完整攻击面记录见 [LLM 安全](llm-security.md#防守方一线black-hat-2026-现场的供应链与凭证视角2026-08)。
