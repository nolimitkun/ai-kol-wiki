## 一、⚠️ "software factory"到底被定义成了什么：四个限定词

（[00:02:02]–[00:03:03]）

- ⚠️ **他自己的定义**：
  > **"一个云上的 agentic 系统，你在里面定义各种 agent 在为你的团队或产品构建软件这件事上分别扮演什么角色，而这个系统里有一定程度的自治性。"**
- **他紧接着加的三个限定，本页认为限定词才是这条定义的实质**：**"这个系统对我来说应该是非常可测量的、非常闭环的"**，而目的是**"随着时间你作为一个团队可以去调它、测它、给它做 benchmark"**，最终**"拿到信心"**。
- ⚠️⚠️ **而他说的误区，是本页认为这一期最有用的一处"词义澄清"**：
  > **"有时候人们把 software factory 理解成……不是一个具体的东西，而就是'我们大量用 agent 在发软件，我们把这个叫做我们内部的 software factory'。"**
  - **他的反对是把它变成一个可指认的对象**：**"不不不，你应该把 software factory 当成一个非常具体的东西——你应该用代码定义你的 factory"**，并且**"你应该能在某个时间点把它跑起来、然后测它表现得怎么样"**（[00:03:03]）。
- **两条结构性约定**：**"一个 product surface 对应一个 factory"**（[00:04:03]）；**factory 本身绑一组 repo、一组 skill、一组 MCP，加一条 workflow**，而**"这条 workflow 大致就匹配你的团队本来已经在怎么改这个代码库"**——**triage、写 spec、实现**（[00:04:03]–[00:05:03]）。✅ **载体是一个 YAML 文件。**

### ⚠️ 两类使用者，而这一期给的其实是其中一类的工具

- **他给的两个 persona**（[00:05:03]）：**做产品的人**——**"他们在做产品工程，他们通过 factory 发特性"**，而**他们用 factory 的方式是通过自己已有的工具**（Slack、Linear/Jira、GitHub、API 或 MCP）；**比喻是"你把一个工作项放进 factory"**，放进去就启动了那条预定义的 workflow（[00:06:03]）。
- ⚠️⚠️ **而 swyx 当场把演示的受众问出来了，本页认为这是全期最有校正作用的一次追问**（[00:12:07]）：**"我有点在想，是不是 Warp 其实有不同的层级——你给我们看的这个是 CTO 层级的？"**
  - **他的回答把范围收得更窄**：**"用这个的部分是工程经理或 CTO，但也非常常见地是平台团队……不是你那种日常的工程师。"**
  - ✅ **本页标注这条，因为它决定了本期所有内容的适用面**：⚠️ **这一期讲的不是"怎么用 coding agent 写代码"，而是"一个平台团队怎么度量并调优全公司的 coding agent"**。**他对那个团队要解决的问题给了一句很直白的概括**：**"我们怎么在我们公司里把 Claude Code（或者 Codex 之类）用到最好。"**

## 二、⚠️⚠️ 中央化的 trace：本期整套东西的前提

（[00:06:03]–[00:08:03]）

- **他说收益的来源是单一入口**：**"全都走同一个系统，这是关键的点"**，而第一个收益是**"你拿到全公司任何有 factory 的产品上、所有人在用 coding agent 做的事情的完整 trace"**。
- ⚠️ **他对这件事的定位不是看板，而是改进的燃料**：**"当我说闭环系统的时候，这些 agent 对话、这些 agent trace 就是这个系统怎么改进的关键环节。"** **trace 里包含完整对话记录、computer use 截图、以及编排 agent 各个环节分别在做什么。**
- ⚠️⚠️ **而他给的"为什么大多数公司没有"的理由，本页认为是本期最可被独立验证的一条行业状态陈述**：
  > **"在你们团队里，我跟公司聊的时候大部分都没有这样的东西，因为他们的工程师基本上是各自在自己的终端里用 Claude Code、或者用 Codex 的 app 之类，在自己本地的环境里。而他们想到的是一个有中央化的世界。"**
  - ✅ **本页的归纳**：⚠️⚠️ **他指认的缺口不是能力缺口而是**位置**缺口——agent 跑在个人机器上，于是公司层面没有任何可供分析的产物。这正好是本库此前多期材料的共同背面**：🔗 **[Arca 把员工每一次编辑或取消都变成一条 eval](20261031-latent-space-arca-agents-prompt-people-constrain-at-capability-edges.md)、[Coinbase 按团队/仓库/个人建 brain 且要求纠正必须写回](20260910-no-priors-brian-armstrong-agentic-finance.md)、[Legora 想做却被数据所有权挡住](20261102-latent-space-legora-cto-cant-see-the-traces-agent-as-api.md)——这些做法全都要求产物落在一个公共位置上，而本地终端恰好不是。**

### ⚠️ 他们实际在看的四类指标

（[00:08:03]–[00:09:05]）

- **① 传统 DORA 类**：**"发一个东西要多久"**。
- ⚠️⚠️ **② 自动化程度，而他给了一个本页认为很值得搬用的口径**：**"对每一个被 merge 的 PR，人类一共得对它动手几次。"** ✅ **本页标注这个口径的好处是它不需要定义"成功"——它只数人类介入次数，于是可以在任务类型高度不齐的真实工作流上横向比较。**
- **③ 吞吐。**
- **④ 成本，而他说这一条是客户最在意的**：**"我们跟公司聊的时候，成本这件事非常非常重要"**，目标是**"用对的模型、对的 skill 去调你的 factory，把每个 PR 的成本随时间降下来"**；**切片维度是按人、按自动化、按在 SDLC 的哪个环节花钱**。

## 三、⚠️⚠️ scorer：把 LLM-as-judge 常态化挂在真实运行记录上

（[00:09:05]–[00:11:06]）

- **他叫它 online eval 或 scorer**，**跨度从很泛到很具体**：**"你的 agent 是不是太啰嗦？它们效率高吗？代码质量好吗？"** ⚠️ **他对最后一项当场自嘲**：**"这块我们还有活要干。"**
- **开箱与自定义都有**，而**自定义的驱动力是客户自己的失败模式**：**"他们的 agent 可能有某些他们特别想追踪的具体失败模式"**，例如**"这个 agent 是不是在做某一类会把我们的构建搞坏的改动"**。
- ⚠️ **机制是对历史运行记录的追溯打分**：**"有一组 run——我说 run 的意思是被存下来的历史 agent 对话——然后一个 agent 去追溯地给它们打分。"**
- ⚠️⚠️ **他举的那个失败模式本页认为值得单独记，因为它是一个很具体的"agent 产生的技术债"**：**冗余测试**——**"有时候它们写一堆你不需要的测试。它们是在搞清楚怎么实现这件事的过程里写的，然后就把它留在代码里了。"** **后果他给了两条**：**"这就把你的代码库搞肿了，而且它浪费 token。"**
- **scorer 的配置项**：**选一个 judge 模型、选它在哪里跑、写判定用的 prompt、再加一个采样率**。⚠️ **采样率的理由是成本**：**"因为这些是正在跑的 agent，你得意识到它们的成本。"**
- ⚠️⚠️ **本页在这里标一处他没有讨论的事**：**整套 scorer 是 LLM-as-judge + 抽样，于是这套测量设施自身的可靠性与它所测量的对象是同一类问题，而本期没有涉及任何 judge 校准或 judge 漂移的处理。** 🔗 ✅ **这正好咬住 [Joseph Kim（OpenAI）那条"eval 的 bug 只在它让模型显得变差时才会被发现"](20261031-latent-space-openai-finance-joseph-kim-plugin-95-percent-taste-reward-model.md)——一套只在分数难看时才被审查的打分器，会把自己的误判沉淀成结论。本页不判定 Warp 是否有这个问题，只记它在本期未被问到。**

## 四、⚠️⚠️ 在自己公司的真实运行记录上做 benchmark：本库第一份具体做法

（[00:16:11]–[00:17:11]）✅ **本页认为这是本期最该被 [评估与 Benchmark](../topics/evaluation-and-benchmarks.md) 长期保存的一节。**

- **做法**：**"把你系统里跑过的任何一个 coding agent 加进一个 benchmark 套件"**——**"你可能会策展一组跟做前端之类相关的 coding agent 运行记录"**——**然后"把那些同样的任务，拿去对着一个由不同配置组成的矩阵重放"**。
- ⚠️⚠️ **而本页认为关键是被变动的维度有两个，不是一个**：
  > **"我是个坚定的信奉者——不只让你变模型，还要让你变 harness。所以在 Warp 里我们有我们自己的 harness，但我们实际上会让你对着 Claude Code、Codex 或者 Pi 去做 benchmark。模型你也可以挑。"**
- **产出形态他自己做了对照**：**"你最后拿到的结果看起来很像 SWE 或者 Terminal Bench 那种公布出来的结果，但是跑在你自己公司真实的运行记录上。"**
  - ⚠️ **坐标轴是成本对正确率**：**"你想在左上角——最低成本、最高正确率。"**
  - ⚠️⚠️ **他给的两个点，本页只取结构、不取型号**（专名不可确证，见页首）：**一档是 95% 正确、平均花 6 美元；另一档是 93% 正确、花 2 美元。** ✅ **本页记这组数的意义只在于它呈现了一个 2 个百分点换 3 倍价钱的决策形状。** ⚠️ **他自己也加了时效限定**：**"这些模型现在已经有点旧了，因为这世界变得太快。"**
- ⚠️ **下游用途是路由，而他把 harness 也放进了路由对象**：**"你可以把这个信息喂进一个模型路由策略，或者说实话是 harness 路由策略，而它是专门针对你自己的工作流和代码库定义的。"**
- 🔗 ✅ **本页标注这一节在本库里的位置，因为它把三条分散的材料收到了同一个形状上**：
  - ⚠️⚠️ **[Arca 用内部 harness benchmark 否掉外部 benchmark](20261031-latent-space-arca-agents-prompt-people-constrain-at-capability-edges.md)、[Eve 批评外部 benchmark 是维度错配](20261030-a16z-eve-plaintiff-law-supply-constrained-outcome-pricing.md)——两者都是买方说"公开榜单对我没用"；而这一期是把"那你自己建一个"做成了产品形态。**
  - ⚠️ **[Ali Ghodsi 那条"harness 本身值 2 倍成本"](20260918-a16z-ali-ghodsi-pacing-rsi-four-criteria.md)是一条孤立的量化，而这一期给的是产生这类量化的设施。** 🔗 **[Satya Nadella 的"模型 + harness"](20260915-all-in-satya-nadella-microsoft-ai.md)则是同一判断的口号版。**
  - ✅ **本页的归纳**：⚠️⚠️ **公开 benchmark 的替代品不是"更好的公开 benchmark"，而是把自己的历史工作变成可重放的任务集。而这条路径有一个前置条件——你得先有第二节那个中央化的 trace。两者是同一条链上的上下游，不能只要后面那个。**

## 五、⚠️ self-improvement：一条闭环，以及它承重点上那个明确的空缺

（[00:14:07]–[00:15:10]）

- **触发方式**：**另一圈 agent 盯着 scorer 的结果**——⚠️ **他自己插了一句"这年头什么都是 loop"**——**"它们在找你的分数里的失败、找那些跑得不好的东西，然后试着建议改动来让它变好。"**
- **他给的那个例子很具体**：**self-improvement agent 看了他们的 triage 环节，报出"我们有 54 个这种形式的失败案例——如果我们的 triager 当时能派一个子 agent 去做调查，会更好"**。
- ⚠️⚠️ **而闭环之所以能闭上，靠的是第一节那个"factory 定义在代码里"**：
  > **"因为你整个 factory 是以代码形式定义的，而这些是 coding agent，它们本质上可以直接对 factory 的定义提一个 pull request，来试着改进 factory 自身。"**
- ⚠️⚠️ **但验证环节他明确说还没有，而本页判这正是整条闭环的承重点**：
  > **"我们还没有这个，但下一步我们想用它做的是：对任何这样的建议改动，你可以回去重放那些运行，确认它真的会让它们变好。"**
  - ✅ **本页的判断**：⚠️⚠️ **没有重放验证，这条回路就是"一个打分器报出失败 → 一个 agent 据此改配置"，中间没有任何独立判据确认改动有效；而打分器本身又是 LLM-as-judge（第三节）。于是当前形态下它是一条建议回路，不是一条被验证的改进回路。** 🔗 **而这恰好是 [MakerMaker 那条"闭环 ≠ 起飞"](20261012-a16z-makermaker-rsi-numerator-denominator.md) 的一个干净样本：系统确实闭合了，但判据没有同步变硬。本页把本期归到那条判别式的"分母侧"——被优化的是工作流配置，而给出判断的仍是同一代模型。**
- 🔗 ✅ **另一条本页认为该并读的**：⚠️ **[Garry Tan 的"一个 markdown 文件就是一名员工"skillify 循环](20260812-a16z-garry-tan-founder-psychology.md) 是同一个动作的手工版——人从失败里提炼出 skill 写回文件；而这一期是让 agent 对定义文件提 PR。** ✅ **本页记：两者的差别不在自动化程度，而在谁来认定"这次确实失败了"。**

## 六、⚠️ 那个八层栈：本页认为是这一期最耐放的部分

（[00:19:13]–[00:26:19]）✅ **他反复声明这与用不用 Warp 无关**：**"不管是不是 Warp……一般来说，如果你想在这个领域里搭点东西，我会这么想。"**

- **① 底层：用代码声明式地定义 factory。** ⚠️ **他给的类比是 Terraform**，**"你拿到一样的好处，但其实更多"**：**版本化的视图、可以切分支去测、改坏了能 revert**；⚠️⚠️ **而他说多出来的那个好处就是第五节那条**——**"因为它在代码里，coding agent 可以对它建议改进"**。✅ **他的结论句**：**"所以对我来说，一个自我改进的 software factory 的地基就是——声明式地定义你的 factory。"**
  - ⚠️ **他对这个生命周期该叫什么公开放弃了命名**：**"SDLC、AI DLC、PDLC，你想叫什么 DLC 都行。"**
- **② 数据层：一个地方汇总 agent 产生的全部信息。** **要的是 agent 对话 + agent 产物**，而他强调的是跨工具的完整链路：**"一段 factory 对话可能从 Slack 开始，然后接到 Linear，然后接到 GitHub，还有一条 code review 评论，而这整段交互会产出某一块被 merge 的代码。"**
  - ⚠️⚠️ **用途是事后归因，而他举的例子跨过了发布边界**：**"它甚至可能导致某个东西上线之后服务器崩了，而你想能够追溯地回去——很可能是用一个 agent，但你也可以用人——去诊断这件事本来怎么能更好。失败在哪？"**
- **③ 数据入口 + 分权：** **要有插 MCP 的办法**；⚠️ **而他说规模一大就会要分权**：**"市场团队能访问哪些 MCP，和销售团队、和工程团队分别是什么"**。
- **④ 计算层，而他的主张是可插拔：** **"你真的需要一个计算层。你应该把它当成一个单独的东西。"** **他们主用 Namespace**，⚠️ **但他把可插拔说成架构要求**：**"如果你想用 Daytona、Modal 或者 E2B 之类，我会这么架构——让它成为这整个东西里一个可插拔的部件。"**
  - ⚠️⚠️ **而他给了一条很具体的"为什么平台种类重要"**：**"默认你大概想用一个 Linux 类的 sandbox，但对 computer use——比如我们测 iOS app 的方式——你会需要能跑一个 Mac VM，真的让它跑模拟器、点来点去。"**
  - 🔗 ✅ **本页标注这条与本库既有 sandbox 材料的关系**：⚠️ **[Modal 的 Akshat Bubna](20261022-latent-space-modal-rectangles-duration-transformation.md) 是从供给侧讲 agent sandbox 的弹性与经济性，而这一期是需求侧第一次把"sandbox 必须可换"写成架构原则，并给出了换的理由（宿主平台决定了能不能做 computer use）。本页认为两条合起来才是完整的一件事。**
- **⑤ 推理层，而他的理由是客户已有的采购承诺：** **"我们对推理的态度非常开放……我们发现现在很多公司跟 Anthropic、OpenAI 或者 Google 有已经签掉的额度，他们想把它烧掉。"** **于是支持自带推理供应商或从他们这里买。**
  - ⚠️⚠️ **而他把 harness 也列为可自带，并且自己说这是件大事**：**"你甚至可以插你自己的 harness，我觉得这挺大的。"** **口径是协议级的**：**"基本上任何 ACP 兼容的 harness。"** ✅ **本页记这是本库第一次看到有人把 harness 当成一个有协议、可替换的槽位，而不是产品的核心身份。**
- **⑥ 改进层**：即第三、四、五节那些东西。
- **⑦ orchestrator，而他专门把它降级了**：⚠️ **"有时候人们谈 orchestrator，谈得像它就是整个平台。我觉得它是其中一块。"** **职责是**：**把 factory 的定义代码拿过来，把工作推过各个阶段，调用对的模型、加载对的 skill，并触发对的自动化。**
- **⑧ 接入点，而他们的哲学是不另造界面：** **"把 factory 带进一家公司已有的知识工作工具里。"** ⚠️ **他给了一个自家的分布数字**：**"我们 60% 的工作是从 Slack 开始的"**，但也有从任务追踪器开始的，**也有"一个更习惯在终端里用 Claude Code 的开发者，在那儿做一堆活，然后把一份 spec 提交进 factory"**。
  - ✅ **形态上的结论句**：**"factory 自身就像一块 headless 的基础设施，它有这么多不同的入口。"**
- ⚠️⚠️ **他对这整层东西在栈里的位置给了一句定位，本页认为这是本期最该被 [AI 基础设施](../topics/ai-infrastructure.md) 记住的一条**：
  > **"这是开发者基础设施栈里的一个新东西。它比 CI/CD 所在的位置往后退一层，但我觉得大多数公司在软件开发上都会有这么一个东西。"**
- ⚠️ **而 swyx 在这里提了一条本页认为很到位的怀疑，并且它没有被真正回答**（[00:26:19]）：**"这其实有很多层。我在想，大多数……Cognition、Cursor，这些厂都在试着做一个从下到上的捆绑。"** **他的问法是买方视角**：**"我作为一家 B2B SaaS 的 CTO，我在这儿想干好我的活——我真的需要这全部六层吗？"** ✅ **而回答没有谈层数，直接转向了"这是给谁用的"（见下一节）。本页记这处转向。**

## 七、⚠️ 规模下限与反适配清单：本期最可被直接使用的一节

（[00:26:19]–[00:30:23]）

- ⚠️⚠️ **地板他给得很明确，而且方向是劝退**：**"它最能打动的必须是一家有一定规模的公司。如果你就几个人，说实话这是过度设计。"**
  - **swyx 接的那句本页照录**：**"别搞这个。用 Claude Code 的订阅或者 Codex 的订阅，你会更快。"** **而他同意。**
  - **数字**：**"我们开始看到大概 5 到 10 个工程师可能是这件事开始成立的地板。"**
- ⚠️ **甜区**：**"10 到 100 个工程师、快速成长的成长期创业公司"**，而**自助可行的条件是工具组合常见**——⚠️ **他把它叫做 "happy stack"（Slack + Linear/Jira），被 swyx 当场抓住反问"你刚才是不是管那个叫 happy stack"，他含糊了一下**。
- ⚠️⚠️ **反适配的那一类，本页认为比甜区更有信息量，因为他点了名**：
  > **"我们现在遇到困难的是那些基础设施非常非常定制的公司……我们一个不太合适的客户，比如说会是 Uber 或者 Ramp 这种——他们在造自己的东西，他们有非常大的内部开发团队。"**
  - ⚠️ **他另给了一条随规模上升的交付成本**：**"公司越大，这件事要的实施工作越多……要在一家公司自己的基础设施里把这样的东西立起来，不会是纯插上就能用的。"**
- ✅ **本页认为这一节有一条可以直接搬用的判据**：⚠️⚠️ **他画出的适配区间两头都是封闭的——下限是"人少到不值得建度量设施"，上限是"大到会自建"。而这个形状不是 Warp 特有的，它是所有平台层产品的形状；本页记它的价值在于它给了"什么时候该买、什么时候该自己写、什么时候什么都别建"一个有数字的参照。**

## 八、⚠️⚠️ 订阅套利：一条他自己说不清合规性、却被当成竞争格局前提的事实

（[00:30:23]–[00:33:24]）✅ **本页认为这是本期最该被 [AI 商业模式与价值捕获](../topics/ai-business-and-value-capture.md) 长期保存的一节，因为它把一条采购层的价差直接推导到了一整个品类的存亡。**

- ⚠️⚠️ **价差是 swyx 先给的**：**"很多人直接走按 API 付费，而那个比直接买一大堆订阅贵五到五十倍。"**
- ⚠️⚠️ **而 Zach 给的一手观察本页认为是本期最具体的一处现场事实**：
  > **"我们聊过的很多小公司是这样——他们说'这套系统看起来很棒，我们想要'，但我们现在是一堆 200 美元的订阅在轮着用。我是在十七个不同的订阅之间轮。"**
- ⚠️⚠️ **合规性他明确说自己不知道，本页照录，因为这正是这条材料的性质**：**swyx 问"这是不是严重违反服务条款，以至于根本不值得折腾"**，**他的回答是**：**"你没法想象那被允许。但我——说实话，我就是真的不知道。"** **而他同时承认它好用**：**"如果你能这么干，那确实会是最便宜的办法，但你会丢掉一大堆别的好处，而且它不是一件可扩展的事。"** ⚠️ **他给了一条到期条件**：**"如果你公司规模到了某个点，你肯定不会被允许这么做。"**
- ⚠️ **补贴幅度 swyx 给了一个口径**：**"一个 200 美元的套餐，你拿到 8,000 美元的 API 额度。"** ✅ **本页标注这是主持人自述的估算、无来源，但两人一致认为它是目前最大的一个结构性扭曲。**
- ⚠️⚠️ **而他由这条价差推出的，是一条关于自己不进哪个市场的判断，本页认为这是一条很罕见的"由采购经济学直接推出产品边界"的自述**：
  > **"从生意角度讲，这是我不想待在纯 coding agent 这门生意里的原因之一。你没法在一个贵这么多钱的东西上面做出一个有竞争力的 coding agent。这就是现实。"**
  - **他对自己定位的表述**：**"Warp Factories 的好处是我们其实不是在卖一个 token 转售产品。我们卖的基本上是一个 coding agent 优化平台、coding agent 生产力平台。"**
  - ⚠️⚠️ **他对 Cursor 的解读本页标为他的推断、不是事实**：**"Cursor 很厉害，他们做到了，然后我觉得他们有一个完美的退出，变成了一家模型实验室，因为我觉得他们完全看清了这件事的经济账。"**
  - ⚠️ **他对剩下谁还在独立做 coding agent 的点名**：**"基本上就是 Cognition 和 open code。噢，还有 Factory。"** **而他对它们的前景明确表示不知道**：**"我不知道它们要怎么做下去。"**
- 🔗 ✅ **本页标注这一节在本库里的位置**：⚠️⚠️ **本库此前关于"应用层会不会被模型厂商吃掉"的材料，论据几乎都在能力一侧（[Legora 的"他们永远不会做到我们这么深"](20261102-latent-space-legora-cto-cant-see-the-traces-agent-as-api.md)）或在数据/流程一侧。而这一期给的是第三类论据——定价结构**：⚠️ **当同一份算力在订阅渠道与 API 渠道之间存在一个数量级的价差，任何必须按 API 价买算力去转售的产品都在结构上无法与渠道持有者竞争。** ✅ **本页认为这条论证的强度取决于那个价差能持续多久，而他与 swyx 都没有讨论这一点——两人都把它当成了当下给定的条件。**

## 九、⚠️ product engineering 与 factory engineering：一条岗位二分

（[00:33:24]）⚠️ **这一段是他对即将做的 keynote 的预告，因此只有提纲、没有展开，本页照此记录。**

- **他说那场 talk 的问题是**：**"在这个 factory engineering 越来越多的世界里，当一个工程师是什么样子？你的角色是什么？你的工作会是什么？"**
- **二分本身**：**"两种工程是哪两种——product engineering、factory engineering。"** **而他把后者当作一门新学科来问**：**"factory engineering 这门新的学科（如果你想用这个词的话）实际上长什么样？工具是什么？"**
- ⚠️⚠️ **而落点那一句本页认为是本期最该被 [AI 与就业](../topics/ai-and-jobs.md) 记住的表述**：
  > **"你作为一个工程师要怎么练出对的技能，去工程化那个造软件的系统，而不是直接去造软件？"**
- 🔗 ✅ **本页标注它与本库既有材料的接口**：⚠️ **本库此前关于工程师角色变化的材料主要落在"从写代码变成审代码/定 spec"（[DHH 的三阶段](20260826-lex-dhh-agentic-programming-omarchy.md)、[徐天音的任务规约成本](20260822-uncle-moon-tianyin-xu-systems-agent-infra.md)）；而这一期给的是再往上一层的岗位——不是审那次输出，而是改那条产线。** ✅ **本页记：这是一条尚未被兑现的岗位预测，而它的可检验形态很清楚——平台/DevX 团队里是否会出现以调优 agent 工作流为全职的职位。**

## 十、⚠️⚠️ 本页记两处本期的空缺

### 一、整期的核心主张是"从氛围到测量"，而全部证据是自家演示里的自报数字

（[00:13:07]）**那条主张本身本页认为是对的、也值得保存**：

> **"你在 Twitter 上一直看到这个——你该试试这个新模型、你该用这个新 harness。到底哪个更好？是 Pi 还是 Claude Code 还是 Cursor？……这个世界需要的是把理解 coding agent 这件事从氛围的领域里拿出来，真正进到测量的领域里。"**

- ⚠️⚠️ **但本页标注一处方法论上的不对称**：**这一期用来支持"测量胜过氛围"的，是 80 → 15 美元、吞吐 +40%、revert 率未上升这三个由 Warp 自己采集、自己定义口径、自己公布的数字，没有任何外部可核验的部分。** ✅ **本页不因此否定这条主张——它在逻辑上不依赖 Warp 的数字；但本页把那三个数字记为立场陈述而非证据。**
- ⚠️ **特别是 revert 率那一条**：**"我们量了 revert 率，而它没有上升"**（[00:24:16]）——✅ **本页认为这是全期唯一一条质量侧的守门指标，而在成本降了 4–5 倍、吞吐升了 40% 的同时质量不退，是一个相当强的联合声明；本期没有给出这个指标的定义、窗口或基数。**

### 二、⚠️⚠️ 被明确问到"最强的反驳是什么"，而回答换成了"它不适合谁"

（[00:29:23]–[00:30:23]）**swyx 的问题措辞很清楚**：

> **"对于搭这一整套东西，最强的那个 steelman 批评是什么？当你遇到批评或者推回来的意见时，人们应该知道些什么？"**

- ⚠️⚠️ **而回答从第一句就换了题**：**"我会这么答——有一类经典客户，我觉得他们不适合上这个东西"**，内容是**规模太小、以及基础设施太定制（Uber / Ramp）**。✅ **swyx 还当场试图把题拉回来——"而且除了规模那件事之外"——但回答绕了一圈又回到"对非常小的团队来说，直接用订阅更经济"，并自己承认"这又回到规模那件事上了"。**
- ✅ **本页的判断**：⚠️⚠️ **"谁不适合买"是市场分层，不是对方法本身的反驳。而对这套方法本身，本页认为至少有三条他没有被问到、也没有自己提起的反驳，并把它们记为本期的空缺而不是本页的结论**：
  1. ⚠️ **测量设施自身的半衰期**：**factory 的定义、scorer 的 prompt、benchmark 的任务集都是围着当代模型与 harness 搭的脚手架。** 🔗 **而 [Legora 在前一天刚好给了这条的买方版本](20261102-latent-space-legora-cto-cant-see-the-traces-agent-as-api.md)——"直到最近，做真的很复杂的 eval 其实不太值得，因为模型就是都变好了"。✅ 本页记：如果那条成立，那么在成本曲线下行最快的阶段投入建一整套八层栈，本身就是一个可能判断错的时机决策，而本期把它当成了无条件正确的方向。**
  2. ⚠️ **中央化的另一面是它改变了被度量者的行为**：**"每个被 merge 的 PR，人类动手了几次"是一个会被优化的指标，而优化它的最简单办法是少动手。本期把该指标当作纯观测量。**
  3. ⚠️ **自我改进回路缺验证环节**（见第五节），**而这是他自己说出来的，只是没有被当作对"闭环"这个说法的限定。**
