### ⚠️ 对象存储正在重塑数据库，而这一段本页认为是本期最可核对的技术内容

（[00:14:07]–[00:15:07]、[00:27:11]–[00:28:12]）

- **Turso 的架构**：**SQLite 本身只有单写者**（它是个文件格式），**Turso 为 SQLite 建了 MVCC**，于是可以多写者。⚠️ **SQLite 的许可很特别，所以他们必须 fork**（最早是 libSQL）。
- ⚠️⚠️ **而他把一部分数据库创新归因到对象存储**：**"数据库领域的一些创新，其实是从对象存储那边正在发生的事里出来的。"** 具体是**S3 加了一批新特性，于是你可以开始把它当数据库用一点**；**11 个 9 的数据持久性**（⚠️ **他自己马上补了一句"那是持久性，不是可用性"**）。
- **两条具体的 S3 创新**（[00:27:11]）：**强一致性**（⚠️ **"他们免费做了这件事，直接给所有人推上线，就这么活了。什么？"**）与 **S3 Express**。
  - ⚠️ **S3 Express 为什么是 game changer，他讲得很具体**：**你通常先写本地盘，然后要批量落到更持久的地方；而在能向客户端保证写入之前，你必须先落到某个持久的东西上**——**S3 Express 的写入时间是 1–2 毫秒**，**"没 S3 那么持久，不是 11 个 9，但够持久"**（✅ **主持人概括为"ephemeral durable"，被确认**），**然后后台再搬进 S3**。
- **缓存层次（他列的）**：**内存 → NVMe 盘 / local attached（他说这两者等价）→ S3**。⚠️ **问"还需要 Redis 吗"，答案是**"是，还需要。这个（对象存储）远远不够快"**。
- ⚠️⚠️ **而他给对象存储划的边界本页认为是本节最有判断力的一句**（[00:15:07]、[00:52:25]）：**"在事务型数据库里你要做大量读写，所以这种情况下你大概不想在巨大规模上用它"**——**所以 Multigres（sharding）才是往 PB 级 scale up 的路**；**"一旦你在 OLTP 侧到了一定体量，你就需要 sharding，因为 NVMe 盘空间有上限；如果你需要把事务跨两台服务器切开，你基本上就得从对象存储去取，最终那会拖慢你的数据库。"**

## 二、⚠️⚠️ 声明式 schema：为 agent 改造既有基础设施的一个干净例子

（[00:58:28]–[01:01:31]，以及主持人片头 [00:02:01]–[00:03:01]）✅ **本页认为这是全期最该被 [在实践中用 LLM](../topics/using-llms-in-practice.md) 与 [LLM OS 与新计算范式](../topics/llm-os.md) 同时引用的一段。**

**公司形态的三段位移（他自己的讲法）**：⚠️ **"我们是作为一家 dashboard 公司起家的，那时候那是最好的 DX"** → **headless**（⚠️ **"headless 是我们某种程度上一开始就有的……你可以直接 API 驱动用 Supabase，这也是我们今年成功的原因之一"**）→ ⚠️⚠️ **"今年我们的大重点是从 dashboard 转向 code-first、git-native"**。

- **git-native 的具体形态**：**在本机启动一个 Supabase 实例时，你会得到一个 `supabase` 文件夹，它代表你的数据库**，**里面有所有函数、所有东西**。⚠️ **主持人问"这是个虚拟文件系统吗"，被纠正为"更像是基础设施即代码的一种表示"**；✅ **而且"这个今天就存在，如果你用我们的 CLI"**。
- ⚠️⚠️ **而声明式 schema 的理由必须照录，因为它是本节的全部**（[00:59:29]）：
  > **"一般你跟 Postgres 打交道的方式是：每做一次改动就往 migrations 文件夹里加一个文件，它是一份历史日志。好，这很好，这是行业标准。但你想象一下，把一个 agent 丢到一千个文件上，问它'这张表是什么形状'——它只能在一千个文件里猜。"**
  - ⚠️ **替代办法也被他否掉了**：**"它得重新编译它的……或者你得在本地把数据库拉起来、把 migration 跑上去、再去 introspect 这个数据库——但那太慢了。"**
  - ✅ **于是做法是把 `supabase` 文件夹里的 schemas 目录变成数据库的完全声明式状态**，**"我们把表、策略、数据库注释这些全都抓进了这些文件里"**；**发布一个新库 PG Delta，可以用在任何 Postgres 数据库上**。
- ⚠️⚠️ **而他给的那条关于 agent 的工作假设本页认为比实现更值得记**：**"我们知道 agent 大体上会在代码上操作。它们不想去触达任何别的东西。它们必须在文件系统上非常快地迭代。"**
- ✅ **主持人在片头给了同一件事一句反向注脚，本页认为它是本期最该被跨页引用的一句**（[00:03:01]）：
  > ⚠️⚠️ **"我现在差不多把 Supabase 的势头看成是在做 Postgres 开发的最后一公里——让 agent 能真正很好地用它。但美妙之处在于，它其实并不是关于 agent 的。是我们一直都需要这个东西。所以人类也一样受益，我真的很喜欢这一点。我不喜欢只为了让 agent 高兴而做事。"**
  - 🔗 ✅ **本页标注这与本库既有材料的接口**：**它与 [Matt Garman 的"agent 作为用户"](../people/matt-garman.md)、[Modal 的 "AX≈DX（余弦相似度约 0.9）"](20260708-latent-space-modal-agent-infra.md) 是同一主张的三次独立出现**——⚠️⚠️ **而本页认为这一期的版本最强，因为它附带了一个被改掉的具体行业标准（migration 日志 → 声明式状态），而不只是一句原则。**
- ⚠️ **他对"下一步是什么"的描述带一条个人实验**（[01:00:29]）：**"眼下我在试着只用手机做开发，而且做得相当顺"**，⚠️ **但他马上限定**："当然我知道背后在发生什么，所以我会把那些我知道它从基础设施角度必须做的事告诉它。" ✅ **他的外推是**："我们正在走向一个状态——你不需要是工程师，你有个想法，对你的手机、你的 dot 或者随便什么个人 agent 说'我要造 X'，一秒后你差不多就有了一个在线的应用可以自己迭代。"
- ⚠️ **而他自己说这正是他的两个未解问题**（[00:57:27]）：被问"如果有个水晶球会改变你怎么下注"，答案是**"开发将怎么进行，以及人们会开发什么。这两件事我想得很多。"**

## 五、⚠️⚠️ 企业侧只做 greenfield：对"coding agent 会解放遗留系统"的一次降温

（[00:41:21]–[00:50:24]）✅ **本页认为这是全期信息密度最高的一节，而且它与本库此前多条"AI 让迁移变得可行"的乐观判断正面相撞。**

### 销售方法：一个用对照组定薪酬的设计

- **前提**（[00:41:21]）：**"Supabase 是一家非常著名的 PLG 公司"**；⚠️ **"每一届 YC 批次有 60% 用 Supabase"**（⚠️ 自述）；✅ **"我们几乎全部注意力都放在成为一家 index company 上"**；⚠️ **"我们这里的榜样是 Stripe——他们是我们见过唯一一家经历了十年以上市场变动、还保住开发者喜爱的开发者工具。"**
- ⚠️⚠️ **而这套做法本页认为是本期最可直接迁移的内容**（[00:42:22]–[00:43:22]，⚠️ **全部数字为自述**）：
  1. **他们做的是 product-led sales，看的是 product trigger**（logo、正在 scale up、撞到限额、报错、付到某个金额）。
  2. **假设每周有 1,000 个 trigger，就给这 1,000 个正遇到问题的人发邮件，比如 500 个回了。**
  3. ⚠️⚠️ **不回的那一批被当成对照组**：**"结果他们月环比增长 25%。"**
  4. **回的那一批交给销售，而"你唯一需要做的事就是跟这些人打上电话、帮到他们"**（**因为有全部流量模式，所以能给销售一份脚本，"AI 在这件事上帮了大忙"**）：**"结果他们的账户增长 125%。"**
  5. ⚠️⚠️ **"所以那 100% 的提升量，就是我们给销售发薪酬的依据。"** ✅ **对照的是传统做法**："传统上你会说，跟这些人通话然后卖给他们，然后你拿全额 quota。"
- ✅ **本页标注这条为什么值得保存**：**它把"AI 辅助销售"从一句宣传变成了一个可检验的归因设计**——⚠️ **而本页同时标注它的弱点：对照组是自选的（不回邮件的人），不是随机分配的，所以 25% vs 125% 这个差里含有选择效应。**

### ⚠️⚠️ 为什么不做迁移

- **企业客户为什么来**（[00:43:22]）：**"通常是因为他们想启动很多很多数据库"**；⚠️⚠️ **"而几乎从来不会是把他们的生产数据库搬过来。"**
- ⚠️⚠️ **而这条是本节的核心论断**：
  > **"我们在创业之初的核心论点就是：我们看过的每一家 Postgres 公司、每一家数据库公司，过去试图靠迁移来做的，随时间都失败了。你就是没法说服人迁移。"**
  > **"即便你造出一个更大、更好、更可扩展的 Postgres——你要做的是第一天就落到他们那里，然后确保他们待到第 1,000 天、第 10,000 天。"**
- ⚠️ **五年的战略取舍他讲得非常明确**（[00:44:22]–[00:45:22]）：**"未来说五年，我们在企业侧几乎全部精力，都是确保我们能接住 greenfield 的用例"**；**Multigres 当然给了他们接大负载的机会，"但它不会是我们的核心重点之一，至少未来五年不是"**。⚠️ **"我保证他们几乎永远不会迁。"**
  - ✅ **而他给的"为什么 greenfield 在企业里反而变多了"是一条本页认为值得记的因果**：**"现在在企业里它反倒成了一个非常高频的用例，因为他们想让所有产品侧的人尽可能多地开发、创新。"**
  - ⚠️⚠️ **还有一条冠军角色的变化**：**"以前我们全部精力都投在开发者身上——卖给开发者、让他成为内部的 champion。现在我们有 CPO 跑来说'我过去十年都没写过代码，但因为 Lovable 和 Supabase，我现在在内部做了一大堆东西'——所以我们在 C 级有了 champion，而不需要围绕那里做一套很大的 motion。"**
- ⚠️⚠️ **而对"coding agent 会让你终于迁走遗留软件"这个判断，他们的反驳落在物理层，本页认为这是本期最该被跨页引用的一段**（[00:48:22]–[00:50:24]）：
  - ✅ **他们承认 AI 解决的那一半**：**"让 Oracle 这么黏的一件事，是你最后会写出上百万行的 stored procedure，你把所有东西都塞进数据库里——而重写这些，今天其实确实容易多了。"**
  - ⚠️⚠️ **但接着是那条反驳**：
    > **"迁移的大部分问题其实不是重写。"**
    > **"问题在于，你的 OLTP 数据库通常在支撑你最产生收入的那个应用。所以一分钟停机就意味着实打实的钱没了。于是你最后得把两套东西并行跑起来，而这样的风险是你会得到 split brain——一些数据在这边、一些在那边。任何试过去对账 split brain 的人都知道，那是个非常难的问题。"**
    > **"所以 OLTP 这边的风险高得多，很多时候人们干脆就开始把负载拆开、起新的负载……然后希望有一天能把东西迁过来。"**
  - ✅ **他给了一个明确的反面对照**：⚠️ **"数据分析那边的迁移其实挺容易，从一个仓库迁到另一个仓库。"** ✅ **本页认为这个对照是这条判断最有用的部分——它把"能不能迁"的分界线画在了 OLTP / OLAP 上，而不是画在"AI 够不够强"上。**
  - ⚠️ **主持人的反方也照录**：**"我每天跟 coding agent 的人聊，那个大承诺就是你终于能从所有这些遗留软件上迁走……希望这意味着你能把一切切换过去。"** ⚠️⚠️ **而嘉宾的回答是"也许还没到"。**
- ⚠️ **"rip out Oracle"那条被当成愿景但不当成计划**（[00:47:22]）：**董事会成员 Karen 的论点是"你们不只是在替代 Firebase，你们也是新的 RDS"**（⚠️⚠️ **自动字幕写成 "Karen from CO2"，本库推测指 Coatue，但不写定**）；⚠️ **"大概一年前有人说，按收入算只有 5% 的 Oracle 负载跑在云上"**（⚠️ **转述的转述，本库不采信**）；✅ **而他的回应是**："听起来很美妙，我们当然自己也会去试，为什么不试？但它极其困难。"

## 六、⚠️⚠️ 开源的未来：rewrite in Rust 是"一次性升级"

（[01:07:36]–[01:10:37]）主持人的问题有两层：**大型商业开源的未来是什么**；以及⚠️⚠️ **"你们的依赖现在变成可选的了——你可以直接 vibe code 出任何你想要的东西。"**

- ⚠️⚠️ **回答的框架是"重写到哪一层为止"**：**"我觉得 rewrite in Rust 是一个有效的机制。"** ✅ **而他讲的那个内部对话很有用**：**团队里有人说"我在把我们做的所有东西都用 Rust 重写"**，**他的反问是"你要重写到什么层级？你要重写数据库吗？你要重写 Postgres 吗？"**
- ⚠️ **他给的限制是成本**：**"所以存在一层层的东西、你想重写到哪一层为止，然后你不想把你真正的创新 token、真正的 token 花在把一切都重写上。"**
- ⚠️⚠️ **而他的预测是收敛到一个赢家**：**"几乎每个工具大概都会塌缩进——比如说 Rust，如果那最终成了写东西的终极方式，因为它更快更正确。而在你做完这一轮迭代、所有东西都跑在这种高效语言上之后，你就不会每次都把所有东西重写一遍了。会有几个赢家。"** ⚠️ **他举的例子是 Postgres**（⚠️⚠️ **此处他说"Postgres 是用 Haskell 写的、很难维护"——事实错误，Postgres 是 C 写的；本页只保留论点结构**）：**"现在能用 Rust 重写吗？大概能。而那个功能仍然有价值，所以如果那发生了，大概会有一个 Rust 版的 Postgres fork，而它就是那个类目的赢家。"**
- ⚠️ **他们自己还没做**，**而且"很多东西是 Elixir"**；✅ **Elixir 的理由是 BEAM**（**"所以你开始想：在运维东西的时候，什么才是对的机制"**）。✅ **而主持人那句被接受**：⚠️ **"但现在你可以相当容易地换范式了，只要你能过掉所有测试。"** ⚠️ **"是啊，这是个好问题。我还没怎么想过我们会不会把 Elixir 换成 Rust。"**
- ⚠️⚠️ **而本节最该保存的是主持人引的那条第三方提议**（[01:09:37]）：**Vercel 的 Malte 的一条推**——**拨出一笔钱，把我们所有 C / C++ 层的依赖重写成 Rust**，**"因为我们就是知道那更好：更安全、更正确"**；✅ **主持人给它的定性是**：⚠️⚠️ **"而它是开源的一次性升级。"**
  - ⚠️⚠️ **嘉宾的回应是赞同 + 一条预测失败的理由**：**"作为一个想法我挺喜欢。但我不认为它会发生，因为人们就是喜欢自己来。"** ✅ **"不过作为一个想法，我们作为公司会 100% 支持它。"**

## 七、⚠️⚠️ mode collapse：担忧来自写了几十年代码的人

（[01:01:31]–[01:03:32]）✅ **本页认为这是全期最该被 [在实践中用 LLM](../topics/using-llms-in-practice.md) 引用的一段，因为提出担忧的人同时是这波浪潮最大的受益方之一。**

> ⚠️⚠️ **"作为一个已经写了几十年软件的人，你对软件该怎么造是有强观点的，比如持续集成、持续交付这些。我发现我自己在把我的观点推给 agent：噢，你应该用这种方式做。但现在越来越地——你不需要了。"**

- ✅ **主持人给了这件事一个名字**："mode collapse。"
- ⚠️⚠️ **而他讲出担忧的内容时，落点在行业文化上**：**"软件开发这个行业最棒的一点，就是那些著名的圣战——到底哪种做法才对。我们会不会失去这个？"**
- ⚠️⚠️ **接着是本节最该照录的那句**：
  > **"所以你想要观点上的多样性，这样最好的想法才能胜出。但接着，模型会让你懒到根本没人去看细节。然后它们就全都收敛到同一种造软件的方式——而这会不会是个局部最优？"**
- ⚠️ **主持人的回答分两层**：**① "这是个有效的恐惧，但我觉得这不在你的控制范围里"**；**② 分层**——⚠️⚠️ **"低品味的、姑且叫随意的 app builder，会收敛到那个均值、那个模型，也就是你们。但那些有鉴别力的高技能的人，会一直真的在意细节，而且他们应该在意。"** ✅ **他的机制是"然后它会逐层下渗"。**
- ⚠️⚠️ **而嘉宾的追问本页认为比主持人的回答更有力，因为它指向了这条机制的再生产问题**：
  > **"但这些高技能的人，还会继续被培养出来吗？"**
  - ⚠️ **主持人的回答是不确定 + 一条外推**：**"我不知道。我确实觉得人们足够有热情。"** ⚠️⚠️ **"我确实觉得一般的大学大概完蛋了——你大概不需要再上大学了，因为你大概可以自学、然后自己拿到工作。"** ✅ **他的依据是"一直都是这最顶层的一批人在推动很多事"**，而他们**"总会找到办法满足自己对'什么可能更好'的好奇"**——⚠️ **他举的例子是**"那种休一年假去 Recurse Center、就为了做些有意思的编程问题的人，哪怕他们本来能去行业里赚钱"。
  - 🔗 ⚠️ **本页标注这段与本库既有材料的接口**：**它与 [Alpha School 那期"两小时完成 85%"的讨论](20261027-a16z-alpha-school-two-hours-85-percent.md)、以及 [Lex #503 那位数论学家的"学你头脑能承受的最难最抽象的数学"](20261026-lex-math-crisis-quasi-rh-navier-stokes.md) 落在同一个问题上**：⚠️⚠️ **当工具把下限抬起来之后，上限那批人还是怎么长出来的。✅ 本页不裁决，但记下这是三期材料里反复出现的同一个未解问题。**

## 八、⚠️ AI 支出：本库目前最具体的一组横向数字（但口径全部由说话人自定）

  - ⚠️ **一条可迁移的教训**：**某次 launch week 每一个发布都上了 HN 首页，他发推晒了，然后被狠狠骂了一顿**——✅ **"给任何人的提示：永远不要截图你上了 HN 首页然后发到 Twitter 上，因为那看起来确实像——而且说实话，那就是在炫耀。"** ⚠️ **他们自述被 HN 管理员"因为一周里发太多东西"训过好几次**，✅ **而他们认为对方的顾虑是正当的**（**"他对 HN 和 YC 的关联有理所应当的偏执"**）。
- ⚠️ **两位联创"吵什么"这个问题他们答不出来**（[01:03:32]–[01:04:33]）：**"我们当然有分歧的时候，但只要另一个人稍微推一下，这个人就会说'好吧也许你对，我们试试'"**；⚠️⚠️ **"而且事实证明大部分那些东西其实根本不重要。只要大方向是对的，就还行。"** ✅ **他们自己给的解释是优先级**："它从来没重要到值得真的为它吵一架。而且我们也很忙，在处理业务的不同部分。"
- ⚠️ **配对方式与 Entrepreneur First 的一条反直觉**（[01:04:33]–[01:06:35]）：**两人（和主持人）都在新加坡的 Entrepreneur First，做着不同的公司，同期结束后留下来当室友**；**那栋房子里住了七个人，全是 builder、全是技术的**。⚠️⚠️ **"传统上，特别是在加速器模式里，作为技术的人你会被推着去和某个领域专家配对。但在我们住的那栋房子里，基本上七个人都是 builder、都是技术的人；而我们发现这种配对有效得多，尤其是做开发者工具的时候——因为作为开发者，你自己就是领域专家。"** ✅ **后来他们把那栋房子里大部分人都招成了员工**（⚠️ **跑 GTM 的 Rory 就是其中一个**）。
- ✅ **第一个全职雇员那条本页认为值得单独记，因为它是一条明确违背加速器建议的决定**（[01:06:35]–[01:07:36]）：**第一个全职 hire 是 Postgres 的首席维护者 Steve Chavez**；⚠️⚠️ **"YC 给你的建议是：我们会给你一笔钱，但别招人，最大的诱惑就是去招一个大团队。而我们去找我们的 partner 说'可是我们有这个人 Steve，他是 Postgres 的首席维护者'，他说：立刻招。忘掉那个建议，去把他拿下。"** ✅ **而雇佣条件更值得记**：**"我们招了 Steve，然后跟他说：别管 Supabase，你就继续建 Postgres、把它做得很棒。"** ⚠️ **后来 Steve 想扩团队时，他们就招了更多专门做那个项目的人。**
- ⚠️ **"operate"那一层主持人的概括**（[00:03:01]–[00:04:02]）：**更多上下文（更多日志、更多 check、更多连接）**、⚠️⚠️ **"给你的 SQL 配 markdown 文件，这太酷了"**、**knowledge 与 skills**、**以及自家的第一方 ETL**（✅ **他自己的判断是**："随着你 AI engineering 的职业走得越来越深，一般的 ETL 问题会越来越变成数据工程栈的一部分"）。
