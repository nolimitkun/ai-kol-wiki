## 一、这门课是什么：两次迭代之间改掉了什么

（[00:01:00]–[00:05:00]）⚠️ **课程代号 CS146S 不可确证，见页首。**

- **沿革**：**2026 年秋是第二次开课，第一次是 2025 年秋**；**课程构想起于 2024 年 11 月**，**"花了大概 9 到 10 个月"过委员会、写提案**（[00:02:00]）。✅ **他说参考了 Chip Huyen 开那门 designing machine learning systems 的流程。**
- ⚠️⚠️ **而两次之间的差别本页认为是本节最有信息量的一处，因为它描述的是一个领域从"扫盲"进到"有原则"的那一刻**（[00:04:00]）：
  > **"去年那一版……感觉更多是在做一次广度的巡游——这里是你能用 coding agent 的所有地方。很大一部分课程是为了曝光，是一种概览，一种奥德赛式的穿行：嘿，你以前知道的关于 SDLC 的一切，现在都因为 AI 在变。"**
  > **"今年，我觉得有些原则正在固化下来——非常仔细的 context engineering 这个想法，以及真正把设计和架构想透、当作处理极复杂任务的手段。"**
- ⚠️ **他对去年那种形态给了具体的失效原因**：**去年九个作业是"我自己想出来的教学式练习"，例如"这儿有个 repo，用一个 AI code review 工具去提一条 review，然后看它为什么好、为什么不好"**，而问题是**"说实话相当容易，我觉得很多人可以直接一次就过"**（[00:10:06]）。
- ✅ **定位他说得很明确，本页认为这条限定决定了全期内容的适用面**（[00:04:00]–[00:05:00]）：
  > **"这门课的性质是——它不是给初学编程的人上的。它不是传统计算机科学（算法那类）的替代品，事实上很多那种课是我这门课的先修。"**
  - **他把它说成实践者的课**：**面向"学生毕业后、刚进入职场时，怎么成为职场里最有产出的成员"**。
- ⚠️⚠️ **而他给学生的那条"地板抬高了"的说法本页认为很具体，值得与本库就业线的材料并读**（[00:06:01]）：
  > **"地板高多了。所以你是作为毕业后的第一份工作进来的，但只做到一个（比如用 Google 那套分级的话）L3 是不够的。你一般得比那个好，几乎要到 senior 的水平才进得去。"**
  - **他对这件事的回应方式是能力论而不是安慰**：**"一个受过良好训练的 AI native 工程师……可以是任何公司能有的最有用的资产之一"**，✅ **而他说这是第一周第一堂课就讲的话**：**"每一家公司都需要你们。"**

## 二、⚠️⚠️ 把作业改成开源贡献：本库第一条针对"品味断层"的机构级处方

（[00:10:06]–[00:13:06]）✅ **本页认为这是本期最该被 [AI 与教育](../topics/ai-and-education.md) 长期保存的一节，因为它正面咬住了那一页标为"本页最硬的一个问题"的那条断层。**

- ⚠️ **触发这次改版的是一条课堂调查结果，本页认为它本身就是一条可引用的现状描述**（[00:10:06]）：
  > **"我周二调查过的每一个学生——没有一个人还真的在手打代码了。所有人都在用 coding agent。而这些是 Stanford 的大二、大三学生。"**
  - ⚠️ **而 swyx 当场追问市场占比，他答还没问**：**"我还没调查，但这是个好提醒。"** ✅ **本页记这条缺口——全期唯一一次接近"学生实际在用哪个工具"的量化机会被放过了。**
- **credits 这一侧他讲得很细**：**学校层面默认已有各家的教育计划授权（他列举 Claude、Cursor，并猜测还有 Cognition）**；**而他额外去谈的是不让学生被 20 美元/月卡住**（[00:11:06]）：
  > **"我不想让大家被那个每月 20 美元的订阅卡住。如果你们想 token max 一下、就为了看看什么是可能的，那你们就该去。"**
  - ⚠️ **结尾处他给了这件事的上限**：**有赞助方说"如果他们想玩疯，告诉我，我们做几次一次性实验，让他们直接开到一千多个 agent"**（[01:59:04]）。✅ **本页记这是本库目前关于"单人并发 agent 数"最高的一个口径，但它是一次教学实验的授权额度、不是生产用法。** 🔗 **对照本库此前唯一的一手并发数据——[Peter Steinberger 并行 4–10 个](../people/peter-steinberger.md)。**
- ⚠️⚠️ **而处方本身的结构，本页认为关键不在"做开源"，而在他把**mentorship 的供给**接到了维护者身上**（[00:12:06]–[00:13:06]）：
  - **他先说出要防的那件事**：
    > **"我最担心的一件事是，如果所有人都在说……他们 cooked 了，那他们会怎么样？会有一种被落下的感觉。而我觉得 mentorship 是把所有人往上带、确保不会出现一条巨大裂缝的非常重要的一块——那条裂缝出现在已经在行业里待过、知道怎么回事、然后采用了 coding agent 变得很厉害的资深的人，和只能说'好，那我们现在干什么'的初级的人之间。"**
  - **做法**：**让学生在"我认为属于最好的那批 AI native 仓库"（本身就是 coding agent，或者是为 agent 造工具的项目）里做贡献，并把贡献作为作业的一部分**。
  - ⚠️⚠️ **而承重点是这一句**：
    > **"在做这些项目的过程里，你会真的在和维护者对话。他们会 review 你的代码。他们会帮你建立起关于什么是好软件的心智模型。这样一来，就有了一次把真正的好软件设计的接力棒传下去的过程——而我觉得大多数学生是没有机会做这件事的。"**
  - ✅ **他也说了功利的一面**：**"当然还有个好处是，我确信其中一些人会因为在这些作业里做得好而被挖走、被捞走。"**
- 🔗 ✅ **本页标注这一节在本库里的位置，因为本库此前该条线上的材料全部停在"没有解法"**：
  - ⚠️⚠️ **[徐天音明确说这是结构问题且自认无解](20260822-uncle-moon-tianyin-xu-systems-agent-infra.md)——"既然是有经验、有品味的人去指导 agent，那一个应届生怎么成为这样的人？这个训练与指导的过程没有了"**；**[John Platt 给的是同一问题的第二个提法](20260922-latent-space-john-platt-era-scorable-tasks.md)——"人怎么在不做那些苦活的情况下获得 taste"，而他的部分答案是"训练 vs 发挥"的时间分配。**
  - ✅ **而这一期给的是第三类答案，本页认为它与前两条的差别在层级**：⚠️ **前两条都是对个人的建议（学生自己要怎么练），而这一条是对**供给**的安排——它承认 review 与 mentorship 是稀缺品，然后去别处把它调来（开源维护者），而不是指望学生自学出来。**
  - ⚠️⚠️ **但本页同时标出这条处方的规模限制，而且它是结构性的**：**开源维护者的 review 带宽是一个远小于学生人数的量**，而**这门课能调到它，靠的是授课者个人花了一整个夏天去谈（他自述"我花了这个夏天的大部分时间去跟他们聊、让他们对这件事感兴趣"）**。✅ **本页判：这意味着它作为一门课的设计是成立的，作为一个可推广的制度则尚未被证明——而本期没有讨论可推广性。** 🔗 **这也正好是 [Alpha School 那一节](20261027-a16z-alpha-school-two-hours-85-percent.md) 的同类问题：单点有效、而承重的那个投入很难复制。**
- ⚠️ **第五十九分钟他给了这条设计的一个极端版本**：**OSS 伙伴之一会专门做一个"跑着 factory 的 Warp 版本"，让学生"就是在造那个 factory、给那个 factory 做贡献、让它一直跑着"**（[01:42:50]）。✅ **swyx 的一句玩笑把这件事的性质说清楚了**：**"在我们的工厂里打工。"**

## 三、⚠️⚠️ 那份十周大纲：一张"什么已经稳定到可以教"的清单

（[00:15:07]–[00:19:10]）✅ **本页按他自己的顺序照录，并标出每一周他给出的理由。**

| **2** | **规模化的 context engineering；工具设计与 MCP** | **"超出单纯的 vanilla prompting"**；⚠️ **"我仍然是 pro MCP 的……它已经是一个存在的标准，我觉得它会继续存在"** |

| **9** | **AI-native 团队** | **LLM gateway、MCP portal（"规模化的 MCP"）、以及"演化中的岗位"**——⚠️ **"到底哪个东西正在被吞掉，哪些角色在演化或者在新出现"** |
| **10** | **software factory** | **"一旦我们在造 factory 了，人还存在于哪里？那些被有意留下的人类介入的新咽喉点在哪里"**；**假设是"80%、90% 的代码完全由 agent 驱动"** |

- ⚠️⚠️ **而两位主持当场给大纲加的限定本页认为必须与大纲同等显著地记下来**（[00:20:11]）：
  - **swyx**：**"其中有些比另一些更是已成形的模式……人们需要知道，这里面不是全都是已定的科学。"** ✅ **他同时背书了清单本身**：**"但我会给所有这些背书，当作人们在谈的、你应该知道的东西——我们知道那些开放问题，只是可能还不知道答案。"**
  - **嘉宾自己的承认**：**"很大一部分课程内容相对去年变了，所以整个课程的发展有一种动态性。"** ✅ **他把这说成"设计上的特性，也许同时是某种 bug"。**
- ⚠️ **他对处理这种churn 的手法是把前沿外包给客座讲者**（[00:08:05]）：**"我不想声称我今天就有全部答案，那会是很大的自负"**，**于是结构是"一位实践者的聚合洞见 + 那些真的在前沿、看到更远东西的人把他们的世界观摆上来"**。
  - ⚠️⚠️ **而 swyx 在这里划了一条本页认为很有用的课程质量判据**（[00:09:05]）：**他拿这门课与另一门"只有名字"的课做对照——"那就是一串名单，只有名单"**，**而这门课的区别是"他实际上也在产出东西——比如 200 行的 Claude Code，而这是没人会告诉你去做的事"**。✅ **他的归纳**：**"当你想在一个你能用得上的框架里教基础、教一种能工作的理解，这就是你要做的事。"**
- ⚠️ **大纲之外他另给了一条本页认为最低成本、也最可执行的建议**（[00:21:13]）：
  > **"简单到就是每天实验 10 分钟。就花 10 分钟做一件你之前没做过的事……哪怕就是做同一个问题、只是换上那个新东西，光这一件事就能补上大部分的差距。"**

### ⚠️ 三个层级的教法：消费者 → 200 行基线 → 用 MITM proxy 拆开真货

（[00:25:15]–[00:28:17]）✅ **本页认为这是本期关于"怎么教"最具体、也最可直接复制的一处。**

- **他的判断是学生基本都是消费者**：**"大多数学生最后就是在用这些工具。我不觉得他们在课业里得到过任何把这层洋葱剥开的曝光。"**
- **第一层：200 行。** **他的论证是只需要入门算法水平**：**"你可以通过基本上入门算法级别的理解，就定义出一个 agentic loop，它能做你会称之为 coding agent 的大部分事情。"** **而他说规模是**：**"如果你想看到一个你能跟它说话、然后它真的会编辑你的文件、而你能用它做相当复杂的事情的东西——那不需要超过 200 行。"**
  - ✅ **他对这件事的教学理由本页认为值得单独记**：**"我在教育上很多时候想做的事，是把那些像秘方一样的东西剥掉，展示出它核心其实就是……Stanford 有门课叫 106B，入门算法。你不需要比 106B 更多的东西就能造出这样的东西。"**
- ⚠️⚠️ **第二层：拦截真货。** **第二堂课的做法是用 proxy 工具拦 Claude Code 的请求与响应**，**而对象是"两天前刚出的模型"**：
  > **"我拦截了那些请求，这里就是正在发生的一切——这是 prompt，这是 system prompt，这是 plan prompt，这是 compaction prompt。然后我们就把这些全过了一遍。"**
  - ✅ **swyx 的背书**：**"如果还有人没做过 MITM proxy 这个练习，你该做一下。你会震惊。"**
- ⚠️ **而他们在这里顺带给出的几条关于 system prompt 的观察，本页记为两人的一手观察而非厂商口径**（[00:29:18]–[00:31:18]）：
  - **swyx**：**"Claude Code 在所有 coding agent 里有最长的 system prompt，差不多两万 token。"** **嘉宾补**：**"不过他们也把体积削掉了 80%。"** **swyx 的归纳是"锯齿形"**：**"然后又长回来，又削，又长。"**
  - ⚠️⚠️ **而嘉宾给的那条变化的归因，本页认为是本期最该被 [LLM 实用方法论](../topics/using-llms-in-practice.md) 保存的一条机制观察**：
    > **"曾经是 system prompt 一部分的东西——比如怎么用 git，或者怎么设置任务这类——已经不在 system prompt 里了。它现在实际上被期待更多地被捕捉在模型里，在模型权重自身里。"**
    - **他把这推成一个选型问题**：**"这就提出了关于模型与 harness 的有趣问题，以及你怎么想这个权衡。公司该投什么？你自己该投什么，才能真正推动你自己能力的前沿？"** ✅ **他的现状判断是未定**：**"我觉得作为一个社群，我们在两者之间来回摇摆得很厉害。"**
  - ⚠️ **他对早期 Claude Code 为什么流行的解释是"少而强的工具"**：**"在早期他们是最早真正倾向于'让更少的工具做更多事'的那批人之一——倾向 SQL、倾向 Bash、倾向那些像瑞士军刀一样强的东西，并让它成为能力的很大一部分来源。"**
  - ✅ **swyx 给了一条用得上的推论**：⚠️ **"更弱、更老的模型，你需要给它们例子——这是好的、这是坏的。然后在某个时点你显然把那些削掉"**，**于是"如果你在用一个本地 coding agent、模型不是最强的，你可能需要加回这些例子"**；**而反向的代价是"随着模型变好，你什么时候会因为加了那些例子而过度约束了它"。**

## 四、⚠️ context engineering：RAPID，以及 sub-agent 那块两人都说没答案的地方

（[00:32:18]–[00:37:20]）

- ⚠️ **他对行业现状的描述本页认为是本期最可被独立验证的一条行业状态陈述**（[00:32:18]）：
  > **"即使在我面试人的时候我也看到这个——业界里非常少的人会进展到超出单纯的 vanilla prompting。就是'帮我做那个事'，对吧？而随着模型变好，那确实能带你走一段距离。"**
  - **他给的失效条件是代码库规模**：**"任何从 Google 这类有极大代码库的地方出来的人都知道，现实是你必须对你怎么把东西喂进 context 这件事思考得多得多。"**
- **他的框架叫 RAPID，而他自己做了对照**（[00:33:18]–[00:34:18]）：**"功能上类似 Dex 的 RPI"**——**research → proposal（给出几种备选解法）→ plan（也就是 spec）→ implementation → 用测试收口**。
  - ⚠️⚠️ **而他把人留在哪一步说得很明确，本页认为这是这套框架最实质的一处设计**：**"这里我也把 human in the loop 请进来，让人当那个在一种方案和另一种方案之间做决定的人。"**
  - ✅ **他给的适用规模**：**"TLDR 是，确实有一种做法能扩展到几百万行长的代码库。而它不是单纯的 vanilla prompt。"**
- ⚠️⚠️ **而 sub-agent 的 context 怎么处理，swyx 当场明确说自己没有答案，本页照录，因为这是本库少见的一次主持自认方法失效**（[00:34:18]–[00:35:19]）：
  > **"我现在对 context 的想法里最奇怪的部分，是当你切出一个 sub agent 的时候，因为 sub agent 可以从主线程继承你的全部 context，也可以不。……我不喜欢我现在做的任何做法。所以我没有任何答案。"**
  - **他说自己唯一确定的是扇出**：**"当你想把工作扇出去，它不再是一个 agent 了。它是关于扇出工作，并确保它们都有对的 context、都有对的指引。"**
  - ⚠️⚠️ **而他描述的那个"扩张—收缩"循环本页认为是本期最具体的一处失效模式**：
    > **"你总会经历这个扩张收缩的阶段——'天啊，这些家伙 context 不够，我得给他们更多 context'。好，很好。然后他们会对你很久以前随口说的某一条一次性评论过度调优，然后犯一些非常愚蠢的错，因为你不是那个意思，但他们当成了法律。"**
  - ✅ **他给这件事起了个没定下来的名字**：**"给 context 做的多 agent 管理。"**
- **嘉宾接的那一侧是"艺术多于科学"**：**"扇出去做探索、扇出去做子任务，然后再做合并、压缩，随便你叫它什么"**；**他引 Dex 的 "dumb zone" 概念——"对 dumb zone 要更有意识一点"。**
- ⚠️ **swyx 另给了一条研究方向的线索，本页记为可查证的研究指引而非结论**（[00:37:20]）：**AIE 上有论文研究 Claude Code system prompt 的 delta——"什么被改了，然后他们把性能的一堆变化画出来，试着反向工程它"**；**另有一篇看 context window 管理怎么影响下游性能**。✅ **他自己给了降权**：**"它们不是最好的论文，但相当容易上手……这是个你可以很容易扎进去的好领域。"**

## 五、⚠️⚠️ skills：两人都认为现在这个形态是对的方向、错的形状

（[00:37:20]–[00:46:23]）✅ **本页认为这一节是本期最该被 [LLM 实用方法论](../topics/using-llms-in-practice.md) 长期保存的一节，因为它罕见地包含一条来自重度使用者的"这东西该死"判断。**

- **嘉宾的定位是从工具到流程**：**skills 是"从单一的、引号的函数式 tool calling（比如 MCP，与第三方外部服务交互）延伸到你会称之为流程的东西"**——**"你怎么把某一组动作一遍又一遍地自动化，然后把它形式化成一个 skill.md 之类的东西"**。
- ⚠️⚠️ **而写 skill 这件事两人一致认为被低估了**（[00:42:21]）：
  - **swyx**：**"很多人在关注的是 skill 的消费……但不，你该自己写你的 skill。"**
  - **接着那句本页认为是本节的核心句**：**"而实际上当你天真地去写它们，它们通常是坏的。写一个 skill 其实需要一点 skill。"**
  - ⚠️ **他的做法是一个"剪刀 skill"**：**"Claude Code、Codex，它们都有创建 skill 的 skill。然后我有一个 skill cutter skill 把它剪短——它基本上就是把那些默认创建出来的 skill 坏在哪里的每一种方式都记录下来。"** ✅ **流程是每次创建后都跑一遍。**
  - ⚠️ **而他对"为什么不能直接扔掉 slop"给了一条很细的理由，嘉宾当场接住了**：**"有时候确实有 slop，但 slop 里有好东西，然后你得把它们筛下来。"** **嘉宾的复述**：**"即使是 slop，它仍然是在 agent 的语言里。所以那个 slop 是有意义的。"**
- ⚠️⚠️ **最具体的失效模式是误触发**（[00:43:22]）：
  > **"最糟的部分是当一个 skill 在你不期待的时候触发了。你某一次写它是为了修一件事，然后现在你在做一件完全不同的事，它触发了。为什么？因为它写得差——因为触发条件写的是'只要什么什么发生就叫我'。"**
  - ✅ **swyx 说有人在做园艺式的维护**：**点名 Eugene Yan**——**"他们对自己有多少 skill 很讲究。他们会剪枝。不用的，每几周清一次。"**
- ⚠️⚠️ **而 swyx 那条判断本页认为是本期最尖锐的一处，必须完整记下来，包括它的来源性质**（[00:44:23]）：
  > **"我怀疑——Anthropic 那边有一些非常聪明的人想让 skills 死掉。"**
  - ⚠️ **他自己标了这不是公开表态**：**"这不是个受欢迎的说法。不，他们不会公开这么说。"** ✅ **本页因此把它记为 swyx 的推测，而不是 Anthropic 的立场。**
  - **他给的理由是审美性的、而他承认这个理由对自己同样成立**：**"但它就是感觉很 sloppy。这感觉很 sloppy。而我知道——我能看到我自己的 skill 也在变 sloppy。"**
  - ⚠️⚠️ **而落点那一句本页判是本期最有引用价值的一句**：
    > **"它不是 AGI 本来应该长的样子。它就是每个人都有一大堆 markdown 文件。"**
- ✅ **而反方的两条本页同样记下来，因为它们不是修辞上的平衡、而是不同的使用层级**：
  - **第二位主持给的是"不看也行"**：**"很多人其实不去看他们的 markdown 文件……光是聊天说出你想要什么、在聊天里创建一个 skill、用它、看输出——你不用看 markdown 也能拿到很多价值。"** ✅ **她/他给的可执行版本**：**"如果你在重复做某件事，就说：看看我们最近五次是怎么做这件事的，给我做个 skill。"**
  - ⚠️⚠️ **而嘉宾给的是一条本页认为可能更耐放的区分**（[00:45:23]）：
    > **"但在像 Devin 这样的情形下，我们把 skill 形式化成了一种表示我们最佳实践的方式，然后把它暴露给 agent、给 code review 系统，让它按我们喜欢的方式去定义 API、按我们定义的方式去立服务级边界。这是一种表示组织级知识的替代方式，而不那么像那种'你不想每次都写 prompt 的任意事情'。"**
    - **他的预测**：**"我感觉这个定位、这个用途可能会比那些随机流程活得更久。"**
  - ✅ **本页的归纳**：⚠️⚠️ **两人没有分歧，分歧是对象不同——swyx 说该死的是"个人的一堆临时流程"，嘉宾说能活的是"组织的成文规范"。而这两者在文件格式上完全一样，于是"skills 会不会死"这个问题在当前形态下无法被回答。** 🔗 **这条区分正好接上 [Garry Tan 的"一个 markdown 文件就是一名员工"](20260812-a16z-garry-tan-founder-psychology.md) 与 [Warp 把 factory 定义写成代码](20261103-latent-space-warp-software-factory-80-to-15-dollars-per-pr.md)——后两者都属于嘉宾说的"能活的那一类"。**
- ⚠️ **另记一个他点名很喜欢的 skill，因为它的机制与本库"理解代码"这条线正好对上**（[00:38:20]–[00:39:20]）：**Geoffrey Litt 的 explain diff**——**跑完之后不只给一个可视化表示让你略读，"而我真正喜欢的是最后那个几乎像小测验的环节，你走一遍，真正强化你是不是理解了在发生什么"**。
  - ✅ **swyx 在这里给了一条本页认为很到位的反直觉**：⚠️ **"每个人都想用 coding agent 来把脑子关掉。他们就是'给我做个 app，读我的心，不用我告诉你就全部弄对'"**，**而"这些 skill 里很多其实是'不不，请多问我一些问题'这个门类的"**。
  - **第二位主持接的那句本页记为本节的结论句**：**"把代码写出来、把活干完，这件事比以前容易多了"**，**于是"你该花更多时间想你到底在做什么"。**

## 六、⚠️⚠️ code review 成了瓶颈：本期对"年度最大变化"的指认

（[01:12:35]–[01:19:38]）

- ⚠️⚠️ **他对去年到今年最大变化的指认很明确**（[01:12:35]）：
  > **"去年到今年之间也许发生的最大的一件事，是突然非常清楚地看到 code review 是一个瓶颈——特别是一旦人们变得非常 AI pill，生成端的速度变得那么高，理论上你一天可以提 30 多个 PR。"**
  - **他给的两难是对称的**：**要么"你把自己插进中间，用传统方式做门禁和 review，但那样你就字面意义上成了约束、成了速度的咽喉点，而那不好"**；**要么"那大规模生成的意义又在哪里"**。
- **他说课上要讲的是中间地带，而条件是前几周那些东西**（[01:13:36]）：
  > **"如果你在 agent readiness 上投入了经过思考的设计，在可验证性上投入了经过思考的设计，那么有一类问题你可以在某个百分比的时间里放心地自动批准。"**
  - **他把问题形式化成两问**：**"从设计、从架构的角度，要什么成立才能直接自动批准？什么时候你必须把自己插进来说'这个我还是要仔细看'？"** **以及"即使你仔细看，你还在做逐行 review 吗，还是在做别的什么？"**
- ✅ **他点名了几篇他认为写得好的工程博文作为课程读物**：**Amplitude、Cloudflare、Augment**；⚠️ **他对 Cloudflare 的点评特别标了公司类型**：**"某种意义上像个传统公司、或者说更大的公司，但我觉得他们在 AI SDLC 的内容上做得非常好。"**
- ⚠️⚠️ **而 swyx 在这里提了一条本页认为比"review 瓶颈"更根本的问题，并且它没有被解决**（[01:15:36]–[01:16:37]）：
  - **嘉宾先说了 Monaco 的做法，而它是一个很干净的可搬用手法**：**PR 描述本身被当成 spec 写**——**"不只是一段话。它实质上就是这个 PR 里发生了什么的 spec，甚至有文件级的指针指到东西改在哪。所以你不只拿到发生了什么的高层，还拿到文件的构成、以及你碰到的那些服务级边界。"** **他的判据是时效性**：**"只要那是最新的、代表代码库此刻状态的东西，我觉得这其实就够了。"**
  - ⚠️⚠️ **而 swyx 的反驳是层级错位，本页认为这是本期最清晰的一次技术分歧**：
    > **"我说的是那个 feature、那个代码库的 spec，因为那是所有 PR 的总和。如果你的 PR spec 弄错了或者漏了什么，那就会成为整个代码库该做什么与你这个 PR 想做什么之间的差额。"**
    - **他自认没有解法**：**"我不期待你有答案，因为我自己也真的为这件事焦虑。我试着指示模型去做，它们做得很差。"**
    - ⚠️ **他对人的角色给了一个说法**：**"所以人类是 spec 之神——'五周前我做了另一件事，而你现在在把它反过来'。"**
  - ✅ **嘉宾给的是一条第三方做法而不是答案**：**Basis（那家做会计的公司）用 git 跟踪不同的文件制品**——**"有些是 spec、是应当如何的意图，另一些是他们称为代码的 canonical state 的东西，那更像是隐性知识、隐性意图，也必须被形式化到某个地方。那部分全部纳入版本控制。"** ⚠️ **他对效果的表述是转述**：**"我觉得他们发现这对他们是有效的。"**

### ⚠️ "god box"：一条 swyx 的基建论，以及嘉宾给的那条政治性反驳

（[01:33:44]–[01:40:50]）

- **起点是 MCP portal 这一周。嘉宾的定位是规模触发**：**"MCP portal 只有到了某个规模才变得有意思——那时你实际上必须有一个单一入口来做治理、安全、审计、成本优化这些事。"**

- ⚠️⚠️ **而 swyx 由此给出的那条基建论本页认为是本期最有再用价值的一条抽象**（[01:36:47]）：

### 一、整期在讨论"学生怎么办"，而样本全部来自 Stanford，且这一点被点出后没有被回到

（[00:07:04]）**swyx 自己在第七分钟就把局限说清楚了**：

> **"我以前说过这个，它几乎是那种为了说得辛辣而说的话，但我其实真的有点相信——大多数学生是 cooked 的，其中一些会非常有价值。我不觉得这是个很受欢迎的说法。Stanford 的孩子会没事的，对吧，他们是 Stanford 的。但美国其余那些人会怎么样？"**

- **嘉宾的回答只有半句**：**"对，那是个开放问题。"** ⚠️⚠️ **而全期此后没有再回到它。**
- ✅ **本页判这处空缺的重要性在于它改变了第二节那条处方的读法**：⚠️ **把开源维护者的 review 带宽调给学生，这件事成立的前提包括"这所学校有能力去谈这些合作"、"赞助方愿意给这批学生额外 credits"、以及"维护者愿意 review 这批人的代码"。** ⚠️⚠️ **这三条全部与学校声誉相关，于是这条处方越有效，它越可能是在扩大那条被点出的裂缝，而不是在补它。** ✅ **本页不判定它实际效果如何，只记这个方向在期内被提出且被放过。** 🔗 **对照 [Alpha School 那期本库标出的同类张力：谁"cooked"了](20261027-a16z-alpha-school-two-hours-85-percent.md)。**

### 二、⚠️ 全期关于"学生实际在用什么、用得怎么样"的量化只有一个数据点，而那个点是定性的

- ✅ **期内唯一的调查结果是"没有一个人还在手打代码"（[00:10:06]）**，⚠️ **而工具占比他明确说还没问**。
- ⚠️⚠️ **本页认为这是本期体裁上的结构性限制**：**这门课第二次开课、刚上到第一周结束（他自述"这是第一周的结束"，[01:58:02]）**，✅ **于是全期关于这套课程设计是否有效的证据只能是去年那一版的印象性反馈（"很受欢迎、学生很感兴趣"、"去年还有一篇 Business Insider 的文章写过这门课"）。** ✅ **本页因此把全部课程设计内容记为**设计意图**，而不是经过检验的教学结果**，并记下它的可检验形态：⚠️ **那些开源贡献作业最终有多少被合并、维护者的 review 负担实际有多大。**

### 三、⚠️⚠️ "软件工厂里人还剩什么"被当成第十周的内容，而期内给出的两个咽喉点都未被论证

（[01:41:50]–[01:42:50]）**他给的答案是两点**：

> **"今天我觉得答案是 intent 和 review 的某种组合——intent 是你在定义 spec、定义需要被造出来的东西，review 是你在做某种程度的自己的检查。"**

- ⚠️ **他对两者的先后给了一个判断**：**"而当然，我觉得那个瓶颈（review）会在 intent 那一块之前先被放松。"**
- ⚠️⚠️ **而本页标注这两个咽喉点在期内都被自己的材料削弱了**：
  - **review 侧**：**第六节里 swyx 指出"codebase 级的 spec 是所有 PR 的总和"而模型做不好、人类是"spec 之神"——这说的是 intent 侧的担子更重，而不是更轻。**
  - **intent 侧**：**第九节那条"主指标换成什么"整段没有答案，而 intent 的质量恰恰需要一个指标才能被衡量。**
- ✅ **本页因此记：本期把"人留在哪两处"讲得很清楚，而"留在那儿的人用什么判断自己做得好不好"这一问在同一期里被明确问出、明确没有答案。本页判这两处是同一个缺口的两面。** 🔗 **而 [Warp 那期把这个缺口往前推了一步但也停在同一位置](20261103-latent-space-warp-software-factory-80-to-15-dollars-per-pr.md)——它给了"每个被 merge 的 PR 人类动手几次"这个可度量的口径，✅ 但本库此前已标注那是一个会被优化的指标，而不是一个纯观测量。**
