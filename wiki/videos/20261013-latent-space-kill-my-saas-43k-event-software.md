## 一、被替掉的是什么，以及为什么他改了主意

- **标的**：会议/活动管理软件（原产品 Session Board），用于管理讲者；
  报价 **$43,000/年、四场活动**。他的对照是"**43K 可是很多 token**"（[00:01:01]）。
- ⚠️ **买方视角的两条具体不满**：
  - **变更请求的交付周期**："买现成软件、提变更请求，常常要 **3 到 6 个月，或者永远不会**
    真的发出我们想用的东西"（[00:01:01]）。
  - ✅ **SaaS 是一个捆绑包**："**我们大概只用了这家供应商卖给我们的三分之一，
    而没用的那些部分没有折扣**"（[00:02:01]）。
- ⚠️⚠️ **本页认为这一段是全期最值得记的立场变化，因为它附带了一条制度证据**：
  他说**多年来公司的创始合同里明文写着——没有他的明确批准，任何人不得自建内部软件**，
  理由是"**太容易得 not invented here 综合症**"、太容易被"造本来可以直接买的商品化软件"分散注意力。
  **"今年我改了主意。我认为 agent 终于好到可以让我们拥有个性化软件了，而我正押上真金白银来验证。"**
  （[00:01:01]–[00:02:01]）
- **他对标的类型的界定**（本页认为这条限定很重要）：**这是"例行的中档业务软件"**——
  "**不是 Salesforce，也不是你一天就能 vibe code 出来的东西，是中间那一档**"，
  而那里"**有数十亿美元规模的烂软件正被普通人每天使用**"（[00:03:02]）。

### ⚠️ 为什么这类软件比看起来难复刻
- **待办事项链条**（他逐条列的）：讲者投稿 → 评审打分 → 委员会接收 →
  需要讲者门户上传头像与幻灯片 → 未完成任务要发提醒 → 排进某个房间与档期 →
  改档期 → 讲者改标题后要正确出现在公开议程上 → 加共同讲者 →
  **再对受邀讲者、赞助商、参会者各走一遍**（[00:03:02]）。
- ⚠️ **角色是多重且会临时发明的**：一个人可能同时是讲者 + 赞助商 + 参会者，
  或者组织者、志愿者、供应商——"**有时候我们就因为某个特定情况当场编一个角色出来**"（[00:04:03]）。
- ✅ **为什么活动行业极度风险厌恶，他给了后果口径**：**软件把我们推过截止日一周，
  就会有人出现在错误的地点，或者会议干脆开不起来**——"**这些我们都经历过**"，
  还要付加急费、工会费（[00:04:03]）。
  配一句行业观察："**我认识的人里没有一个喜欢自己的会议 app。**"（[00:04:03]）

## 二、竞赛是怎么跑的

- **给builders 的材料**：他本人写的 brief + **真实产品的操作录屏** + brief 里附的 **42 张截图**；
  **冠军奖金 $10,000**；并为认真参赛者提供**最多 $500 的 token 报销**
  （"因为没人会在一个 $20 的套餐上造这个"）（[00:04:03]）。
- **规模**：**最终 72 个人/团队提交**；"**大多数仍然在线且开源**"，会全部给出链接（[00:02:01]）。
- ⚠️ ✅ **验收设计是本页认为这次实验真正的方法论贡献**：
  最终决定权交给**他的真实活动团队**，而**不是他本人**——
  "**他们不懂技术，不在乎你用什么栈、什么 agent、什么模型，不在乎开源还是闭源。
  他们只在乎自己到底会不会买、会不会用。**"（[00:02:01]）
  他把这叫做"**半盲评测（semi-blind eval）**"（[00:05:05]）。

### ⚠️⚠️ 三件所有人都栽的事——而且都不在规格里
1. **多种门户**：讲者、受邀讲者、赞助商**各自需要自己的门户**，
   而"**多数提交只造了一种门户，而且不太灵活**"（[00:05:05]）。
   ✅ **验收方 Kelsey 的原话给出了更精确的区分**：她称赞某个提交是
   "**少数真的把 form 和 portal 的区别解析出来了的**"，而最大的减分项是
   **缺少让管理员配置多个不同门户（CFP 门户、赞助商门户、受邀讲者门户）的能力**——
   "这也是我们在 Session Board 里有的功能"（[00:05:05]）。
2. **拖放（drag and drop）**：他称这是"**UI 里更复杂的元素之一，模型很难做对**"。
   ⚠️ **测的不是能不能拖，而是三件事**：**放下时那个 section 是否真的移动了**、
   **你能不能看出它是已确认还是已更新**、**歧义有没有被表达出来**——
   因为"**显然你不能让同一个人同时出现在两个 session，也不能把同一个房间同一时段
   重复预订给多个 session**"（[00:06:06]）。
   ⚠️ **Kelsey 给了一条很具体的"工具提示反而暴露问题"的观察**：
   提示告诉你"点这里加一个 session"，但它**感觉像是一层覆盖层，而没有真的去做它正在教你做的事**——
   "**我就想，我为什么不能直接点那个按钮在那里加一个 session？**"（[00:06:06]）
   她同时说明自己为什么把拖放列为判据：**它能让她判断"他们到底有没有照着说明做"**（[00:07:08]）。
3. **不走 CFP 表单直接加一个 talk**——受邀讲者或 VIP 需要这个（[00:07:08]）。
- ⚠️⚠️ ✅ **本页认为这是全期最该被引用的一句**：
  **"这三件没有一件在我们的文档或 Session Board 的说明里被好好写明——
  但只要你像一个真实的人那样去用这个产品，你会立刻发现它们。"**（[00:07:08]）

## 三、⚠️⚠️ AI 评委 vs 人工验收：本页认为这是本期最有价值的数据

- **AI 评委的定位是他自己先声明的**：**公开发布、但不用来决定冠军**，
  只是让参赛者把应用跑起来的 sanity check——
  ✅ **"基本上是一个去掉了 RL 的 RL environment"**，一个供人 **hill climb** 的环境（[00:07:08]）。
- **实现**：**Claude 以每一种角色登录、点完他们写的 20 个正常用户流程场景**，
  **再用 Claude 打分**；这样"**按钮叫什么、放在哪里，你有灵活度**"（[00:07:08]）。
- ✅ **他给其他人的操作建议**：如果你要办这种竞赛，
  **把自己点完整个应用的过程录下来、转成场景、发布出去让人 hill climb**（[00:08:09]）。
- **覆盖与饱和**：**56 个应用跑过这套评测，其中 40 个覆盖度足够参与排名**；
  ⚠️ **前七名彼此相差 2.3 分之内——"基本上就是饱和了"**（[00:08:09]）。
- ⚠️⚠️ **而人工验收与 AI 评委的相关性很差，这是本页认为最该被记的一组数字**（[00:09:12]）：
  - **AI 评委 top 10 里有 6 个被人类评为"弱"**；
  - **最终获胜者在 AI 排行榜上排第 19**；
  - 他自己的定性是"**所以它挺弱的**，有某种 R² 相关性但远不完美——**而它本来也不打算是**"。
- ✅ **他明确说明一部分不相关是故意设计的**：**他们允许参赛者按自己的品味偏离规格**，
  而且是**鼓励**——因为"**老实说这同时也是一次招聘练习，在找能带着品味写代码的人**"。
  目标是找**理解待办事项本身、而不是机械克隆产品**的人，能**定义什么叫好的用户体验、
  并代入真实测试者的角色**（[00:09:12]）。
- ⚠️ **他对这次竞赛客观性的自我定性非常直白**：
  **"所以这场竞赛其实并不客观。评分细则没有良好定义，规格也没有良好定义。"**
  "如果真有一张清单，我们就能发布清单了"——他们**确实发布了一张可克隆的清单**，
  **但"品味才是我们真正想从那些操纵编码 agent 的人身上找的东西"**（[00:09:12]–[00:10:12]）。
- ⚠️⚠️ ✅ **一条来自参赛者的独立确认，本页认为它是上面那组数字的机制解释**：
  参赛者 Open Stash 告诉他们，**他们最自豪塞进应用里的大部分东西，AI 评委完全没有覆盖到**。
  **"而他们是对的。而我们之所以发现这一点，是因为我们让人类点过了每一个应用。"**（[00:10:12]）

## 四、他们到底怎么造的：过程数据

- **规模数据**：**公开 repo 的中位数是 91,000 行代码**，"人们连着好几天跑 agent"（[00:10:12]）。
- ⚠️ ✅ **模型使用分布，以及他自己给出的"没有 alpha"结论**（[00:10:12]）：
  - **Claude Code 与 Codex 基本打平**；
  - **66 份提交里有 40 份同时用了两者**；
  - "**几乎所有人都混用了不同模型家族**"；
  - 三位入围者都用了同一款 GPT 系模型，**但另外 66 份里也有 50 份用了**——
    **"所以这里没有 alpha。"**
    ⚠️ **型号在字幕里损坏，本页不写定。**
- ⚠️ **他主动对照了自己的做法，而且是反过来的**：
  "**我自己通常一个项目只用一个模型，这样所有 context 都留在一个地方**"——
  他要一条 Codex 线程覆盖全部、也要一条 Claude Code 线程对它最擅长的任务做同样的事。
  **"结果很多这些 builder 不这么干。他们会切换角色。"**（[00:11:13]）
  ✅ **本页标注这是一条难得的"主讲自己的实践被自己的实验数据反驳"的记录。**
- **材料可查**：他们让 builders **自愿把 prompt 与过程文档提交到 GitHub**，
  "**所以你可以真的读到他们到底怎么做的**"（[00:11:13]）。

### ⚠️ 他从提交物里挖出的三种多模型协作模式
1. **聪明模型决定做什么，便宜模型当"slot cannon"去写被指定的东西**。
   例子：Cboard HQ——**Claude 做计划与评审，Codex 写大部分代码**（[00:11:13]）。
2. **一个模型造、另一个模型检查，而且通常由"更擅长驱动浏览器或做测试"的那个来检查**；
   他说"**我认为现在那个是 GPT Codex**"（[00:11:13]–[00:12:14]）。
3. ⚠️⚠️ ✅ **没有模型批准自己的工作**——本页认为这条是三者里最有机制含量的：
   Green Room HQ **让一个 Claude 团队和一个 Codex 团队在各自的 worktree 里跑，
   在对方验证之前谁都不能 merge**。
   **他给的原理是"on-policy 与 off-policy 验证"**：
   **"agent 对自己的工作往往比对别人的工作更宽松。而我认为这也反映了人类的行为。"**（[00:12:14]）

## 五、三位入围者的共同做法：代码之前的工作

✅ **主讲自己总结的共同点是"在任何代码被 prompt 出来之前他们做了多少工作"**（[00:12:14]）。

- **Marco（TrackStage，第二名）——先把一切计划完**。他此前给客户做过克隆应用，规则是先规划：
  "**如果 UX/UI 已经定了，我唯一做的事就是坐下来 8、9 个小时，以最细的粒度规划出整个
  数据 schema、业务逻辑，以及字面意义上的伪代码。**"
  ⚠️ **他紧接着那句对照本页认为很有分量**："有点好笑，因为**如果你把我四五年前做的这些任务、
  加上设计，字面上塞进一个 LLM，然后走开两三个小时，你就能拿到整个东西、像素级完成**。"
  （[00:13:14]）
  他的具体做法是**把主讲给的操作录屏 + Session Board 的 API 文档直接喂给 Claude**，
  并指定自己偏好的栈（**Convex + Next.js**），理由是**速度很重要**——
  Convex"给你一个实时数据库，不用太多功夫就能得到高性能、手感好的东西"（[00:16:17]）。
- **Yazin（Conferencer，第一名亚军）——从研究开始**。
  他**先把 Google Doc 转成 markdown**，然后**用 firecrawl 爬完了 Session Board 的整个帮助门户**，
  以及搜索结果里几个类似站点，"**就是想尽可能多拿信息**"（[00:13:14]–[00:14:16]）。
- **Valentin（获胜者）——把力气花在护栏上，并把它变成可复用模板**。
  "**我把它做成了一个模板而不是形式化文档**……很多项目我都得重做这套老活，
  而这个项目就是个完美例子……**如果有人要接手这个项目，你希望他能在上面写代码**，
  所以我花了很多时间放那些 link、那些 code review 之类的东西，**现在我直接把它做成了一个
  GitHub 模板**"，每个新仓库从它克隆，"**而不是有一个 Google Doc 写着我做过什么**"；
  **完全开源**（[00:14:16]–[00:15:17]）。
- ⚠️⚠️ ✅ **Valentin 的探索方法本页认为是本期最具体的一段 agent 使用记录**（[00:15:17]）：
  他让 Codex"**给我画出这个 app 每一个功能的每一条流程**"。
  **令人意外的是 agent 用的是一堆 YouTube 视频——逐帧截图去判断"哦，这里发生了什么"**。
  产出是**一大堆 markdown 文件夹，每个功能都写明预期**；
  **然后才是规划：把它切成可以并发做的部分**（有些功能会重叠所以必须串行），
  "**为每一步定出能并发多少个 agent，然后全部跑起来**"。
  ⚠️ ✅ **而他接下来发现的那个问题，本页认为是这段的真正落点**：
  跑完之后他手工走了一遍，发现"**不完美。为什么？因为我看到他其实从来没有在本地把 app 跑起来。**"
  **于是下一步是把整个流程重做一遍，但这次 app 在本地跑着。**
- ⚠️⚠️ ✅ **主讲对这一节的收束，本页认为应当完整保留**：
  **"所以如果你看这些片段，注意没有一个人说自己打了一条 prompt 然后走开。
  真正的情况是，那条 prompt 几乎是最后一步——你是在建立起对问题的完整认知、以及 mock、
  文档、规格这些东西之后才走到它。大部分工作是搞清楚这个软件到底在做什么，
  然后他们才能从那里偏离出去。"**（[00:16:17]）

### ⚠️ 自己当真实用户，反复用
- ✅ **主讲转述的一条诊断**：有人写道**"agent 非常擅长构建，但相当不擅长注意 UX 问题"**。
  **具体例子**：头像上传功能把照片存到了某处，**但公开讲者页面根本不从同一个地方读取，

## 六、⚠️⚠️ 他自己给出的反方：为什么这还不叫"杀死 SaaS"

✅ **本页认为这一节是本期最重要的部分，因为它是出题人自己在给自己的结论设限。**

- ✅ **他把这条取舍压成一句对称的话**：
  **"你搞坏了它，它就是你的。而很多人也在说反过来的那一面：你拥有了它，你就能搞坏它。"**（[00:20:19]）

  ⚠️ **她的限定条件给得很实**：**"我们正受困于这个拼凑效应，而我们懂得足够多，
  能说出'我们想要更好的、我们能做得更好、我们需要更好的'。但我们没有时间。

- ⚠️⚠️ ✅ **"刷新缓存"那个故事，本页认为是全期最有说服力的一段买方论证**（[00:21:19]–[00:22:19]）：
