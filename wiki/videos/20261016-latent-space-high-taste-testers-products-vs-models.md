## 一、⚠️⚠️ 好模型与好产品：一条把产品失控归因到 AI 写代码的论证

（[00:01:01]–[00:12:12]）全期开场就是对 DevDay 发布的集体不满，**而且不满的对象是产品而不是模型**。有嘉宾直接说 **"实验室在产品上真的很吃亏"**（[00:08:08]）：

- **"Codex 桌面端刚发时是那么对，然后每更新一次就更不对一点。我认为 DevDay 的大部分更新是退步"**（[00:08:08]）——给的具体退步是：**多加的那条副侧栏**、**性能变差**、**断网时输入框整个冻住**。
- **功能被藏起来**（[00:02:02]、[00:09:10]）：新助理产品 **Dots** 深埋在 UI 里（**有人以为它会是独立 app，"我很震惊它不是"**）；**ChatGPT 里有一个地图功能，藏在第二条侧栏的三个点里**，有嘉宾发帖说起，官方回"这早就有了"，他的反应是 **"你在说什么？'早就有了'是什么意思？"**（[00:10:10]）。
- ✅ **他们自己给出了藏起来的理由**（[00:09:10]）：**"因为如果我们为那 800 万不吃 AI 药丸的用户把它弄坏了——所以我们必须把所有东西藏起来，信任 power user 自己找得到。"**
- **"fork chat" 被改名**，理由是"非开发者不懂 fork 这个词"——说这事的人反应是 **"但我就是开发者啊"**（[00:12:12]）。
- ✅ **一条产品论断（本页认为是这一节最可迁移的）**（[00:11:10]）：**"有这么一类中间地带的产品，想成为所有人的某样东西，结果成了没有人的东西。"** 他举的对照是：**Grokbot 状态很好，因为它明确就是一个专业人士的个人助理**；**Muse 对终端消费者非常好用**；**而 Codex 被兑淡、ChatGPT 被弄复杂，两边都不开心。** ⚠️ 同一处还有一条担忧：**Dots 的发布同时讲 enterprise 和 consumer——"那是两个不同的产品"**。

### ⚠️⚠️ 归因：产品的不连贯是 AI 写代码的症状

（[00:10:10]–[00:11:10]）这是本页最想留下的一处：

> **"有点讽刺，我觉得这里头很多是用 AI 写代码、用 AI 做产品的症状。……就拿 Codex app 来说，太多东西随时在无缘无故地变，从开发者的角度看非常令人沮丧。……几乎就像 AI 写出来的文字——你眯着眼一看，然后'等等，什么？'"**

- ✅ **他明确说这句**"正反两面都成立"**（[00:11:10]）：**"Codex app 也真的很好，而且我觉得前 AI 时代要做出来会非常难"**——不只是驱动它的 AI 复杂，browser use 这些东西本身就复杂。
- **另一位接着给的词是 "它感觉毫无方向感（directionless）"**（[00:11:10]）。
- ⚠️ **本库判定**：这是一条**观察，不是证据**——没有人给出"哪一处改动是 AI 写的"。✅ **但它值得记，因为它和同一天 [a16z 那期的论点](20261016-a16z-why-ai-cant-keep-code-running.md) 指向同一件事的两侧**：那期讲**生成代码的能力跑在了运维/可靠性之前**，这期讲**这个落差在终端用户的产品体验里长什么样**。

## 二、⚠️ "东西到底在哪儿跑"：本期反复回到的那个未解问题

（[00:04:03]–[00:07:08]、[00:19:16]–[00:20:16]、[00:42:26]）

- **实验室宣布的和实际做到的**（[00:05:05]）：有嘉宾转述 DevDay 的那种 **"任务完成，你们可以合上笔记本了"** 的调门，然后说 **"我的笔记本还是没合上"**——他试过那个云端按钮，**"没太搞懂怎么配，它要我做一堆事，然后我合上笔记本它就停了"**。⚠️ **这一期有一处很具体的日常证据**：主持人说某位嘉宾来录音路上问"我要带笔记本吗"，得到"就是来聊天"的回答后说 **"行，那我把它开着放办公室，这样我的 agent 能接着干"**（[00:05:05]）。✅ **他的结论："所以不是任务完成。他们宣布的那件事，他们没做到。"**
- **这件事难在哪**（[00:05:05]）：另一位替实验室说了一句——**"远程执行是个很难的工程问题，尤其是要把 UX 为普通人做好"**。
- ⚠️⚠️ **一条明确的技术路线分歧**（[00:06:06]）：**多数 coding agent 默认把状态放在内存里**，要能在本地↔云之间自由迁移就得**把状态外部化**，这需要重写。**Pi 刚做了（"Pi durable"）**，而 **"Claude 和 Codex 不知怎么的要花一年才做"**。
  - **给出的"正确做法"极其朴素**：**"基本的事情就是：一切都该在一个日志里。有一个文件，你往后追加，然后从上次停下的地方接着来。"**
  - ⚠️ **而且他们指出这其实已经是内部表示**——"从技术上说这就是 Claude Code 和 Codex 的内部表示，他们有那个大 JSONL 文件"。**"那把东西发到云上有什么难的？"**
  - ✅ **真正的卡点被说成是接口承诺，不是工程**：**"问题是他们没有对这个 API 做出承诺。所以我们干脆自己造了一套 coding harness，就带这个只追加日志的性质——因为我们不想基于一个 OpenAI 团队或 Claude Code 团队不保证将来不变的 API 来开发。"** ⚠️ **本库按业务推断这位是 Dex Horthy（HumanLayer 做 coding agent 基础设施，且片尾他自述"我们在做 software forge"），但稿中无标签，存疑。**
  - **标准缺口**：没有 `agents.md` 那样的东西管这件事（[00:06:06]–[00:07:08]）；提到有人在推一个 agent 状态标准，**"但得等某家实验室接过去才算有"**；此外**只有一些给研究和 benchmark 用的 trace 标准**（"把 agent 做过的一切打包起来"）。
- ⚠️ **到了 [00:42:26] 这条变成了对助理产品的不信任**：Dots **会把活儿甩出去开 Codex 线程**，但 **"它怎么做这件事非常不确定，比我希望的要激进得多"** / **"我不信它"**。✅ **收尾那句是本节的小结**：**"整个'执行发生在哪里'的模型就是坏掉的。"**

## 三、agent vs 助理：一场关于命名的较真，和开发者的反驳

### Alex Volkov 的"改名运动"（[00:14:13]–[00:15:15]、[00:18:16]）

来源：[Latent Space / High Taste Testers](20261016-latent-space-high-taste-testers-products-vs-models.md)

- **他的时间线**：**"我们曾说 2025 是 AI agent 之年，然后 2026 我们换成了 proactive agent"**，而他要推的是 **"改名成助理（assistants）"**。
- **他给的理由不是技术而是受众**（[00:15:15]）：**"在我们这个泡泡之外，agent 对他们是个可怕的词。助理是个容易的词。为什么？因为他们知道所有有钱人都有个私人助理替他们安排事情。"**
- **他给的功能分界**：**一边是"你用来写代码的 AI agent"**，**另一边是"替你主动做事的东西——读你的邮件、判断哪些重要并提给你，从而减轻你的负担而不是增加负担，替你约理发和各种预约"**。
- ⚠️ **他的类比论证**（[00:18:16]）：**"公司里的高管忙到管不了自己的日程，于是有个人替他们做。那些人回不去了。这是人类的标准套路——你上到下一个层级，你还是会更忙，但你能做更多事。"**
- ✅ **他在片尾把这条落成了自己的"一个请求"**（[01:12:46]–[01:13:46]）：**"我想让人们解开对 AI 系统可能性的想象。……我认为对抗末日论也很重要，因为'新闻里说它要来抢我们'是一回事，'它真的替我订了理发、省了我五分钟'完全是另一回事。一旦人们感到那种触手可及的'它帮了我、省了我时间'，他们就会转向'AI 其实是有用的'。"** ⚠️ **本页提醒这是一条立场表述，不是证据。**

### ⚠️ 开发者的反驳："为什么不直接把 Codex 用成助理？"

（[00:17:15]–[00:20:16]）有嘉宾直接问：**"我们都是开发者。为什么不能把 Codex 或随便哪个 agent 做成更好的助理体验？同样的工具、同样的调用。"** 而且**多数人实际就是这么干的**：

- **一位的做法**（[00:17:15]、[00:59:37]）：**"我现在用来做个人助理的主 agent 就是 Pi——我给了它自己的 Gmail，它有信用卡，有提醒和 cron"**，他自称这是 **"Codex 克隆 + ChatGPT"** 的组合，**"就是能用"**，而且 **"比 Dots 好"**。⚠️ **他自己给了保留**：**"我其实没怎么调主动性那部分，我估计那才是真正难的部分。我现在对它没有强烈的渴望——也许我只是不知道我缺什么。"**
- **另一位的做法**（[00:59:37]）：**"我的个人助理还是一个 git repo，一堆脚本，整个大脑、整个记忆系统都是 markdown，我要干活就在里面起 Claude / Codex。"**（同一个人在 [00:04:03] 说这个 repo **"在 OpenClaw 成为选项之前就已经是 OpenClaw 形状的"**。）
- ⚠️ **反驳的反驳有两条，本页认为第二条更强**：
  1. **你需要的是打磨过的产品**（[00:19:16]）：Grokbot 之所以好用是因为**移动端 app、网页界面都做得很顺手**，而且 **"你不用自己配记忆"**——"那你自己就有答案了：因为你需要一个打磨过的产品"。
  2. ⚠️⚠️ **"我不想多一个问题"**（[00:20:16]）：**"我引入一个助理是来解决一个问题的，结果现在我有三个问题。我得维护基础设施。我想减负，不是增负。又多一个要我管的盒子，它还会宕。如果我跑在我们买来给 OpenClaw 用的那台 Mac Mini 上，那台 Mac Mini 会掉线，然后它就不在线了。"** ✅ **本库认为这是本页上对自建派最有力的一条反驳，而且它和第二节"东西在哪儿跑"是同一个问题的消费者侧。**
- ⚠️ **一条关于收敛的预测**（[00:20:16]）：**"我觉得 ChatGPT 和 Codex 合并的很多原因是，长期看一切都会是 Codex，因为他们想在一套 harness、一套工具、一种做事方式上做 RL。Dots 也会是。底下全是 Codex。"** 他自注 **"他们还没到，但最终会落在那儿"**。⚠️ **这是推测，不是消息。**

## 四、⚠️⚠️ 信任的那条线：连什么、读还是写

### "温度计"：连个人邮箱才是真的线（[00:15:15]–[00:17:15]）

- ✅ **本页认为这是全期最有价值的一处集体自述**，因为它问的是**同一个具体动作**："你把个人邮箱连上了吗"。
- **一位的答案**（[00:15:15]）：Dots 是 **"我第一个连上个人邮箱的 agent 或助理"**；**"我不信 Instinct，我不信这些里的任何一个"**；他用过 Poke，**"我对这种事非常非常偏执"**，只连了日历，**"那对我是 80/20——它能改我的日程、发日程邀请，但我没走到邮箱那一步"**。
- ⚠️⚠️ **他给的名单**（[00:16:15]）：**"全世界真的只有三家公司我会信，按顺序是 Apple、Google、OpenAI——对我来说没有第四家。"**
- **另一位连邮箱的理由是认了既成事实**（[00:16:15]）：转述另一位创始人的话——**"OpenAI 反正已经有我最私密的内心想法了"**，而且 **"我的数据保留设置已经配好了"**。
- **一致的排除项**：**"Amazon、Facebook 拿不到个人邮箱。"**
- **一处有价值的时间差**（[00:16:15]）：**"我也是直到 Cognition 买了 Poke 才连的……因为我知道他们认真对待这件事。"** ✅ **即信任被挂在收购方身上，而不是产品本身。**
- ⚠️⚠️ **Meta 为什么被排除——理由不是"不小心"**（[00:16:15]–[00:17:15]）：有嘉宾说他在 Muse 内测里被问要不要接邮箱，他说不，对方问 **"你为什么不信我们？"**。他的解释是：**"我确实信他们。更多是……我觉得 OpenAI 有很多数据，我觉得他们不太会拿我的数据乱来。我感觉 Meta 如果那意味着他们赢的可能性哪怕高一点点，他们就会直接做，然后以后再承担后果。"** ⚠️ **同席有人当场表示不同意最后这句（"我不同意最后那点"）。** ✅ **本页照录这处分歧，不做裁决。**
- **另一条具体的拒绝**（[00:17:15]）：**"我永远不会把邮箱密码打进 Gmail 以外的任何东西，而他们当时要我的邮箱密码——绝对不行。"** 对方补充 **"他们当时还没有 OAuth 连接器"**。✅ **本页认为这条值得单独记：被拒的是认证方式，不是厂商。**

### ⚠️ 读 vs 写，以及一个来自日常使用的错误率（[00:54:34]–[00:58:36]）

- ✅ **全期被重复了三次、也是转录稿开头被剪进预告的那句**（[00:58:36]、[00:00:00]）：**"我基本还停在只读，写要显式许可。"**
- **具体形态**（[00:55:34]）：**"邮箱是连着的，我也在那儿用，但在我看到真正的草稿、自己按下发送之前，它不许发任何东西。"** 有人抱怨某个产品的审阅 UI **"要往右滚才看得见，是最烂的审阅 UI"**；Grokbot 的被夸 **"就显示成一条普通消息，很好"**。
- ⚠️⚠️ **而这是本页认为最该被引用的一个数字**（[00:55:34]）：**"但我注意到的是——不常见，但我会说大约五分之一次，里头有些细节和内容是我不想发出去的。"** ✅ **本库此前所有关于 agent 权限的材料都是制度设计（沙箱、守门模型、有状态策略），这是第一条来自个人日常的人工复核命中率。**
- **一位把默认设成许可提示**（[00:55:34]）："我把它设成会先给我一个许可提示"。

### ⚠️⚠️ 提示注入：一次正面分歧，和一条更重要的重构

（[00:13:12]、[00:53:32]–[00:55:34]）

- **分歧本身**（[00:13:12]）：有人说 **"我觉得提示注入基本上已经解决了"**，立刻被打断 **"完全没有。什么？"**
- ⚠️ **"已解决"一方给的证据有两条**（[00:13:12]、[00:53:32]）：① **Pliny the Liberator 当面给了五次机会去攻破 Matthew Berman 的新 Hermes agent，没成功**（⚠️ 质疑方当场的回应就是 **"才五次啊"**）；② **新模型的指令层级**——"我看了一批专门做提示注入的 benchmark，从 Astra 和 Opus 5.5 开始，**这些模型不信任任何来自系统提示之外的东西**……他们有一套很强的层级：**先是 constitution，是预训练进去的；然后是开发者给的 system prompt；然后才是内容**，而且他们总把内容用'从这里到这里是一封邮件'这类标记包起来，很难越狱"（[00:53:32]–[00:54:34]）。⚠️ **本库按自指（"我的 Hermes agent"、"我在播客上问过"）推断这位是 Alex Volkov，存疑。**
- ✅⚠️⚠️ **而本页认为真正的收获是对方的重构，它把问题从"对抗"挪到了"分类"**（[00:54:34]）：
  > **"提示注入绝不是我唯一担心的事。我觉得还有很多别的方式能让你的生活很受伤，而且不是别人故意造成的。"** —— **"模型真心想帮忙，那危险得多。"**
  >
  > **"我甚至不确定提示注入是不是正确的词，但——只要你的模型开始回邮件，而你希望它在某些时候给出信息，它就一定会误判。无论是不是有人故意想让它误判，它都会误判什么该说什么不该说。我相信这是真的。"**
  - ✅ **本库判定这条可迁移性最高**：它不依赖任何模型版本，且**给出了一个结构性理由——"有时该说"这个需求本身就把任务变成了一个会出错的分类问题**，与本页第五节（分类是最难的问题之一）正好接得上。
- **他随即向全席要证据**（[00:55:34]）："我要你们都给证据——你们见过吗？"，于是出来三个具体事故：
  - ⚠️ **"有人问他朋友的 Instinct 要邮箱里的 Netflix 二次验证码，它就给了。"**（[00:55:34]）
  - ⚠️ **Muse 的一起**（[00:13:12]）：有人在 Facebook Marketplace 卖东西，**买家出现在卖家家门口时，Muse 直接跟那个人说了些话**（⚠️ 原话未说完，本页不补）。
  - **同处给的假设性清单**："不小心告诉你老板你在找新工作"、以及一个现场玩笑——某人缺席是因为"在面试人"，"面试接你班的人"。
  - ⚠️ **一起真实的尴尬**（[00:53:32]）：**"我们公司的 Azure 对接人……我们开始在专属支持群里收到他们 OpenClaw 发来的消息，'你好，我是某某人的 openclaw'——而这些人我是本人认识的。"**
- ✅ **一条本页认为值得与第四节开头对读的旁证**（[00:52:32]）：**"你一年前就能加一个收文本、发邮件的工具，但没有一个脑子正常的人会在自己真的邮箱上那么干。而现在你会了。"** 说话人被追问时特意强调 **"我用词很精确：没有一个脑子正常的人"**。

## 五、⚠️⚠️ decision model：新的是校准概率，解锁来自价格与速度

来源：[Latent Space / High Taste Testers](20261016-latent-space-high-taste-testers-products-vs-models.md)

（[00:20:16]–[00:32:20]）背景：**OpenAI 在 DevDay 发了一个 [decisions API](20260930-latent-space-openai-devday-computer-use-decisions-api.md)**，被席上直接称为 **"Jev 克隆"**；**Cloudflare 也发了一个**；**Jev 本身来自 [TypeSafe](20260921-latent-space-typesafe-jev-system-one-models.md)**。⚠️ **注意本节有利益相关：Latent Space 刚做过 Jev 创始人 [Diogo Almeida](../people/diogo-almeida.md) 的专访（[本库已收录](20260921-latent-space-typesafe-jev-system-one-models.md)），主持人在本期多次提及（[00:20:16]、[00:25:17]、[00:29:18]）。**

### 新东西到底是什么：**校准过的逐决策概率**

- **OpenAI 的版本"现在就是 Luna 加一层结构化输出包装"**（[00:20:16]，主持人转述自己那期专访），**"显然他们会改进"**，而且 ⚠️ **"所谓发布其实是进了等待名单，还没公开"**（[00:32:20]）。**Jev 的差别是多模态**（[00:21:16]）。
- ✅ **本页认为这一节最实在的一条**（[00:21:16]）：**"Jev 最酷的地方是，大多数模型提供方把 log probs 拿走了，而我确实想知道这些输出各自的百分比——不只是'答案是这个'，而是能多拿到一点信号。"** 追问 **"你要的是逐 token 还是逐决策？因为 Jev 给的是逐决策"**，答 **"对，就是这个意思"**。
- ⚠️⚠️ **而旧办法失败在校准，不在能力**（[00:22:17]）：**"用结构化输出当然早就能拿决策概率，它们只是校准得很差"** —— **"我从不信模型给我一个 1 到 100 的数"** —— **"你可以说 0 到 1，但不管你怎么提示，它本质上只会分到 0、0.5 或 1 这三档。"** ✅ **"而现在它感觉像是真的概率。"**

### ⚠️ 解锁不是新能力，是价格和速度

- （[00:21:16]–[00:22:17]）**"结构化输出和流水线这套东西已经存在很久了……你用 GPT-4o-mini 就能做掉 Jev 能做的几乎所有分类，这已经很久了。它显然更聪明更好更快更便宜，但它没让任何技术上全新的事变得可能。只是价格和速度让它能用在新地方。"**
- **量级自评**（[00:29:18]）：问"和 GPT-3 那次同级吗"——**"不"**；问"和推理模型 / o1 那次同级吗"——**"没完全到，但在接近……对我们来说大概是那次的 30%"**，并补 **"我觉得它还没完全渗透开，但我们会看到"**。
- ✅ **一条相反方向的乐观**（[00:30:18]）：**"Jev 还严重没被探索够。"**

### ⚠️⚠️ 本页认为最可直接拿去用的一条：切换成本被构造成接近零

（[00:22:17]–[00:23:17]，也是转录稿开头被剪进预告的那段）

> **"一旦你有了很多带标签的数据，你就能轻松换模型——你可以直接说：拿我现有的全部标签当 eval。如果出来个便宜 10 倍的东西，它跟我历史标注的一致率超过 x%，那你只需要复核不一致的那部分。"** —— **"所以切换成本非常非常低。"**

- **同处还有一条更土的做法**（[00:23:17]）：**"我们做的是穷人版 GEPA——好，这是一个不 work 的 case，拿它当 eval，然后一直改提示直到……"**

### 产品形态的解锁：把 AI 塞进它以前进不去的地方

（[00:23:17]–[00:24:17]）

- ✅ **最具体的例子是 command-K 菜单**：网页上那个搜索菜单 **"经常是坏的、差的、怪的"**；而 **"你把它丢进 Jev，它快到瞬时，直接预测该去哪一页"**。
- ⚠️ **他指出被消掉的是一个二选一**：**"以前你得做个决定——要么在 JavaScript 里查一张表、把所有状态都加载进来，要么用 AI、然后你就得等着 token 流出来。现在你不需要这个决定了。"**
- **机制**：**"基本是瞬时的。所以你可以直接排这 20 个——这是用户可能去的 20 个页面，他敲了这三个字母，他想去哪个？这种排序会让很多奇怪的东西手感变好。"**
- ⚠️ **他对公共讨论的不满**（[00:24:17]–[00:25:17]）：**"我被关于 Jev 和这类模型的一般讨论烦到了，因为那些最病毒的例子大多是蠢的"** / **"蠢得咄咄逼人"** —— 举例是有人说 **"现在我有 Jev 了，我可以保证输出是我想要的格式"**，他的反应是 **"哦我的朋友，你把自己暴露了"**。✅ **即把一个校准概率模型当成格式保证来用，等于没看懂它新在哪。**
- ⚠️ **另一处提到 Dots 没做这件事**（[00:23:17]）：**"我其实挺意外 Dots 就是纯文本打印输出……你明明可以生成动态的东西，但我意外地没看到任何关于 UX 的巧思。"**

### 一份带数字的流水线实测（[00:30:18]–[00:31:18]）

- **用法**：一条 **"agentic 记忆流水线"**，**"在 Jev（结构化输出）和一个 Soul 5.5 / Soul 6 类模型（更结构化的输出）之间来回，然后再用 Jev 做排序和重排"**，任务是 **"看我所有的 agent trace，告诉我该往我的 CLAUDE.md 里加什么"**。
- ⚠️ **数字**：**"我们拿一堆聪明模型试过，把 Jev 放进去之后成本降了 10 到 20 倍。"**
- ⚠️ **准确率被追问时的回答很克制**：对方先说 **"成本在分类上太容易降了"**，然后给 **"在我们所有 eval 上，它和 Opus 5.5 **不开推理** 的表现相当吻合"**（[00:31:18]）。
- ✅⚠️ **接着是一条本页认为很有意思的理论观察**（[00:31:18]）：**"如果你深想，没有明显的理由说分类需要像现在这样、总是要那么多推理才能给出好答案。"** ⚠️ **但同处立刻给了相反的经验事实："而且如果你用任何前沿模型做分类、又不给大量推理，它们在分类上糟糕得一塌糊涂。"** ✅ **本页认为这组对照正是 decision model 这个品类存在的理由，也是它最难被替代的地方。**

### ⚠️⚠️ "这东西没法被公正地 benchmark"——一处罕见的、厂商自己承认的评估空缺

（[00:25:17]–[00:28:18]）

- **厂商的态度**：**"Jev 的创始人（[Diogo Almeida](../people/diogo-almeida.md)）做的一件很有策略的事是：不要给我们跑 benchmark。"** 主持人补充 **"我把我和他的对话剪了精选——他在整期播客里重复了大概七次'我不信 benchmark'。他真的信这一点。"**
- ✅ **而席上部分同意，并给出了技术理由**（[00:25:17]–[00:26:17]）：**"在这种结构化分类上，过拟合某个具体领域真的真的非常容易——而这可能反倒没问题：如果你的任务是超可重复的，过拟合它就挺好，你可以有一个过拟合的分类器而完全够用，只要它被约束得很死。但 Jev 的整个卖点是超多样的数据、在极大范围的任务上都很好——所以我觉得它可能非常难被忠实地 benchmark。"**
- ⚠️ **于是结果是选不出来**：**Cloudflare 那个很小的模型据称"同样性能但快得多"，大的那个"性能更好而且明显更快"**（[00:25:17]）；而 **"那家公司在数据上干了两年，他们的数据无可挑剔。我们怎么分辨？"**（[00:26:17]）——答案是 **"是啊"**。✅ **本库 [评估与 Benchmark](../topics/evaluation-and-benchmarks.md) 上第一条"厂商主动拒绝 benchmark + 用户同意确实没法 benchmark"的双向记录。**
- ⚠️ **一条分类难度的判断，本页认为它是整期最被低估的一句**（[00:27:18]）：**"我有一个非常坚定的信念：分类其实真的真的非常难，而它看起来骗人地简单，因为你某种意义上只是返回一个 0 或 1。但我认为字面意义上的二分类是世界上最难的问题之一。"** 他给的旁证是 **"OpenAI 很久以前有篇很好笑的论文说幻觉其实就是个二分类问题，然后一堆人就说'太好了，OpenAI 解决了幻觉'——不是，它只是'真或不真'，而那真的真的很难"**。⚠️ **本库未核实那篇论文的内容，照录其转述。**

### 价值归谁：一家小公司能不能守住一个被三家抄的品类

（[00:26:17]–[00:29:18]）

- ⚠️ **公司自己的问法（由在席者转述，"我的一些朋友"）**：**"我们公司的核心问题是：如果 OpenAI、Anthropic 和所有人都有一个 Jev 式的东西，你会专门去弄一个 TypeSafe 的 API key，还是就用你手上的 OpenAI？"**
- **三种答案并列**：
  1. ⚠️ **"我其实是通过 Vercel AI gateway 用的，所以我没去弄 key。所以我不知道这对他们是好是坏。"**（[00:27:18]）✅ **本页认为这是最锋利的一条——分发层把品牌抹平了。**
  2. **"我觉得它会跑在设备上。我不想再要网络上的 Jev 了，模型在变便宜"**（[00:26:17]）；对方补 **"WebGPU 上已经有了，可能达不到 Jev 的质量，但话说回来我们没法分辨"**（[00:27:18]）。
  3. ✅ **品牌 + "不只是模型，还有怎么想这件事"**（[00:28:18]）：**"他们不仅是 Jev 这个模型的专家，还是'该怎么思考 Jev'的专家。他们发过一个关于怎么造 harness 的东西，还说'我们想过用 Jev 造一个 harness，我们决定不做，这是开源的、你自己怎么加到你的 harness 里'。"** ——评价是 **"非常非常聪明"**。另有 **"他一直很擅长说'不，这是一种蠢用法'"**。
- ⚠️ **本页记一条明确标为传言的数字**（[00:26:17]）：**"传言 TypeSafe 这周关了一轮 100 亿美元"** —— **原话就带 "the rumors are"，本库不作为事实收录。** ✅ **本库 [TypeSafe 专访页](20260921-latent-space-typesafe-jev-system-one-models.md) 记的是 2026-09 的产品主张，没有融资数字，两处不冲突。**
- ⚠️ **OpenAI 为什么现在才进**（[00:31:18]–[00:32:20]）：有嘉宾说他去问过，**"我得到的、不引述任何具体人的字里行间的答案是：Jev 这类东西证明了这个品类存在、有市场契合，然后我们的开发者会希望我们在这块也有东西，所以他们就发了"**。⚠️ **这是明确标注为二手且不具名的转述。** 同处还有个未说出口的玩笑：Jev 创始人在播客里说过这个想法是他拿给 Sam Altman、Sam 说"好主意你该去做"的——**"所以我真的很想跟 Sam 开个玩笑：你是不是等你哥们先发了，你才进这个品类。"**
- ✅ **一条对"一次性公司"论的反驳**（[00:29:18]）：**"去看一家很久以来第一个改变了人们使用模型方式的公司，然后说'就这样了，他们到头了'，那会非常愚蠢。"**

## 六、模型选择与"新一代"：带数字的几处，和一条关于实验室自用的观察

来源：[Latent Space / High Taste Testers](20261016-latent-space-high-taste-testers-products-vs-models.md)

### 各自在用什么（[00:32:20]–[00:33:22]）

- **"主要是 Astra ultra，开最快的模式"** —— 被问"你能烧多少"时答 **"我大概 20 分钟就能把一整周的额度烧完，很容易"**，但 **"我觉得值"**。
- ⚠️⚠️ **一条明确标为"我的套话（party line）"的风格判断**（[00:32:20]）：**"Claude 模型有灵魂。GPT 模型显然没有灵魂……几乎是设计使然。像是出色的工程师，零灵魂。而 Opus 5.5、Fable 有灵魂。"** 他的用法后果是 **"任何和写作有关、甚至只是沾边的事我都大量用 Opus 5.5"**。
- **对方承认这是公开问题**：**"Sam 非常公开地说过这个。他说我们知道我们的模型不擅长写作，我们在努力追上。"**（[00:33:22]）

### ⚠️ Anthropic 版本史在用户侧的实际手感（[00:33:22]–[00:35:23]）

- **给出的版本评价**：**"4.6 是最后一个很棒的 Opus，4.8 是一团糟"**，**5 很差**，而 **"5.5 就是 4.6 但更聪明"**。
- ✅⚠️ **一条带业务后果的一手记录**，本页认为是本节最该引用的：**"我每天跑 AI 摘要，默认模型一直是 5.5"**——⚠️ 注意按上下文这里指**旧的 Sonnet/Claude 5.5 这一档**而非 Opus 5.5——**"我们从 4.6 换到 4.8 的时候，客户真的生气了，他们说'我读不下去'，还发截图过来。"** ✅ **即模型升级在一个具体产品里是可读性回归，并且被用户用截图举证。**
- ⚠️⚠️ **一处关于厂商自我评价的异常**（[00:33:22]–[00:34:22]）：**"Claude 这次发布另一件有意思的事是，他们基本上出来把自己以前所有版本的 Claude 都喷了一遍"**——**"他们做了那种梗图，说它慢慢变差、然后 5 是现在这个、我们修好了"**，**"而他们直到现在才承认"**。评价是 ⚠️ **"对 Anthropic 来说很不一样。我不觉得他们以前做过这种事。"** ✅ **本库 [AI 实验室文化](../topics/ai-lab-culture.md) 上第一条"厂商公开承认自家旧版本退化"的记录。**
- ⚠️ **但同席有人不买账**：**"我其实没那么感觉到"** —— 对方的解释是 **"他们只是没在用高品味的东西"** / ⚠️⚠️ **"Anthropic 没人在用 Opus。他们一直在用 Fable。"**
- ✅⚠️⚠️ **本页认为这是本节最可迁移的一条**（[00:34:22]）：**"我不觉得他们在用已发布的模型。他们在用未发布的模型。他们一直在试玩，而且是无限量、超快的——那和用户拿到的是完全不同的体验。"** ✅ **这给"实验室为什么会误判自己发布的模型"提供了一个具体机制，与第一节"实验室在产品上吃亏"同向。**
- **而发布后的意外**（[00:35:23]）：**"我真以为 Opus、Sonnet 这些会永远是被遗忘的孩子，尤其是 Opus 5 那么差之后。结果他们把它带回来了，而且带得这么漂亮。"**

### ⚠️ "新一代"的分界，以及它怎么改变够用的档位

- **大小模型分工的现状**（[00:35:23]）：**"现在 Anthropic 有一个差不多 5.5 的选项，OpenAI 有一个 6.1 Soul，这让你几乎不需要去拿 Astra / Fable 来做日常工作了"**——**"对大多数人那些模型就够了，去拿大的是为了'赶紧把这个季度干完'那种：重构一切、审查巨大的东西，或者真正难的任务。"**
- ⚠️ **一条对"代"的定性尝试**（[00:51:30]–[00:52:32]）：**"模型能力有这么几条能力线，所有东西都会逼近它、又过不去——它们几乎贴到线上了却跨不过去，直到你突破那个天花板，然后你到下一个能力平台，大家再追上来。"** 他的断代是：**"夏末在 Astra 和 Fable 5.1 之前，所有人都在逼近上一代的天花板——子 agent 编排、长任务、能解很多问题，但没有现在新模型里那种力量和判断力（discernment）。"** 他列进"新品类"的只有 **6.1、Soul、Astra、Opus 5.5、Fable 5.1**。
- **被追问"能给这个品类命名吗"时的回答**（[00:52:32]）：**"大的那条是真正好的 swarming 行为"**，然后承认 **"很难给一个严格的词"**，另一位接 ⚠️ **"除了'信任'想不出别的——这些新模型身上有某种程度的信任。"**
- ✅ **一处很好的自我降温**（[00:52:32]）：**"每次新一代来的时候，总有个梗要病毒式传播一下，比如那个 blender slop 或者那个视频"**——**"那就是营销"**。✅ **本页认为这条值得保留，因为它出自同一批正在给新一代下定义的人。**

### ⚠️ 一份部分数据：Opus 5.5 写的代码量与测试占比（[00:50:30]–[00:51:30]）

- **出处**：一个叫 **"slop code bench"** 的 benchmark，**"出自威斯康星大学的一个实验室"**，由在席者在跑。

### Grok 4.7 的一次集体负面评价，以及它唯一被认可的位置（[00:45:27]–[00:49:28]）

- ⚠️ **定价**（[00:46:27]）：**"他们太急着说这是更好的模型但同价。而那根本不成立：context window 超过 200k，价格翻倍；开快速模式，价格翻倍；两个一起开，接近三倍。"** ✅ **所以"最后变成一个很贵的模型"。**
- ⚠️ **token 效率**：**"糟糕透了。它会走那么多步、推理那么多。"**
- ✅ **本页认为这是最清楚的一句定位批评**（[00:46:27]）：**"它不是那个快的模型——那现在是 Muse；不是便宜的那个——那是 Muse 或 Luna；也不是能力最强的那个——那是 Opus。Opus 没那么高效，但它强到无所谓。而你在 Grok 上付的是 Opus 的价。"**
- ⚠️ **归因**：**"它唯一手感好的地方是 Grokbot，因为他们在 Grokbot 上对模型做了 RL——我感觉就是他们把它献祭给 Grokbot 了。"**
- ✅⚠️ **但 Grok 作为产品被一致认可，而且理由是数据不是模型**（[00:47:28]）：**"Grok 不只是模型，Grok 还是 grok.com 这个产品，以及 X 里面的 Grok——它能拿到 Twitter 的实时数据，别的模型都没有，这给了它研究上的超能力。"** 被问"为什么"时的回答是 **"它是最好的研究模型"** / **"每天都用"**。
- ✅⚠️⚠️ **一条非常具体、可直接用的技巧**（[00:48:28]）：**"Grok 的 build CLI 其实是个很好的 CLI，但它最有用的地方是你可以让别的 agent 把它当子 agent 来调，因为它原生带 X API 能力、免费不限量。"** —— **"不用给 Twitter 接 MCP，你就说'要 Twitter 的东西就去'，让它调那个去取帖子。"** ⚠️ **同席对"不限量"和"工具是否自动暴露"都提了保留**："我不知道是不是不限量" / **"你在 build CLI 里可以，但我不觉得登录之后那个工具会自动被暴露出来"**，最后以 **"我们录完查一下"** 收场。✅ **本页照录这处未解决。**
- **一个已修的 bug 被当作产品教训**（[00:47:28]）：X 内置的 Grok **有一个半月不知道用户是谁**（"把我说过那条推拉出来"→"你好，我不知道你是谁"），**而 grok.com 知道，因为你在那儿是登录的**。

### ⚠️ 开源与本地：一条被明确拉大的差距（[00:49:28]–[00:50:30]）

- **硬件与模型**：**"我有四台 DGX Spark"**，⚠️ **买入理由很值得记**：**"GLM 5.3 Flash 出来的时候我一看模型体积就想，哦，这些东西要涨价了。所以我立刻给我爸发消息，让他去俄亥俄的 MicroCenter 在涨价之前替我买下来。"** ✅ **他自己的评语是本页最好的一句旁白："我在算力上赚到了钱，这很蠢。它不该升值。"**
- **本地模型的实际结论**：**"它确实能干成事，很好玩，对任何能用验证硬磨下去的 hill climbing 问题都有用"** —— ⚠️ **"但对真正的日常工作没用。前沿（OpenAI）和字面意义上的其他一切之间有那么大一道鸿沟，我不觉得目前可行。"**
- ⚠️⚠️ **而且他给了一个明确的时间判断变化**：**"曾经有个时刻开源模型只落后六个月；然后 Opus 出来——5.5 这个最新的，还有 6.1——前沿又直线上冲，开源就不在那儿了，可能差一年。"** ✅ **本库 [开源基础设施](../topics/open-source-infrastructure.md) 上第一条来自重度本地部署者、且方向是"差距在 2026 下半年重新拉大"的一手口径。**

## 七、agent 循环、子 agent 与上下文：这一期最密集的实操段

来源：[Latent Space / High Taste Testers](20261016-latent-space-high-taste-testers-products-vs-models.md)

### ⚠️⚠️ 过夜跑的那条闸门，以及它为什么刚被打开（[00:36:23]–[00:37:25]）

- ✅ **这是转录稿开头被剪进预告的第一句，也是本页认为全期最该被引用的一条使用纪律**：
  > **"我其实真的相信，如果你在做生产软件，你整夜不停地跑模型，你会造出比你能可靠消费和吸收的更多的代码。"**
- ⚠️ **而他自述这条闸门刚刚被模型质量打开**：**"5.5 之前……它终于好到让我进入那个状态了。我很久没干过这件事，因为我相信上面那句。"** —— 现在是 **"我手上有 10 个不同的原型，我想，好，我真的在做那件事了：晚上 10 点你把夜间 agent 都起来，早上 9 点你登上去干活。"**
- **推理档位**：**"说实话很多就是 medium 或 high。"**
- ✅⚠️⚠️ **具体技法——"有界的 Ralph 循环"，本页认为这是最可直接照做的一条**（[00:37:25]）：
  > **"我会做一个穷人版的 Ralph 循环：我就排一串提示——做这个；好，现在做一次更好的 compact；现在做这个；现在读计划；现在继续把它做得更好；然后 compact。这些会排队、过夜跑，而不是……所以它像 Ralph 循环，但是有界的。你只排 5 到 10 条消息。"**
  - **同席给的类比**：**"你在下棋，而且每一步都预先走了（premove）。"**
  - **他排的提示里有两条是直接骂**：**"嘿，这设计烂透了，重做"** / **"整个架构太复杂了"**。
- **并行的办法**（[00:37:25]–[00:38:25]）：一个 **"detach 模式"的 skill**——**"有点像那个（前台跑的东西），但你在后台跑：你起 CLI 版本、带上 agent，然后丢到后台"**，理由是 **"这样我能并行跑 40 个"**，然后 **"你可以盯日志，也可以全部暂停、改进日志、再重跑"**。

### 子 agent vs 多会话：一条来自厂商的机制性说法（[00:38:25]）

- ⚠️ **"我问过 Codex 的人，Codex 能不能起多个你能看见、能对话、还能互相对话的 Codex 线程……但他们也有子 agent 这个原语。好几位 Codex 的人都说，**子 agent 明显更好更快，因为缓存优化、以及模型对待子 agent 和对待不同会话的方式不同**。"** ✅ **本库此前关于子 agent 的材料多是使用偏好，这是第一条给出"为什么"的厂商口径（⚠️ 二手转述，不具名）。**

### 配置数字（[00:38:25]–[00:39:25]，⚠️ 均为个人设置）

| 项 | 实测 |
|---|---|
| **子 agent 数量** | **"我 toml 里放到 48 个的时候，Astra 两小时就烧穿了我的额度"**，于是退回默认；另一位 **"我保持在 15 左右"** |
| **上下文** | **"如果你有不限量的访问，100 万 token 我觉得是个好主意"** |
| **auto-compact 阈值** | **"我昨天把 auto-compact 设成了 400k"**；对方指出 **"默认大概是 275"** |
| **加子 agent 的方式** | **"你可以直接在 config 里说给我更多子 agent，也可以直接叫 6.1 去做，它就会做"** |

### ⚠️ compaction 是被集体讨厌的那个原语（[00:39:25]–[00:40:25]）

- **想要的不是更好的摘要，而是别摘要**：**"我希望能在 Codex 里关掉 compaction"** / **"我希望它只是截断工具输出、截断字面上任何东西，除了摘要"**。理由很具体：**"很多时候前面消息里就是一堆图片或者一堆别的什么。"** —— **"你想把最大的那些剥掉。"** / **"对，就把那种剥掉。"**
- ⚠️ **有人提到 Claude Code 内部曾经就是这么做的**（"以前内部会那么做，我不知道现在还做不做"）。
- ✅ **一个顺带提出的、与第五节接得上的想法**（[00:39:25]）：**"我希望他们用 Jev 来做工具调用，需要的时候再把全部还给模型。"**
- ⚠️ **Claude Code 的 compaction 有个被多人确认的症状**（[00:40:25]）：**"它会以为自己是个新人——'嘿，我看到你之前在做什么'"**，被叫作 **"Memento 时刻"**；**"我碰到过好几次"**。
- **对 OpenAI 的 compaction 评价**：**"我很喜欢"**，但 ⚠️ **"它很慢，太慢了"**——**"如果你在跑 20 个东西，那就有影响"**。

### ⚠️ 主线程该不该干活：一处明确的相反做法（[00:40:25]–[00:42:26]）

- **一派（chief of staff 模式）**：**"别在主线程里干任何活。我不要你的上下文——你的上下文应该是我和你的对话，不是执行。执行该发生在别处。"**
- ⚠️ **另一派当场说"我反过来做"**：**"我在（主线程里）做事，然后在旁边开一条关于这件事的对话"**——理由是 **"那条支线是易逝的（ephemeral）"**。✅ **本页照录这处分歧，不做裁决。**
- ✅⚠️⚠️ **而对最难的问题，他们给的是同一个配方**（[00:40:25]）：**"要跑超重的长循环，那肯定是最好的办法。我唯一能让它啃下那些我用任何模型都搞不动的变态问题的办法，就是：开 ultra，给它大量子 agent，然后告诉它——你唯一的工作就是派发子 agent；给它们设个计时器；如果它们停了或者偷懒了，就一直推它们。它就是那台推进机器。"**
- **他们自己给的组织类比**（[00:41:25]）：**"有点像大公司里那个模式——开发者升到自己无法胜任的管理层级。但公司其实很想让开发者一边管人一边继续写代码。"** 而他的立场是 **"我这边正相反：我不想让主管的那个去写代码、去跑工具，我只想让它用最好的方式去告人、然后复核、然后拿回来"**。
- **监督机制**（[00:40:25]）：**"我一直有一个 skill，开一条支线去看主线程的推理。"** 而且**他们确实在看轨迹**：**"你会抓到它跑偏得很厉害"** / **"你看到那个思考，你就'不行，我其实要的是——'"**。⚠️ **问的人自己先说"我会看，而且我觉得我做错了"，得到的回答是"不，我也看"** ——✅ **本页认为这处犹豫本身值得记：盯轨迹是不是浪费时间，这群人也没有共识。**

## 八、⚠️⚠️ 助理碎片化：本期发现的那个新成本

来源：[Latent Space / High Taste Testers](20261016-latent-space-high-taste-testers-products-vs-models.md)

（[00:56:34]–[01:02:37]）这是一位嘉宾主动"带到桌上"的问题，而且**全席都承认没有好答案**。

- ⚠️⚠️ **问题陈述**（[00:56:34]）：**"这是我用了很多这些工具之后注意到的一个问题：我在想人们会不会就选一个然后一直用，因为在这些工具之间切换是有注意力成本的。我现在到了这种地步——我不记得哪段对话是跟哪个助理进行的。"**
- ✅⚠️⚠️ **而本页认为真正的发现是接下来那个比喻，因为它解释了为什么"导入记忆"不管用**（[00:56:34]–[00:57:35]）：
  > **"把它们的记忆从一个导到另一个也不够好，因为它们的记忆是以不同方式移动的。如果你把它们当成克隆体——克隆体在某个点上开始过上不同的人生，这个知道这件事，那个做了那件事。"**
  - **于是他的问题是分法**：**"好吧，是按用例分吗？我只去 Grok 办工作的事，然后用别的管个人？你们怎么处理这个？我真的想知道，我没有好的解决办法。"**
- **另一位的回答是 "我有个办法，但不好"**，而这个办法是本页认为最具体的一条基础设施应对（[00:57:35]）：
  - ⚠️ **中心化 MCP 网关**（朋友在做的公司，稿中名为 **Executor**）：**"基本就是一个大的 MCP 网关，装着我所有的连接——Gmail、Google Drive、Notion 等等。它跑在我家里一台 Linux 机器上，我用 Cloudflare 的 DNS 代理，这样我任何设备都能连到它。"**
  - ✅ **关键在于它装的不只是连接**：**"现在我每配一个新的个人助理，我只做一次 MCP 连接，登录，然后它就有了我所有的工具——而这些工具里包含了用它们的 skill、用它们的 prompt、每个的配置。"**
  - ✅ **他给的收益是把最烦的那层拎出来**：**"我的核心连接层——也就是配起来最讨人嫌的那部分——集中在一个地方，所有设备共享。所以我在那儿改一个东西，到处都改了，而真正干活的界面就变得相当轻量。"**
  - ⚠️ **他自己给的例外**（[00:58:36]）：**"有些按产品的连接器我还是会用原生的，比如金融连接器——我真的很喜欢 Grokbot 里的金融连接器，有用，但那个我不会走直连 MCP。"**
- ⚠️ **碎片化的实际形态（各自的分法，[00:59:37]–[01:01:37]）**：
  - **"我用 Instinct 做不需要我数据的事，就是去和商家沟通、帮我订活动之类；我的个人助理还是一个 git repo + 一堆脚本。"**
  - **"我基本是 Grokbot 管所有工作行政类的事，但很多管理还是在 Codex 里做。"**
  - ⚠️⚠️ **"我同时在用 Poke、Lindy 和 Instinct，这是地狱。"**
  - **最极端的一份清单**（[01:01:37]）：**Codex 为主 + 自建 harness、一个"大体保持更新"的 Hermes agent、**"大约 30 个 Grokbot 各干不同的事"**、再加 Muse 和 Dots、以及 Instinct。
    - ✅ **他的分法里唯一被他自己称为"看起来在起作用的模式"的**：**"Grok 主要管工作，比如个人的公司管理。我在那边有一个 chief of staff、一个 PM。我在它们之间接了一个 Linear 连接器，它们全都通过 Linear 开工单，这样它们可以互相 @。"**
    - ⚠️ **还有一条很土但诚实的做法**：**"如果有个任务三个都能做、又不会造成伤害，我就复制粘贴发给三个，看谁更好、谁更快。"**
    - **他给 Muse 的位置是一次性语音问题**（[01:02:37]）：**"我的酒店离那个地方多远？我几点得出发？"** —— **"立刻就出来了。"**
- ⚠️ **另一位的立场是"零信任"**（[01:00:37]）：**"Codex、我自己搭的那个带我自己小 Google Drive 的东西……对任何东西都零信任。"** 而且 **"邮箱我甚至连读都怕——因为有些情况下你的二次验证码是发到邮箱的"**。✅ **本页认为这条和第四节那份"三家可信名单"是同一个人的两面，但稿中无标签，本库不并案。**
- ⚠️ **而主持人给出的规范性判断与所有人的实践相反**（[01:08:43]）：**"其实你们在做的一切，对你们自己的最佳体验来说都是次优的——应该有一个东西拥有你所有的搜索历史。所以你不该路由。路由是坏的。"** ✅ **当场的反驳也很干脆："但不测你就当不了 high taste tester。"**

### ⚠️ 支付：想要的是每个供应商一张虚拟卡（[00:58:36]–[00:59:37]）

- **需求**：**"我唯一想要写权限的是——有些人对每个供应商都用一张不同的虚拟信用卡，我太懒了不想弄。但如果我能告诉我的 agent：去 Mercury 上开一张虚拟卡然后……"**
- **被指出已有产品**：**"那是 link.com，那是他们的钱包，它就是干这个的。你把那个 skill 给你的 agent，它为你助理的每一笔消费生成一张虚拟卡，然后你批准。"**
- ⚠️ **但他给的限制很具体**：**"它们还是都走我同一张卡，所以我没法设单独的限额、也没法设有效期。"** —— **"我只是想给 AWS 一张、G Suite 一张之类。"**
- ⚠️ **同席还有一条明确的拒绝**：**"我不想给我的 agent 一张卡。"** ✅ **本页认为这组对照值得与 [VGS 那期的 agentic token](20261015-a16z-vgs-agentic-tokens-wallet-wars.md) 对读：那期是发卡与清算一侧讲"agent 长出了手脚"，这期是使用者一侧讲他们到底想要什么形状的手脚——答案是"按供应商隔离 + 带限额和有效期"，而现有产品只做到了"每笔一张卡 + 人工批准"。**

## 九、委派、日常与"低估的东西"

来源：[Latent Space / High Taste Testers](20261016-latent-space-high-taste-testers-products-vs-models.md)

### ⚠️ "Devin 就是一台电脑"：为什么沙盒形态比仓库形态重要（[01:03:37]–[01:04:38]）

- ⚠️ **他说这是几乎每家公司都掉进的同一个坑**：**"Devin 默认就只是一台电脑。就像一个在电脑上的 agent——你可以建个 repo，可以用一个已有的 repo，可以跨 repo 工作，就是一台电脑。所以它在这方面超级灵活。"**
- ✅ **他给的使用后果**：**"我每有一个野点子，我就去那儿。"** 而别的东西 **"会问：你想在哪个仓库里工作？"** —— **"有时候你根本不想待在一个仓库里，你就想要个东西。你就是有个想法，而如果它非要在一个仓库里工作，它就会'那我把它加到这个页面'……我就是想试一下这个新模型、试一下 Jev、试一下随便什么，有个沙盒太好了。"**
- ⚠️ **对 Cursor 的具体抱怨**（[01:03:37]）：**"Cursor 好，但要从它身上拿到好东西太费劲——你得给每个项目配好云环境、搞好环境变量、确保脚本是对的。对 agent 来说很容易，（对人）工作量太大了。"** 另加一条行为抱怨：**"它太爱开发了。你让它写点什么，它会发个 PR。我不需要 PR，我只需要一个答案。"**
- ✅⚠️ **而本页认为这一节真正的论点在这里**（[01:04:38]）：**"我觉得这也是助理和那些为写代码而造的 coding agent 的区别——它们被训练成做 diff 的活、写一个 markdown 文件、跟什么比对、塞到某个文档里、写测试。而我只想说：把那个东西写出来，给我。"** —— 配上那句对系统提示的吐槽：**"整个系统提示就是'呃我做不了那个。你今天想写什么代码？'——我不想写代码。"**

### 被点名"低估"的几样（[01:05:39]–[01:09:44]）

- ⚠️ **6.1 Soul**：**"它比大多数人以为的好得多，纯粹因为发生了些奇怪的品牌问题"**（Six Soul 上周、6.1 Soul 这周）——**"一个极好的模型，价格极好，值得一看"**，而且 **"它就是来跟 Opus 5.5 竞争的"** / ⚠️ **"字面上就是在给（对手）砍腿"**。⚠️ **同处有一条明确标为"字里行间听来、不想点名消息源"的说法**：**"它本来不叫 Soul，是最后一刻市场部决定的。"** ✅ **本库按传闻收录。**
- ⚠️⚠️ **Google 的 AI 搜索概览——这是本页最意外的一条**（[01:07:42]–[01:08:43]）：**"超级被低估。任何我想要快答案的问题，我都去 Google。"**（有人应"我也还在这么干"。）**理由是延迟："它真的很快，大概 300 毫秒，页面加载完答案就在那儿了"**，而 **"ChatGPT 我总在最大推理档，要改设置，可改了之后我新开一个对话它又是那个傻设置"** —— **"那就是 10 到 30 秒才拿到答案"**。
  - **替代路径**：**Raycast 的 AI**（**"command-enter，打你的东西，回车，完事"**，**"它会复制到剪贴板"**，模型 **"你想用啥用啥"**）；也有人提到 ChatGPT **"有个切到 instant 的键盘快捷键，那个还在"**。
  - ✅ **另一位给了一个相反方向但不矛盾的理由**（[01:08:43]）：旅行时**午夜在阿姆斯特丹下火车**，问助理"最近的火车站在哪"、"我能刷卡吗"，得到"可以，刷卡出门走两段"——**"它大概没 Google 快，但如果我只想要一个是或否、或者一个很短的答案，它压倒性地没那么让人招架不住。而且因为你刚说的那些原因，我不会去开 ChatGPT app。"**
  - ⚠️ **本页判定**：这组对照里真正被说出来的变量是**延迟**和**信息过载**，不是答案质量——✅ **三个人里没有一个人说 Google 的答案更好。**
- **Alex Volkov 的那一条是"用例而不是产品"**（[01:05:39]–[01:07:42]）：他的论证是 **"在极限上它们大多做同样的事：大多能订东西，大多能回你邮件、扫你邮件。所以聊用例比聊产品有意思"**，并给了自己的一个：
  - ⚠️ **"某个周末我早起带孩子去上空手道课，到了发现没开，我火大了：到了 2026 的主动助理时代，居然没有任何东西提前告诉我'你要去的那个课不开'。"** 于是他做了一个 **"周末计划 bot"**——"每到周末就去搜所有本地的地方、所有我永远不会点进去的网站……然后说：如果你想，这儿有一堆可以做的事；哦顺便说，你本来要去的那个地方不开。"✅ **他的收获是一句很克制的话："现在我知道那个角落被盖住了。"**
  - ⚠️ **他同时给了一条关于实验室动机的判断，本页标明是他的推测**：**"实验室现在懂这件事了，所以他们都在转向更简单的用例。他们也都受益于这对每个用户意味着多少 token——因为大多数人还是打一个查询、拿一个回答。而有了个人助理，他们突然就被接到那条甜美的 token 流上了。"** ✅ **即他认为助理化同时是产品动机和收入动机。**

### 硬件：一条预测和一条反驳（[00:02:02]–[00:04:03]、[01:09:44]–[01:11:45]）

- **开场就在等设备**（[00:02:02]–[00:03:03]）：**"Johnny IV 这次不在台上"**（⚠️ 指 Jony Ive），上一次他和 Sam 同台 **"承诺了有东西要来"**，官方口径是 **"年底"**——⚠️ **而席上的时间感是："三到六个月在现在基本就是长期了。"**
  - ✅ **一条值得记的猜测**（[00:02:02]）：**"我的理论是它不是一个独立 app，它是一个独立设备。"**
  - **大家想要的是家庭助理**（[00:03:03]）：**"我猜 OpenAI 大概会做那种家庭助理，像 Google 的、Amazon 的那个叫 Echo 的东西"**；有嘉宾说 **"至少两年半来我一直在想为什么没人做这个，这很容易"**，而且 **"我和朋友一两周前用一个周末就搭了一个，它能用"**。⚠️ **他给的差别是 harness 而不是模型**：**"区别在于有老办法和新办法——它有 computer use 工具、MCP、CLI 这一整套 harness，而没人真做过这个。"**
- ⚠️ **一条明确标为预测的**（[01:10:45]）：**"小预测，你们看它会不会成：Zuck 展示的那个 charm 小东西——那个 Muse 住在里面的小 Tamagotchi——会立刻卖光。"** 理由是 **"对刚接触 ChatGPT、刚接触助理的人，上手 Muse，那是个完美的圣诞礼物"**。✅ **他还加了一句很有意思的话："我的 agent 的计划里要买大概六个。每个 agent 都会买一个。"**
- ✅⚠️⚠️ **而反驳本页认为更结实，因为它是个约束而不是偏好**（[01:10:45]–[01:11:45]）：**"要充电的东西的数量已经饱和了。有些人有足够责任心能照顾一只手表，但那其实是个很小的数目。我没有 Apple Watch 的原因就是我总会忘了充电。"** 对方说 **"这问题已经解决了，带那种小充电宝就行，15 美元，买四个，到处放"**，他的回答是 ⚠️ **"没解决，因为那样我还得记得——'解决办法是再加一个要充电的东西来充那个东西'，这不work。"** 最后收在 **"对我不work。"/"对你不work。"** ✅ **本页照录这处未达成一致。**
- **已经落地的硬件集成**（[01:09:44]）：**Grokbot 进了 Tesla**（"ultra 那个档现在把 Grokbot 放进你的车里"），用法是 **"你对 Grok 做语音转文字，说'去告诉这个 bot 做这件事'，它就发给那个 bot，然后它会告诉你'那个 bot 回复了什么'"**——评价是 **"车自己开，还替你办事"**。
